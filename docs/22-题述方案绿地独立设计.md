## 0. 绿地约束前提（本方案成立的假设）

1. 目标是**可上线的多租户 SaaS**，不是单机 Demo：允许/应当使用外部基础设施（K8s、消息队列、关系库、可观测后端）。
2. 团队无历史包袱，技术栈自由选择；有常规 SRE 能力。
3. 题一仍以「可视化画布 + Schema 驱动配置」为产品形态（题目六项要求本身暗含画布）；题二以「电商退款运营体」为业务样板，金融合规要求不变（资金动作可审计、可灰度、可回滚）。
4. 多 Bot 为**独立部署的服务**，通过网络协作，不是进程内函数调用。
5. 本文给具体业界选型（写产品名），但每个选型标注**它承载的抽象**，换等价产品不影响架构成立。

# 题一：Schema 驱动配置内核（绿地版）

## 1.1 核心模块划分

总体仍为「Schema 层 / 渲染层 / 校验智能层」三层，但绿地版直接采用成熟生态组件，不自研校验器与表单渲染器：

```
┌────────────────────────────────────────────────────────────────┐
│                       Editor Shell (SPA)                        │
├───────────────┬──────────────────────┬──────────────────────────┤
│ Schema 层     │ 渲染层               │ 校验/智能层              │
├───────────────┼──────────────────────┼──────────────────────────┤
│ Schema 服务    │ Form 内核: rjsf 或    │ AJV 2020-12（编译缓存）  │
│ (版本化注册表, │ Formily（递归渲染/   │  → L1 字段校验           │
│  服务端发布)   │  oneOf/if-then 原生) │ Monaco/CM6 + 语言服务     │
│ JSON Schema   │ Widget Registry      │  → L2 {{}} 诊断/补全     │
│ 2020-12 +     │  (自定义控件扩展点)  │ Graph 静态分析引擎        │
│ $vocabulary   │ UISchema/联动规则     │  → L3 可达/环/分支完备    │
│ 自定义 vocab  │ Expression 编辑控件  │ Diagnostic Bus (LSP 形)  │
│ (vocab 治理)  │ (Monaco Editor)      │ Incremental Engine       │
│               │                      │ (Web Worker/增量)        │
└───────────────┴──────────────────────┴──────────────────────────┘
              Canvas: React Flow（节点图） / 或 workflow-as-code 双形态（§1.6）
```

| 模块 | 绿地选型（承载的抽象） | 为什么不自研 |
|---|---|---|
| 表单内核 | **react-jsonschema-form (rjsf v5)** 或 **Formily v2**（Schema→递归表单） | object 递归/array 增删/enum/oneOf/if-then/联动均为内置能力，正是 Atlas 版要分期造的东西 |
| Schema 校验 | **AJV 严格模式 + draft 2020-12**，standalone 编译产物按 `$id@version` 缓存分发 | 全 keyword、编译缓存、自定义 keyword（vocabulary）有官方机制；无「手写子集」动机 |
| 表达式编辑 | **Monaco Editor**（或 CodeMirror 6）+ 自研轻量 language service（monarch 词法 + CompletionProvider + 语义 token） | 补全、悬浮提示、token 高亮、多光标是编辑器原生能力，textarea 方案直接跳过 |
| 画布 | **React Flow**（形态展示/连线）+ 自研图模型（不可变图状态） | 画布只负责视图，图语义在独立的图模型层 |
| Schema 来源 | **Schema Registry 服务**：内置 schema 随制品发布，工具/技能 schema 由各适配器服务在注册中心上报版本，前端按 `entity@version` 拉取并长期缓存 | 多租户、多适配器团队时 schema 是分布式契约，需要服务端版本化与兼容检查 |
| 诊断总线 | 对齐 **LSP Diagnostic** 形状（severity/range/data.code/quickfix 候选 action） | 直接获得「定位→跳转→quickfix」的交互语义，且 Monaco 原生消费 |
| 增量计算 | **Web Worker + 结构版本号 memo**；大图上图分析用增量图算法；编辑事务化（OT/CRDT 非必需，单人编辑即可） | 500+ 节点不阻塞主线程是上线级编辑器的默认要求 |

扩展机制（题面要求 2）落地为两层：**Widget 注册**（`WidgetRegistry.register(name, comp, meta{schemaKinds})`，业务控件以独立 npm 包形式发布、按需加载）+ **JSON Schema 自定义 vocabulary**（`$vocabulary` 声明 + AJV keyword 实现成对发布，服务端 Registry 做 vocab 准入审核——`x-` 前缀式的野生长尾在生产多团队下不可接受，必须有 vocabulary 治理）。

  AJV(worker)  Expression LS              Graph Analyzer(worker)

                    │
     ┌──────────────┼───────────────┬──────────────────┐
     ▼              ▼               ▼                  ▼

     └──────────────┴───────────────┴──────────────────┘
                    ▼ quickfix action → applyWorkspaceEdit
保存/发布 ──► 编译服务（同一 JSON Schema + 同一分析规则的服务端权威实现）

与 Atlas 版相同、属于通用原则的两条：①**编辑流与提交流共用规则、分开执行**——绿地版更进一步，schema 与图分析规则以**服务端编译产物**（AJV standalone code + 规则包版本号）下发，浏览器和 CI 跑同一份制品，杜绝双端规则漂移；②诊断全链路结构化（LSP 形），错误定位不是文案拼接。

## 1.3 关键 Schema 示例

绿地版直接采用 JSON Schema 2020-12 正式机制：自定义语义进受治理的 vocabulary（示例用 `https://atlas.example/schemas/vocab/editor`，产品中换自有域名），而不是无主的 `x-` 散点。

**节点 Data Schema（审批节点）**：

```json
{
  "$id": "https://registry.example.com/schemas/node/human_approval/1.2.0",
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "type": "object",
  "required": ["summary", "approver", "timeoutSeconds"],
  "properties": {
    "summary":        { "type": "string", "minLength": 1, "editor:variable": true },
    "approver":       { "type": "string", "editor:widget": "approver-picker" },
    "timeoutSeconds": { "type": "integer", "minimum": 10, "maximum": 3600 },
    "onTimeout":      { "enum": ["approve", "reject"], "default": "reject" },
    "approvedTarget": { "type": "string", "editor:nodeRef": { "kinds": ["*"] } },
    "rejectedTarget": { "type": "string", "editor:nodeRef": { "kinds": ["*"] } }
  },
  "if":   { "properties": { "onTimeout": { "const": "approve" } }, "required": ["onTimeout"] },
  "then": { "required": ["approvedTarget"] },
  "editor:outputSchema": {
    "type": "object",
    "properties": {
      "decision":   { "enum": ["approved", "rejected"] },
      "resolvedBy": { "enum": ["human", "input", "timeout"] },
      "target":     { "type": "string" }
    }
  }
}
```

**工具/适配器能力声明**（由适配器团队随服务发布注册，CI 校验 schema 向后兼容：只允许加可选字段/加 enum 值，破坏性变更必须升 major）：

```json
{
  "adapterId": "database", "tool": "database/query", "version": "3.1.0",
  "permission": "read", "idempotency": { "mode": "idempotent", "keyTemplate": "{{sql_hash}}" },
  "inputSchema":  { "$ref": "/schemas/tool/database/query/input/3.0.0" },
  "outputSchema": { "$ref": "/schemas/tool/database/query/output/3.0.0" }
}
```

**UISchema（rjsf 形：uiSchema 与数据 schema 分离）**：字段顺序、分组、widget、联动显式声明；联动规则（条件显示）用声明式依赖，不用命令式 effect：

```json
{
  "ui:order": ["summary", "approver", "timeoutGroup", "targets"],
  "summary":        { "ui:widget": "expressionEditor", "ui:rows": 3 },
  "approver":       { "ui:widget": "approver-picker" },
  "timeoutGroup":   { "ui:field": "collapsibleGroup" },
  "approvedTarget": { "ui:dependencies": [{ "when": "onTimeout == 'approve'" }] }
}
```

**自定义控件契约**（与 Atlas 版同构，但运行在 rjsf Widget 接口 + Monaco 上下文上）：`value/onChange/options/schema/rawErrors` + 注入 `scopeProvider`（查 visibleAt）、`diagnostics`（命中级 range）、`commandService`（提交 quickfix WorkspaceEdit）。

四类形态映射不变（嵌套→properties 递归；数组→items+array 控件；枚举→enum；条件→if/then 管合法性、ui:dependencies 管观感）——**这部分两版完全一致，属于题目通用解**。

## 1.4 变量作用域索引设计

机制与 Atlas 版相同（拓扑推导，非全局平铺），绿地版的差异在工程承载：

- 作用域索引在 **Web Worker 内的语言服务**中维护，前端通过异步 RPC 查询（补全/悬浮场景天然异步）；
- 符号的类型信息来自 Registry 上各实体的 **outputSchema**（绿地版要求适配器注册即声明 outputSchema，没有「缺省时降级仅存在性」的长期状态——那是迁移期兼容口径）；
- 索引产出 JSON Schema 片段供 Monaco 补全做**路径级类型推断**（补全项带 type icon、选中后自动补全后续路径段）；
- `secret.*/env.*` 来源对接平台的**密钥管理服务**（KMS/Vault 类）：编辑器只拿引用句柄和脱敏预览，永不接触明文；
- `reverseDeps` 除增量失效外，直接驱动两个生产功能：**改名重构**（rename symbol → WorkspaceEdit 全图改引用）与**数据依赖环检测**。

可见性规则（trigger/global 恒可见、入边反 BFS、loop 体区域、parallel 汇聚点后见 result、subgraph outputs、受限来源单列）与引用四码（`NODE_NOT_FOUND / NOT_IN_SCOPE / PATH_NOT_FOUND / TYPE_MISMATCH`）两版一致，是通用解，不重复展开。

## 1.5 校验分层与伪代码

分层与 Atlas 版相同（L1 字段 / L2 模板引用 / L3 图级），差异在每层的承载：

- **L1 = AJV 严格模式**（编译期把 `$ref` 全部 bundle，禁 additionalProperties 意外放行）；错误经 AJV `instancePath` 直接映射 JSON Pointer，无需自研指针定位；
- **L2 = 表达式语言服务**：monarch 词法切 token → scopeProvider 解析 → Diagnostic.data.code 四码；
- **L3 = 图静态分析器**：不可达用 BFS 支配/可达分析；控制流环在摘除合法回边（loop）后跑 DFS；数据依赖环跑 reverseDeps 图；分支完备是一组针对节点种类的结构化规则（condition 缺 default/有边无分支、parallel 分支约束、loop body/exit、审批双出口、普通节点悬空边/自环/违规直连 END）。

```
onTransaction(tx, graph):
    hash = structuralHash(graph)
    if indexCache.has(hash): reuse
    diags = []
    diags += ajvValidate(changedEntity.kind, changedEntity.value)          # L1
    scope = scopeService.rebuildAffected(hash, tx)                         # L2 增量
    for (entity, pointer, stringValue) in changedStringFields(tx):
        for tok in lexExpressions(stringValue):
            sym = scope.resolveAt(entity.id, tok.raw)
            if not sym:               diags += error('NOT_IN_SCOPE', tok.range)
            elif typeMismatch(sym):   diags += warning('TYPE_MISMATCH', tok.range)
    diags += graphAnalyzer.run(graph, dirtySubgraph(tx))                   # L3 子图增量
    diagnosticBus.publish(rank(diags))   # error 优先、拓扑序，LSP 形
```

前后端权威分工：浏览器 L1/L2/L3 全开（体验）；**发布 CI** 用同版本规则制品在服务端重跑，error 级阻断版本发布。双形态补充：若同一系统允许 **workflow-as-code**（开发者用 TS/Python 写流程），L3 不变、承载换成编译器静态分析（ts-morph/语言服务器），画布渲染只读——绿地版不必押注单一编辑形态。

## 1.6 性能优化方案

| 手段 | 绿地做法 |
|---|---|
| 增量校验 | 事务级 dirty subgraph；L1 仅变更实体；L2 经 reverseDeps 失效引用方；L3 增量图算法 |
| 分层调度 | L1 同步；L2 Monaco 内置防抖（~80ms）；L3 全部下沉 Web Worker，worker 内常驻索引，主线程零计算 |
| 编译缓存 | AJV standalone 按 `$id@version` 编译为 JS 函数，Schema Service 下发缓存；版本不变零编译 |
| 渲染性能 | rjsf 字段级 memo；超大数组用虚拟表格控件（react-window）；React Flow 对视口外节点虚拟化 |
| 补全检索 | 符号前缀索引（trie）+ 类型过滤；万级符号亚毫秒 |
| 大图降级 | >1000 节点：L3 转保存/CI 时全量，编辑期只算 dirty 子图；画布按子图折叠（subgraph 作为一等折叠单元） |
| 协作（可选） | 多用户编辑时 CRDT（Yjs）承载图状态，诊断按作者光标过滤——上线系统才需要，Demo 形态不必 |

# 题二：多智能体协同 + 部署 + 交互模板端到端（绿地版）

## 2.1 总体架构

绿地版最根本的分叉：**主协调者不是自研图引擎，而是 durable execution 平台（Temporal 为代表）**；流程开发者仍可得到题一的可视化产物——画布发布的图编译为**版本化 workflow 定义**，由 Temporal worker 承载执行。LLM 不掌握控制流写入权这一原则不变。

```
┌──────────────────────── 入站与边缘 ────────────────────────┐
│ API Gateway(Kong/APISIX): Webhook / IM 事件回调 / Web SDK  │
│   鉴权·租户解析·签名校验·限流  → TriggerEvent{tenant,channel,payload}
└──────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────── 设计态（题一产物的发布通道）────────────────┐
│ NL 服务(解析/retrieve-rank/plan) → 人审 UI → 编译服务      │
│   → 不可变 Workflow 制品注册（版本 + 规则制品 + 卡片模板） │
└──────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────── 运行时控制平面（Temporal）─────────────────┐
│ RefundWorkflow vN（确定性代码：分支/并行/等待/审批挂起）     │
│   ├─ Activities（自动重试/超时/幂等策略声明式配置）          │
│   ├─ signal: approval_decision（人/系统决策续跑）           │
│   └─ versioning: 每版本独立 Task Queue，worker 按版本部署   │
│        │ task queue: bot.customer      │ bot.logistics      │
│        ▼                               ▼                   │
│  CustomerService Bot (独立服务)     Logistics Bot (独立服务)│
│  (LLM + guardrail + 适配器)         (LLM + guardrail + 适配器)│
│        └──────────── 共同依赖 ────────────┘                │
│  Adapter 服务(shop/payment/http/db) · Secrets(KMS/Vault)    │
│  MQ(NATS JetStream/Kafka): 领域事件/异步通知（非主控制流）   │
└──────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────── 交互与渠道 ────────────────────────────────┐
│ Approval Service（卡片模板渲染/决策回调/首决幂等/动态审批人）│
│ Web 卡片(SDK) · Slack/Teams/钉钉交互组件 · Email(SES 类)    │
└──────────────────────────┬─────────────────────────────────┘
                             ▼
┌──────────────── 发布与可观测 ──────────────────────────────┐
│ Rollout Controller（租户/业务桶/哈希分桶→版本路由）          │
│ OTel trace → Tempo/Jaeger；Prometheus→Grafana 告警；         │
│ 业务指标(退款金额差异率等) → 门控自动回滚；录制/影子回放门禁 │
└────────────────────────────────────────────────────────────┘
```

关键架构事实（相对 Atlas 版的变化与不变）：

1. **wait / 审批挂起 / 重试 / 超时 / 重启恢复全部是平台原生能力**：Temporal 的 timer、signal、activity retry policy、event sourcing 承载，不存在「自研中断-恢复」这一最长前置；进程崩溃后 workflow 自动从最后事件续跑，在途状态不丢。
2. **pin-to-version 原生**：Temporal Worker Versioning（按版本 Task Queue 部署 worker）保证已启动的 workflow 由其启动版本代码跑完，回滚只切新流量——题面灰度/回滚最难的在途语义由平台保证。
3. **Bot 是独立服务**：workflow 通过 task queue 派发（类型化 task，承载题面的任务信封语义），Bot 服务独立伸缩、独立发布、可用任意语言实现；LLM 调用封装在 Bot 内部，对 workflow 而言 Bot 是一个带 SLA 和重试策略的 Activity。
4. **护栏节点**仍保留：Bot 输出结构化「意图+置信度+证据引用」，低置信或 schema 不符 → 确定性分支升级；金融写动作只允许 Adapter 服务执行（ capability token + financial scope），LLM 不直达资金通道。
5. **MQ 不承载主控制流**：NATS/Kafka 用于领域事件、通知、异步对账；控制流（谁等谁、失败怎么办）留在 Temporal，避免事件驱动架构下时序不可推理。

## 2.2 关键流程

**(a) NL → 可运行 workflow（六步，与 Atlas 版同构、承载升级）**：

1. **解析**：NL 服务抽意图/实体（结构化输出受 output schema 约束，函数调用式 API）；
2. **技能推荐（retrieve/rank）**：技能/工具注册中心是带元数据的服务，候选召回走**向量检索 + 标签过滤 + 历史成功率/故障率业务排序**（特征：业务域、租户白名单、权限、平均时延、近 30 天失败率），不是固定兜底；
3. **规划（自动组合）**：planner 产出受限 IR（节点+边+绑定的声明式 JSON），工具 id 必须存在于注册中心（编译服务校验），控制流模板从受控集合选取，禁止自造控制结构；
4. **填充**：所有 `{{}}` 绑定经作用域服务校验（题一 L2），类型不符即打回 planner 修复（带诊断重填，至多 N 轮）；
5. **校验**：L1/L2/L3 全量 + 策略校验（权限、金融通道、PII），NL 草稿无豁免；
6. **人确认**：草稿进题一编辑器，人改后走编译服务 → 制品注册为不可变版本；**NL 永不直接发布**。

**(b) 退款协同（dispatch/join/escalate）**——三模式映射到 Temporal：

- **dispatch**：workflow 向 Bot task queue 发 Activity Task（即任务信封），状态 pending（调度）→ accepted（Bot 领取）→ running（心跳）→ done/failed/timeout；
- **join**：`Promise.all` 两 Bot 任务（客服核验、物流签收入库），均成功且条件「已签收」满足才进入放款审批；任一状态分支走确定性 condition；
- **escalate**：超时/低置信/规则冲突 → 发起审批 workflow 分支（Approval Service 发卡、Temporal signal 续跑），不是自由 @人；
- 「退货退款必须签收后放款」是 workflow 代码中的硬 condition，不依赖 Bot 自觉。

**(c) 审批与交互模板**：Approval Service 是独立有状态服务（卡片模板版本化存储 + 决策端点）；Web 完整卡片、IM 交互组件（Slack Block Kit/卡片消息两按钮）、邮件只读 + 签名 token 链接；决策端点幂等首决（compare-and-set 决策记录），重复提交 409；决策经 signal 回传 workflow。审批人可动态（值班表服务）、可委派、可超时默认拒绝。

**(d) 发布流**：

```
人审保存 → 编译服务(L1/L2/L3 + 策略) → 录制用例批量回放门禁(影子环境)
   → 制品注册为不可变版本(workflow 包+规则+卡片模板+子依赖全部锁版)
   → Rollout Controller 灰度(内部租户→低金额业务桶→5% 哈希分桶→观察窗→全量)
   → 业务/系统双类指标门控越阈 → 自动切回 vN-1（在途 workflow 由旧版 worker 跑完）
```

## 2.3 核心 Schema

**(a) 任务信封（类型化 Task 元数据；投递与状态由 Temporal 承载，信封承载业务语义与跨系统追踪）**：

```json

  "taskId": "01HXX-task",
  "workflowId": "refund-12345",
  "runId": "temporal-run-uuid",
  "idempotencyKey": "refund-12345|approve|v7",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "version": "refund-flow@7.1.0",
  "type": "refund.verify_order",
  "queue": "bot.customer",
  "payload": { "orderId": "12345", "amount": 128,

  "result": null, "attempt": 1

```

**(b) 审批卡片模板（双向；模板本身为版本化制品，变量绑定走题一同一作用域规则——第六类实体原则不变）**：与 Atlas 版形状一致（sections.bindings + actions.output + channels/fallback），增加模板版本与发布渠道清单的运行时字段；IM/邮件渲染降级由 Approval Service 的渠道 renderer 完成，动作回调统一进决策端点。

**(c) 部署与灰度（Rollout CRD 风格；版本路由是独立控制面）**：

**(d) Trace（OpenTelemetry 标准模型，第一天接入）**：`trace_id/span_id/parent_span_id` 贯穿 gateway → workflow（workflow/activity span）→ Bot（跨进程 context propagation，W3C traceparent）→ adapter；flow 版本作为 resource attribute `atlas.flow.version`；业务属性（orderId/金额桶）挂 span attribute。无需自定义超集事件协议。

## 2.4 冲突解决策略（三层分开）

原则与 Atlas 版一致，承载全部升级为生产设施：

| 层 | 场景 | 绿地策略 |
|---|---|---|
| L1 投递冲突 | 重试致任务执行两次 | Activity 幂等键（`资源|动作|版本`）落**幂等记录表**（唯一约束），重复请求直接返回首结果；MQ 侧 ack-at-least-once + 消费端去重；Temporal 自身保证 workflow 内步骤「effectively once」 |
| L2 写入冲突 | 两 Bot 并发改同一退款单 | 业务资源带 `version`，数据库乐观锁（`UPDATE ... WHERE version=n`）/ 或条件键（CAS）；失败方重读，已终态即放弃；资金动作经单一只写服务 + capability token（financial scope）+ 双账核对 |
| L3 决策冲突 | 客服可退、物流未签收 | 硬 condition 写死（未签收禁放款）；规则未覆盖**不做 Agent 投票**——升级人工审批，双方结论作为卡片证据字段；合规留痕 |

超时三级：任务 SLA（scheduleToClose + 心跳，失活 Bot 被快速重排）→ Activity 重试策略（指数退避，幂等键不变）→ 审批 timeoutSeconds 默认拒绝；终态 fail-safe（workflow 不挂死，下游按 status 分支）。与 Atlas 版同属通用机制，差异只是 Temporal/消息设施让它无需自建。

## 2.5 灰度与回滚机制

1. **不可变制品**：workflow 包（容器镜像 + 定义）、schema 规则制品、卡片模板、子流程引用全部按版本锁定注册（OCI Registry + 元数据服务）；任何编辑产生新版本，老版本不可原地修改。
2. **灰度三维度**：租户 allowlist（内部/白标客户先行）→ **业务桶**（低金额仅退款先灰；高金额/退货退款强制人工、不进早期灰度——金融硬条款）→ 百分比（订单 id 加盐哈希稳定分桶 + 粘性窗口，同一单不跳版本）。
3. **路由与在途钉版**：Rollout Controller 决定**新启动** workflow 的版本（写路由决策到事件，可审计）；已启动的由 Temporal Worker Versioning 钉死在启动版本——回滚=切路由 + 旧版本 worker 保持部署直到在途清空（drain），不需要自研 pin-to-version。
4. **门控自动回滚**：观察窗内系统指标（错误率/时延/超时率）与业务指标（退款金额差异率/自动退款率/升级率）任一越阈 → 自动路由回退 + 告警（PagerDuty 类）→ 事故版本用录制流量在影子环境跨版本重放定位（diff 报告）。**只自动回滚，放量仍手动**。
5. **回滚安全前提**：已发生的外部事实不可逆（已退款），所以门禁必须包含**业务结果指标**且灰度按业务桶先行——这一条与 Atlas 版逐字相同，是题面金融场景的通用硬约束，与选型无关。

**可观测四件套（全部托管服务化）**：

| 能力 | 绿地方案 |
|---|---|
| 链路追踪 | OpenTelemetry SDK 全服务埋点，W3C 传播，Tempo/Jaeger；workflow/activity/Bot/adapter span 父子完整 |
| 指标 | Prometheus（系统）+ 指标湖/OLAP（业务事件流 → 聚合口径：退款金额差异率等），Grafana 分面板 |
| 告警 | 分级路由（warning 站内、critical 值班轮换 + on-call），告警动作直接绑定 rollout 控制器（门控自动回滚的执行通道） |
| 回放 | 发布前：流量录制 → 影子环境批量回放 + 跨版本 diff 作为发布门禁；事故后：事件溯源重放（Temporal history 本身即可重放至任意版本代码验证修复） |

## 4. 不变的是什么（两版同一套答案的证明）

以下主张在两版中逐字一致，说明它们是题目本身的通用解而非 Atlas 产物：

1. `{{}}` 模板引用与 JSON Schema 正交，是独立横切层；作用域沿控制流拓扑推导而非全局平铺；
2. 字段/引用/图三层校验 + 结构化定位诊断 + 编辑流与权威流分离；
3. 主协调确定性化，LLM 无控制流写入权，只输出受护栏的意图与置信度；
4. 幂等返首结果 / 乐观锁 CAS / 冲突不投票而升级人工 的三层冲突策略；
5. 不可变版本 + 业务桶优先于百分比 + 哈希稳定分桶 + 在途钉版 + 业务结果指标门控自动回滚（金融硬条款）；
6. 卡片是第六类实体，bindings 走同一套作用域规则；渠道是渲染降级；
7. NL 六步中「校验无豁免、人确认才发布」。
