# 95 · 首登强制改密与口令轮换位（v1 批契约设计）

> 立项 2026-10-04。**起因不是有人提需求，是 prod 演练跑出来的**：`scripts/dev/prod_rehearsal.py` 第 4 段（docs/73 4.1／4.2 的 〔跑〕 证据）实测发现——**「首登强改密」在本仓只有流程约定，没有任何服务端强制位**。证据两条：`/api/auth/me` 的响应里没有 `must_change_password` 之类的字段；改密端点存在且能用，但**登录成功即可访问全部业务端点**，引导口令账号不改密也不会被拦。docs/73 4.1 的验收原文写着「首登强改密」，所以这一条既不是新需求也不是增强，是**已声明要求的实现**。

---

## 1. 为什么要单独一份契约（不是"顺手加个字段"）

三件看起来小的事各自会咬到别人：

1. **判定"该改密"不能靠现场比对哈希。** 最直觉的实现是"`verify_password(ATLAS_ADMIN_BOOTSTRAP_PASSWORD, stored_hash)` 为真 ⇒ 还没改"——它不需要新列，但 bcrypt 单次校验 ≈100ms，放进登录可接受、放进**每个请求**不可接受。所以要么加持久化的"轮换位"（一次写、每次读），要么接受性能税。**选列。**
2. **两档会话存储的语义必须一致。** 内存档 `SessionStore` 直接持有 `Principal` 对象；PG 档 `iam_sessions` 只存 `(tenant_id, username, role, expires_at)` 再重建 Principal（`storage/pg.py:325-360`）。标志若只塞进内存对象，PG 档的 `/api/auth/me` 就会**谎报"不需要改密"**——这正是 docs/73 §6 那类"两档不一致"的老错。故标志必须来自**用户行的读取**或**会话表也带它**；本契约选前者（少一张表要动）。
3. **强制范围是产品决定，不是工程细节。** 见 §2 D-2，需要用户拍板；本文不替他定。

## 2. 决策点

- **D-1 轮换位的载体**：`iam_users` 增列 `password_rotated_at TEXT NULL`（迁移 **042**）。`NULL` ＝ 从未轮换（引导播种态）；任何设置口令的路径（本人改密、管理员重置）都盖章。**dev／test 语义零变化**：那里没有引导口令账号，且强制只在 `ATLAS_ENV=prod` 生效。
- **D-2 强制 breadth（**待用户拍板，三档**）**：
  - (a) **只挡写操作**——`require("operate")`／`require("administer")` 拒 403，`read` 档照常。改动最小、几乎不可能锁死运维，但"看着像没改"（读得到全部业务数据）。
  - (b) **挡一切业务端点，只留 auth 与静态**（推荐）——语义最接近"强改密"：登录后除 `/api/auth/me`·`/api/auth/change-password`·`/api/auth/logout` 外的业务端点全 403；SPA 静态资源不在 `require()` 后面，所以前端能加载并弹出改密框。**代价**：一旦实现错误，运维可能把自己关在门外（因此 §4 的演练段是必需项而非锦上添花）。
  - (c) **只提示不挡**——最保守，但那是今天已经做到的事（演练证明它等于没做），不采纳。
- **D-3 旁路凭证是否同样受约束**：Bearer 通道（A2A／MCP／旧调用方）与 httpOnly Cookie 走同一 `get_principal`。本契约取**同样受约束**（旁路也一样能被引导口令滥用），并在文档里明写"给 A2A 用的服务账号若由引导口令派生，改密前不可用"。
- **D-4 演示形态（prod＋`ATLAS_ENABLE_DEMO_MOCK=1`）与演练档**：演示面开着时**不强制**（该档存在的前提就是"用仓库里的演示口令/账号"），与 `assert_prod_storage_backend()` 的三条出路同构。

## 3. 形状

- 迁移 `db/migrations/042_password_rotation.sql`：`ALTER TABLE iam_users ADD COLUMN IF NOT EXISTS password_rotated_at TEXT;`（幂等、不改冻结的 002，口径照 041）。
- `iam.users` 的账号模型增 `password_rotated_at: str | None`；`authenticate_login()` 在 prod 且该值为 `NULL` 时置 `must_change_password=True`，随 `LoginResponse.principal` 下发（**登录时读一次用户行，不引入每请求成本**）。
- 强制点落在 `iam/deps.require()` 内部（D-2 选定覆盖范围后决定挡哪些 capability）——所有业务端点都经过它，`/api/auth/*` 不经过，所以**不需要路径 allowlist**（这点是它能保持小实现的关键）。
- 拒绝形状：`403` ＋ 结构化 code **`PASSWORD_CHANGE_REQUIRED`** ＋ 中文 detail「该账号仍在使用部署时下发的引导口令，请先修改密码后再使用平台」（错误码进 docs/03 索引与 `lib/runtimeError.ts` 两档文案——A-4 的教训：新码必须同时带前端文案，不然英文态露中文）。
- 前端：`apiClient` 收到该 code 时抛带 code 的错误，`UserBadge` 已有的改密弹窗（`openChange()`）被自动打开并禁止关闭直到成功；i18n 键 `users.forceChange.*` 两档齐（PARITY 守护）。

## 4. 验收（预留 U1140–U1146；先写判据再落码）

- **U1140** 迁移 042 幂等（重复应用不报错；老行 `password_rotated_at IS NULL`）。
- **U1141** prod 引导口令账号登录 ⇒ 响应 `principal.must_change_password == true`；改密成功后再登 ⇒ `false`（**同一条链覆盖"盖章"真的写进了行里**）。
- **U1142** 强制生效（按 D-2 选定的 breadth）：未改密账号打业务端点 403＋`PASSWORD_CHANGE_REQUIRED`；**判别对照**＝改密后同一端点 200。缺了对照，"永远 403"也能让前一条全绿。
- **U1143** `/api/auth/me`·`change-password`·`logout` 在未改密时**始终可达**（否则是自锁死锁）。
- **U1144** dev／test 与 prod＋演示面：`must_change_password` 恒 `false` 且业务端点行为逐字不变（非 prod 零变化的老口径）。
- **U1145** PG 档与内存档一致：同一账号在两档下 `must_change_password` 与 403/200 结果**逐键相同**（这条专门防 §1 的第 2 点）。
- **U1146** 机检：新增业务端点若绕过 `require()`（直接 `get_principal`）而又是写操作，守护点名——防止将来有人从旁路绕过这道门。
- **〔跑〕演练脚本加第 8 段**（`prod_rehearsal.py`，在出厂镜像里真跑）：引导口令首登后立刻打 `/api/graphs` 应 403，改密后应 200，然后**再登一次**确认 `must_change_password` 消失；跑完仍只删本项目卷。D-2 若选 (b)，这一段是**唯一能证明"不会把自己关在门外"的证据**，不是可选附加项。

## 5. 原子序

① 本契约立项（本文＋docs/08 立项条＋docs/00 地图行＋handoff 索引）；② 迁移 042 ＋ 账号模型/两档 store 读写；③ 登录侧标志下发；④ `require()` 强制（D-2 选定的 breadth）＋错误码＋前端弹窗与 i18n；⑤ U1140–U1146；⑥ 演练第 8 段真跑 ＋ docs/73 4.1 收口注记。

## 6. 非目标

不做密码复杂度策略变更（沿用 `iam/passwords.py` 现有策略）；不做 MFA／SSO；不改 dev 种子账号语义；不引入口令有效期轮换（"90 天必须改"是另一件事）；不动 `ATLAS_ADMIN_BOOTSTRAP_PASSWORD` 的引导机制本身（docs/66 的形态保持）。
