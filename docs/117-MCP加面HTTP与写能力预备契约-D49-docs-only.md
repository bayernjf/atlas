# D49：MCP server 加面（HTTP 远端传输 / 写能力 / 扩展）— 预备契约与 ADR 草案（docs-only）

> 号段：无新增用例（本件为预备契约，不落码）｜承接 docs/14 D49（MCP server 面 v1 之后的加面）｜2026-10-09
> 状态：⬜ **触发条件未到，本件不授权落码**；本件把三个加面方向的范围、前置与安全约束预先落成契约，真做时按 AGENTS.md 先记 docs/10 §4 ADR，再据本文落码。

## 1. v1 现状基线（加面前的事实）

ADR T33 落定、并已于 2026-10-01 落码收口（docs/91）的 MCP server 面 v1：

- **传输**：仅 **stdio**（客户端拉起本地子进程，入口 `python -m atlas.mcp`），无网络监听面；
- **工具面**：**只读/plan-only**，7 个工具——`atlas_list_graphs`/`atlas_get_graph`/`atlas_list_templates`/`atlas_get_template`/`atlas_list_runs`/`atlas_list_interruptions`/`atlas_list_adapters`（`mcp/tools.py`）；
- **租户绑定**：进程经 env `ATLAS_MCP_TENANT_ID` 绑定**唯一租户**，工具不带 `tenant_id` 入参 ⇒ 结构上无跨租户读取面；
- **零模型调用、零副作用**：不起 run、不改图、不裁决审批。

T33 当时**明确未选**的面即 D49：②Streamable HTTP 远端传输、③含副作用工具、resources/prompts 与 MCP 扩展（①自研最小子集已弃）。

## 2. 加面方向一：Streamable HTTP 远端传输

### 2.1 范围

- 在 stdio 之外增加 **Streamable HTTP** 传输（官方 SDK v2 提供的 HTTP 承载），形状收敛为**单 POST 端点、无协议级会话、不提供 GET 流**（与 v1 无状态化取向一致）；
- 让远端第三方 MCP 客户端无需本地拉起进程即可经网络调用只读工具面。

### 2.2 安全约束（硬要求）

- **`Origin` 校验 MUST**：拒绝非白名单 Origin，防跨站调用；
- **鉴权 SHOULD（实际作为上线准入）**：HTTP 面不再适用 v1 的 env 单租户绑定，必须改为 **Bearer 令牌 → principal → 租户分区**，口径同 A2A（T32）与平台 REST（docs/80）：
  - 每次请求从 Bearer 解析身份与租户，工具视图按该租户装配；
  - **结构上仍不允许跨租户读取**——不得保留一个 env 绑定的全局租户作为 HTTP 面默认值；
- 传输层（POST 端点、帧、无会话）由官方 SDK 承担，Atlas 只守鉴权中间件、租户解析与工具面装配，不自造协议。

### 2.3 前置

- 真实「远端第三方 MCP 客户端」接入需求（触发条件）；
- ADR 记录 HTTP 传输选型、Origin 白名单管理口径、Bearer 集成方式。

## 3. 加面方向二：含副作用工具（写能力）

### 3.1 范围

- 在只读工具之外，**逐步**暴露产生副作用的工具：跑图（起 run）、退款、发消息等；
- 每类写工具锚定既有平台操作端点的同一服务层，不另起一套绕过治理的写路径。

### 3.2 安全约束（硬要求）

- **不绕单副本三道闸**（docs/62）：写工具若涉及挂起帧认领/一次性动作，必须走与平台一致的认领、互斥与审批口径；
- **人工 Gate/审批对齐**：退款等 FINANCIAL 动作、需人工审批的动作，在 MCP 面同样受审批流与权限位约束，不得因「外部 agent 调用」而降级为自动执行；
- **权限位映射**：写工具调用需携带并校验与 REST 一致的能力位（operate/administer），外部主体的 RBAC 不高于同等平台用户；
- 建议按风险增量开放：先「起 run（可影子/可挂起）」，再「消息类」，最后「资金类」，每档独立立项与 ADR。

### 3.3 前置

- 只读工具面被证明不够用、确有经 MCP 暴露写能力的真实需求（触发条件）；
- 人工 Gate 与审批口径已明确可在 MCP 面复用；ADR 记录写工具范围、权限与风险分级。

## 4. 加面方向三：resources / prompts 与 MCP 扩展

- **resources / prompts**：如外部客户端需要 Atlas 暴露只读资源（图/模板原文）或提示模板，可按官方 SDK 的 resources/prompts 面增量添加；同样受租户分区与只读约束。
- **MCP 扩展**：按需评估 **Tasks、MRTR elicitation** 一类扩展；
- **不实现已被官方弃用**的 `sampling` / `roots` / `logging`（SEP-2577）；
- ①「自研最小 MCP 子集」**已在 T33 弃用**（选官方 SDK 以规避自担协议 revision 跟踪），不再作为方向。

## 5. 推荐加面顺序与 ADR 待拍分叉

**推荐顺序：**

1. 先 **②HTTP 远端传输（仅挂载现有只读工具面）**——不引入新副作用，风险最小，先解决「远端可达 + 多租户鉴权」；
2. 再按需评估 **resources/prompts**（只读扩展，低风险）；
3. 最后按风险分级、逐档开放 **③写能力工具**（起 run → 消息 → 资金），每档对齐人工 Gate。

**真做时 ADR 需拍的分叉（本草案不代拍）：**

- HTTP 面 Bearer 集成：复用平台既有令牌体系，还是为 MCP 单设凭据/受众（audience）；
- Origin 白名单的配置与下发方式（env/配置中心）；
- 写能力是否在同一 MCP 端点暴露，还是按风险拆分面/凭据；
- 各加面是否需要独立的速率限制与审计落点。

## 6. 重开判据

满足其一即应据本件起 ADR 并落码：

- 出现**远端第三方 MCP 客户端**的真实接入需求（→ 方向一 HTTP）；
- 只读工具面被证明不够、确需经 MCP 暴露**写能力**（→ 方向三，且先对齐人工 Gate）；
- 官方 SDK 的协议 revision 或某扩展（Tasks/elicitation/resources）成为真实接入的必需（→ 方向三扩展）。

## 7. 结论与收口

- D49 三个加面方向的**范围、前置与安全约束**已预先契约化；**触发条件当前均未满足，本件不写实现、不引额外依赖、不造假集成**。
- 真做顺序建议＝HTTP（只读）→ resources/prompts → 写能力分级开放；每个方向独立记 ADR、独立原子落码。
