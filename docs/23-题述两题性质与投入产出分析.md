## 1. M5 为什么是题二绕不开的工程硬前置

题一（M1–M4）是纯前端编辑态内核，进程内状态完全够用；题二六项能力全部假设「流程比进程活得久」：

- **B3（任务超时/在途状态）、B4（审批挂起/异步回调）**：现状 `wait` 是同步 `sleep`（1–600 整数秒）、`human_approval` 是 `threading.Event` + 内存 token（10–3600s，T13/D19/D20 口径）——进程重启则所有挂起中的审批与等待永久丢失、token 成死信。跨天审批、等待物流签收是题二主路径而非边角。
- **M7 任务总线**：Envelope 状态机（pending→accepted→running→done/failed/timeout）、幂等返首结果、CAS 乐观锁，没有持久化则「幂等」只在进程活着时成立；D31 触发条件字面即写「先于它需要 11 S1」。
- **M9 灰度回滚**：在途实例 pin-to-version，恢复后要读老版本图——运行记录必须先能存活。
- **M6 版本化是唯一例外**：不可变语义不依赖 PG，只要 M5a（Repository 接口）即可插队开工。

路线排序因此固定为：**M5a → M6（可插队）→ M5b → M7 → M9**（见 20 §1.3、§3）。

### 1.1 「契约设计」缺的是什么（为什么不能照 20 §3 直接落码）

20 §3 明确 M5 只有方向、没有契约，四个缺口：

1. **Repository 接口形状**：八个进程内 store（GraphStore / RecordingStore / FeedbackStore / iam SessionStore / ApprovalBroker / DebuggerBroker / MonitoringStore / TenantRegistry）各有独立 API，需先定统一抽象，进程内实现保留为默认/测试后端，否则 PG 实现是八套各写各的 SQL。
2. **中断状态怎么落库**：LangGraph checkpointer vs 等价自研暂停态序列化二选一，属新选型，必须先在 10 文档 §4 记 ADR（T18 候选；T17 已用于 M3 表单引擎 ADR）；暂停帧序列化内容（现状是线程内 state + Event，不能直接上线）、恢复后轮询/信号机制均待定。
3. **04 §5.5/§5.6 v2 持久化语义**：现有 v1 blockquote 只定义进程内语义；v2 要回答重启后超时计时口径（墙上时钟 vs 运行时长）、决策信号如何跨进程送达、SSE 断线后重连查挂起态的语义。
4. **12 REST 新端点**：挂起运行查询/断线重连的签名、租户 404 口径、与现有 approval/debug token 的关系。

受牵连的同步面：03 graph/debug/identity 三契约加持久化注记；`/api/demo/reset` 分层（进程内后端照旧 / PG 后端 truncate 种子表，录制/反馈保留规则沿用 iam v1 先例）；13 新增中断恢复测试组（序列化暂停态→模拟新进程→恢复）；09 新恢复模块包位；11 S1 表结构回填；14 D19/D20 标注。

### 1.2 M5a / M5b 拆分

- **M5a**：Repository 抽象 + 进程内零行为变化，纯重构；现有进程内实现收到接口后面成为「内存后端」，410+ 后端测试零回归验收；无外部依赖、无新 ADR（接口形状写进 03/09）。
- **M5b**：PG 实现 + 中断落库；复用 `memory/` 已验证的 psycopg 连接层（11 S1 方案，无 pgvector 需求的表不建向量列）；需本地 Docker PG（`atlas-pg` 先例与 integration 标记机制）；验收＝integration 标记下真实 PG 全绿 + 浏览器实测「审批挂起→重启服务→同 token 决策生效、wait 事件等待恢复」。
- **边界（不做）**：真实多实例部署、NATS（D5）、Go 网关（D6）——M5 只让「单实例重启后流程能恢复」成立。

登记位置：08「M5 契约设计待办登记（2026-09-16，未开工未立项）」+ handoff Active work 11。启动时点＝题一主线闭合（或 M8 插队结束）、M6 开工之前；**M5a/M5b 立项前必须先完成契约设计轮**。

## 2. 两题对 Atlas 的性质：重构还是增强

总判断：都不是推倒重来，也不是单纯加功能。**题一＝内部重构打底、增强收尾；题二＝增强为主，但每个增强前面挂着一段重构。** 全部里程碑的共同姿态是演进式：进程内沙盘形态始终保留为默认/测试后端，重型件（PG 等）叠加而非替换，每期 410+ 测试零回归。

### 2.1 题一逐期定性

| 里程碑 | 性质 | 依据 |
|---|---|---|
| M0（已落） | 重构 + 增强 | `variables.ts` 全局平铺 → `lib/scope.ts` 拓扑 ScopeIndex（重构）；L2 引用三错误码实时校验（新能力） |
| M1 | **纯重构** | 九份 schema 是已验证硬编码规则的声明式投影，「提取不重设计」，零 UI 变化，手写校验 dev 双跑保留 |
| M2 | 重构 + 增强 | 手写校验 → schema 派生（重构）；结构化诊断（nodeId+JSONPointer+token range）是现有手写校验给不出的新能力 |
| M3 | **渐进重写** | WidgetRegistry/FormRenderer 上线，九份手写 Config 组件被生成表单逐个替换；等价迁移、迁一个删一个、禁止长期双轨 |
| M4 | 增强 | UISchema 条件显示、增量调度/Web Worker、Problems 面板均为净新增 |

题一不改运行时：图跑起来什么样，做完完全一样（M0–M3 均要求零视觉差异）。重构对象的现状体量（2026-09-16 实测）：`nodeCatalog.ts` 327 行、两个覆盖九类节点的 switch（默认值 + validate）；`propertyPanel/` 下九份手写 Config 组件（Condition/Loop/Parallel/Wait/HumanApproval/Subgraph/ToolCall 等）；`scope.ts` 400 行。

### 2.2 题二逐期定性

| 里程碑 | 重构部分 | 增强部分 |
|---|---|---|
| M5a | 八个进程内 store 收到统一 Repository 接口后，纯重构零行为变化 | — |
| M5b | — | PG 持久化 + 中断-恢复，净新增运行时能力 |
| M6 | 运行时从「graphId 解析 latest」改为「graphId@版本」、在途 pin-to-version | 不可变发布、模板/子图引用递归冻结（D21 钉版部分） |
| M7 | `skills/` 空包首次启用、parallel all_completed 网关被复用承载 join | 任务信封/coordination 总线、dispatch/join/escalate、幂等/CAS、超时三级链 |
| M8 | human_approval 的 summary 字符串升级为卡片 Schema | 交互模板系统（第六类实体验证 D29 内核），进程内渠道降级 |
| M9 | monitoring 从「只展示」变为「能驱动动作」（告警→Router 切回） | Router 灰度、金融业务桶、业务指标门控、自动回滚；D26 批量回放同批 |
| M10 | — | span 模型（traceId/spanId/parentSpanId），不引 OTel SDK |

题二六块能力在现代码库基本无对应物，性质上是增强；M5a 的 Repository 抽象是唯一纯重构前菜。绿地对照系见 22：若从零设计会选 Temporal/rjsf/独立服务/NATS，留在 Atlas 里只能走「声明式化 + 接口后收窄实现」的渐进路线——这正是 22 不构成本仓落码依据的原因。

### 2.3 两题各自的核心意图（到底在解决什么问题）

性质（重构/增强）回答的是「对现有代码做什么动作」，意图回答的是「为什么会有这道题」——两题合起来对应 AI 应用落地的两个阶段断层。

**题一的意图：把「搭一个自动化流程」从写代码变成填配置——让编排能力平台化、让非工程师可安全操作。**

- 现状（W10 沙盘形态）：九类节点能用，但每加一类节点、每加一种可配置实体，都要工程师在前后端手写一整套（规则、校验、表单、文档）。流程的定义事实上**锁死在代码里**，只有读得懂 React/Python 的人能改。
- 题一要把这个形态翻过来：流程定义是**数据**（声明式 Schema），编辑器是解释这份数据的**平台**——Schema 描述有什么、UI 自动生成怎么填、三层校验保证填得对、拓扑索引保证引用存在。其终局是：运营/实施人员面对表单就能搭出合法流程，工程师只在「出现新类型」时才介入，且介入方式是加一份声明而非开一条新管线。
- 题面列的异构实体（节点/工具/技能/记忆/部署/交互模板六类）是这个意图的关键注脚：题一不是为九个节点做美化，而是证明**同一套内核承载六类形态各异的配置对象**——这正是 D29「Schema 驱动配置内核通用化」与题二 M8 卡片（第六类实体）的底座。M0–M4 的递进（作用域索引→Schema 提取→校验器→表单渲染→条件显示）就是「平台化」从地基到外墙的施工序。
- 一句话：**题一解决「谁能造流程、造流程多贵、造错了能不能在运行前发现」**——面向的是建设阶段（build time）的效率与正确性。

**题二的意图：让多个专业化 Bot 像一个组织那样协同完成真实业务，并能长期运行、安全迭代——回答「演示能跑」到「生产能活」的距离。**

- 现状：单个图、单进程内、一次运行、重启清空。它能演示「一笔退款自动走完」，但回答不了真实业务的任何一个长期问题：流程跑了三天等签收，服务重启怎么办（M5）；改了流程，在途的几十笔单子按哪版跑（M6）；客服 Bot 自己定不了的事怎么交给物流 Bot 和人工（M7）；审批怎么出现在人真正干活的 IM/邮件里（M8）；新策略出问题怎么只放一小部分流量、怎么自动撤回（M9）；一笔跨三个 Bot 的订单出了问题按什么线索追查（M10）。
- 题二把多智能体系统从「单个智能体执行任务」提升为「**一个有分工、有协作、有治理的自动化组织**」：确定性 Graph 是制度（LLM 无控制流写入权），任务总线是部门间的工单与签收（dispatch/join/escalate、幂等、冲突仲裁），版本灰度与回滚是变更管理，span 追踪是审计。人机协作（B4）专门保证「人在这个组织里有否决权和兜底位」。
- 金融场景（退款）是刻意选的压测靶场：重复放款、大额误放、跨天等待在演示里不存在，在生产里是事故。题二的每个机制几乎都能对到一条金融级要求——幂等/CAS 对重复放款、业务桶硬灰度对大额资金、自动回滚对指标越阈、中断恢复对长周期交易。
- 一句话：**题二解决「流程能不能跨重启、跨版本、跨 Bot、跨渠道持续正确地运行，出了问题能不能发现和撤回」**——面向的是运行阶段（run time）的可靠与可治理。

**两题的接续关系**：题一让流程「**建得对、建得便宜**」，题二让流程「**跑得久、改得安全、查得清楚**」；题一的声明式底座是题二第六类实体（卡片）与未来技能/适配器配置的承载前提，题二的持久化/版本化又反过来把题一产出的配置从「编辑器里的草稿」变成「有生命周期、有发布版本的生产制品」。没有题一，题二的每个新实体都退回手写；没有题二，题一造出来的流程只能活在演示进程里。

## 3. 题一（重构为主）的意义与优缺点

### 3.1 意义（收益）

1. **消灭「同一事实的多份手抄」**：一个字段的知识（如 `timeoutSeconds` 10–3600、默认 reject、双 target）现状散落在 nodeCatalog 默认值 switch、validate switch、手写 Config 组件、后端 dsl.py/04 文档至少四处，无编译级同步保障。M1 后 schema 是唯一事实源；M3 后连表单 UI 都从它派生。
2. **加节点/加实体的成本从「写一整套」变「填一份表」**：现状新增第 10 类节点要改默认值分支 + 校验分支 + 一份 Config.tsx + 面板接线；M4 完成态是写一份 schema（+ 可选自定义 widget）。M8 交互卡片是第六类实体，无此内核则卡片配置表单要再手抄一套；手写 switch 在「实体种类 × 字段数」乘法下必然失控——这是题一作为题二前置的根本原因。
3. **横切能力一次写、全实体覆盖**：现状校验只能报对错、定位靠人读；结构化诊断（JSONPointer+token range）、条件显示、嵌套/数组字段在九份手写组件里要各写一遍，声明式后是内核层一次性能力。
4. **前后端契约从文档约定升级为可机器核对**：M1 要求 `x-outputSchema` 与 `lib/scope.ts` 投影逐字段一致（U35 固化为测试），直接防 03 契约漂移；U36 双跑等价是自动门禁。
5. **NL 生成与题二拿到可消费的配置描述**：M0 已让后端工具 Capability 带 schema（NL 参数校验）；M1 后节点同样声明式化，「给 AI / 给表单 / 给校验」读同一份东西。

### 3.2 缺点（代价）

1. **零用户可见价值**：M1–M3 界面零像素变化，四个里程碑全是内部结构投入；若项目在题二前停止，投资无回报。
2. **双跑期复杂度税**：手写校验与 schema 派生逐例双跑（U36），两套逻辑短期并存、分歧要逐个裁决；立项已写「迁完一个删一个、禁止长期双轨」防烂尾。
3. **抽象做错的代价比不抽象高**：四个 `x-*` keyword 是本仓自创、无外部生态背书；M3/M4 若发现表达不了某类控件，要么扭曲 schema 迁就 UI，要么返工内核。T16 推迟到 M1 后「携九节点实际复杂度再决策」就是承认对真实复杂度没底。
4. **间接层上升、排错路径变长**：字段为何报错/如何渲染要经 schema → 注册表 → 派生校验/FormRenderer 三层，比直接读 Config.tsx 里的 `if` 绕；对实体种类长期只有九类节点的小项目可能是过度工程。
5. **迁移窗口回归风险**：九份手写表单逐个换生成表单时，U36 只保校验等价、保不了交互等价（布局、校验时机、文案），只能靠浏览器冒烟硬扛。

### 3.3 权衡结论

值不值取决于一个判断：**题二做不做、实体种类会不会增长**。做题二（M8 卡片、M7 技能实体、D22/D23 的 Schema 驱动参数表单都是明确触发条件）则题一是必须先还的债，且趁实体仅九类、规则仅 327 行时还成本最低；停在九节点沙盘演示形态则题一是赔本重构——327 行 switch 对当前规模没有实际故障。M1–M4 渐进拆分、每期零回归门禁、M1 先纯提取不加能力，是给「判断错了」留的止损结构。

## 4. 题二（增强为主）的优缺点

### 4.1 优点

1. **直接对应业务硬要求，逐期可翻译成业务语言**：M5＝服务重启不丢跨天流程；M6＝改流程不影响在途单；M7＝客服/物流 Bot 协同、超时升级人工、钱不重复退；M8＝审批在 IM/邮件一键决策；M9＝大额退款硬走稳定版 + 差异率越阈自动回滚；M10＝一笔订单跨 Bot 调用链可追溯。
2. **兑现早已登记的债务，而非发明需求**：M5→D19/D20、M6→D32/D21、M7→D31、M8→D33、M9→D26、M10→D34，均为 14 文档标注「v1 进程内简化、未来补」的集中收口。
3. **叠加而非替换，轻量开发体验不丢**：进程内实现保留为默认/测试后端，410+ 测试不依赖 PG 即可跑，Demo 启动仍零外部依赖；沙盘 Bot、进程内 Router 与 iam 进程内分区同策略。
4. **金融安全条款在本期闭合**：M9 业务桶（金额硬条件）+ 业务指标门控（退款金额差异率/自动退款率/升级率）+ 告警驱动回滚；M7 冲突三层（幂等键 + CAS + condition/审批，不做 Agent 投票）——正面回答 LLM 编排上生产最被质疑的两点。
5. **每期可演示、验收无歧义**：与题一零像素变化相反，题二每期有端到端剧本（挂起→杀进程→重启→同 token 决策；发布 v2→在途单仍跑 v1；dispatch→未签收拦截放款→escalate）。

### 4.2 缺点

1. **M5 是最长关键路径且纯投入开局**：20 §6 自列第一风险——存储抽象 + 中断恢复牵动八个进程内包与 SSE 语义；M5a 零行为变化、M5b 还要 Docker PG/integration/选型 ADR，题二开局先吃最难的硬工程。
2. **首次引入有状态系统的永久复杂度**：重启即清空本身是简单（无迁移、无脏数据、无版本兼容）；M5b 后要永久背负 DDL/迁移、暂停态序列化前后向兼容、停机期间超时口径、reset 分层。
3. **沙盘验证与真实能力有无法自证的鸿沟**：M7 假物流 Bot 明确「不解除 D31」、M8 渠道进程内降级「不解除 D33」、M9 无 NATS/多实例验不了真分布式灰度、M10 不引 OTel SDK。题二交付的是**语义正确、结构就位**，不是生产可用；中间隔着 D5/D6/D10b 一整批，汇报时须防止「结构验证」被误读为「生产就绪」。
4. **新抽象面积比题一大**：versioning/、coordination/（Envelope/TaskStore/状态机）、卡片 Schema、Router、span 模型五个新子系统，每个配 03/04/05/06/12/13 全套契约同步；M7 概念密度最高（信封/幂等返首/CAS/超时三级），且建立在「join 复用 parallel 网关」的简化前提上，D30 动态键语义若变可能回头返工。
5. **依赖链刚性、插队空间小**：M7/M9 等 M5b+M6，M9 还绑 D26 与 monitoring「展示→驱动」改造，M10 等 M7；中途断档比题一更难留尾——抽了一半的 Repository 比手写节点面板更难搁置。
6. **金融回滚逻辑的验证可信度上限**：阈值/观察窗/业务指标口径在沙盘只能用种子数据走通结构，证明不了真实分布下不误回滚（切掉好版本）、不漏回滚（指标没采到）；正确性最终靠真实流量，沙盘给结构信心而非安全保证。

## 5. 一页总结

- **题一回答「配置内核配不配当平台」**：不做，则卡片/技能/未来适配器表单重复造轮子；性质是重构，收益在边际成本与横切能力，代价是多期零可见产出与抽象风险，止损靠 M1–M4 渐进与零回归门禁。
- **题二回答「系统能不能离开演示环境」**：不做，Atlas 永远是 W10 验收形态的沙盘；性质是增强，每期有业务可演示能力，真实成本藏在 M5 开局与「沙盘≠生产」的差距里，防线是 M5 契约先行（08 待办登记）与所有沙盘项「不解除 D 条触发」的标注。
- 两题共享同一底层姿态：**不推翻、演进式、叠加不替换、进程内形态永生为测试后端**。
