## 3. MVP 判定（两层）

### A. 可演示 / 可陪同试用的 MVP —— ✅ 达到
单实例 + demo/mock 数据 +（可选）真实 LLM key 下，编排→执行→审批→监控 全链路可跑通、可演示、可由实施人员陪同客户试用。即 docs/63 原判定里的「达到」那一档。

### B. 产品核心完全可用的生产 MVP（自主上线）—— ❌ 未达到
docs/63 原判"核心闭环面（接真实店铺＋真实 LLM＋真实定时，并在 prod 里被运维登进去）不可用"依赖的 N1/N2/N4 **代码侧已闭合**，但「自主上线」仍卡在以下（按性质分）：

1. **真实外部集成凭据 / 部署面（非代码缺陷）**
   - 出厂 `docker-compose.yml` 仍默认 `LITELLM_MODEL: ${LITELLM_MODEL:-}` ⇒ 空 ⇒ 起的是**无 LLM 决策的编排壳**。代码已支持真实 LLM（打包 J P0-2 改为启动打印当前决策器与降级状态，不再静默），但**真实部署必须显式配置商业 LLM key**，否则「AI 运营体」退化成规则壳。
   - 真实店铺退款（N2）只"假在 HTTP 传输层"，真 Shopify 返回 200 需真实店铺凭据；IM/SMTP/短信/OAuth 同理，全属 docs/08 **D 组外部资源**。
   - ⇒ 没有真实 LLM + 真实通道，「AI 运营体」这个**产品核心**在自主上线时是失能的。这是与「demo MVP」最大的落差。〔码〕

2. **N3 产品范围表态（仍开）**：PRD 承诺的浏览器自动化适配器是否进 MVP，是产品决策，不是工程问题；若目标场景需要，则核心闭环仍缺一块。〔码〕

3. **prod 形态持久化 / 单实例 HA**：调度 store 仍进程内（重启丢认领历史）；单实例硬约束未撤（docs/62 L1/L2），多副本仍禁止；at-most-once 续跑的代价是 D36「卡住帧 reconcile 批」未立项——生产崩溃会留 orphan suspended run，需人工重放。〔码〕

4. **真实 prod 演练 / 种子客户试用数据 = 0**：docs/18 那句「假定 Go（沙盘假设，非实测）」仍在；这条代码修不了。〔码〕

## 4. 自主上线 MVP 还差什么（按依赖 / 性质排序）

- **必配部署项（解除 S1–S8 后真正的上线前提）**：真实 `LITELLM_MODEL` + 商业 API key；真实 Shopify/IM/SMTP/SMS/OAuth 凭据与连接；`ATLAS_ENV=prod` 真机演练一次（seed 管理员 + 引导口令 + 首登）。
- **产品范围决策**：N3 浏览器自动化是否进 MVP（用户拍板）。
- **prod 形态持久化**：调度 store PG 化（D32 随 11 S1）；D36 reconcile 批立项（单机崩溃兜底）。
- **HA / 多副本**：当前硬禁；若要「生产级」而非「单实例 MVP」，需解锁——但单实例 MVP 本身可交付，HA 可后置。

## 5. 结论

> **达到「可演示 / 可陪同试用」的 MVP；未达到「产品核心完全可用的生产 MVP（自主上线）」。**
> 工程功能面与安全面均已就绪（S1–S8 已 remediation、N1/N2/N4 代码闭合、单实例闭环可跑）；自主上线 MVP 未达的根因不在代码，而是**真实 LLM / 通道凭据 + N3 范围表态 + 少量 prod 持久化 / HA**。若要对外称「可上线」，必须先把真实 LLM 与至少一条真实通道配通、并跑一次 `ATLAS_ENV=prod` 演练。
