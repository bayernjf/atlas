## 一、技能（Skill）

> **M7 立项注记（2026-09-17）**：本节为愿景段；M7（多 Bot 任务总线，08 M7 立项条 + ADR T20）以 docs/19 §2.1/§2.3.1 提案转权威为准——Bot＝技能声明 + 适配器集合 + 受护栏 Coordinator 节点（只输出意图+置信度，低置信升级），`skills/` 空包首次启用，进程内沙盘、不解除 D31。

### 1.1 核心概念
技能是将“多个工具调用 + AI决策 + 逻辑控制 + 提示词模板”封装为一个可复用、可版本化、可共享的黑盒能力单元。它是介于“原子工具”和“完整运营体”之间的中间层。
## 层级关系：
原子工具（点击按钮、查询API）
↓ 组合封装
技能（处理退款、发送跟进邮件、生成周报）
↓ 编排调用
运营体（电商售后机器人、IT运维助手）

## 二、记忆（Memory）配置组件

> **M11 实现边界（2026-09-19 立项，docs-only；权威＝docs/26、ADR T23）**：本节 §2.2–§2.3 的五层记忆策略（working/summary/fact/preference/case）与 memory_config 策略 Schema 为**愿景设计**。M11 仅取回最小可用长期记忆：统一 `memory_item`（kind=fact/preference 两类）、EmbeddingProvider 抽象 + 本地确定性 embedder（256 维词法/hashing、中文 unigram+bigram、纯 stdlib、离线且回放确定；商业 embedding 缓做）、`memory/remember`+`memory/recall` 两个适配器工具（零新节点/DSL）、进程内 + PG/pgvector 两档、REST 浏览/语义搜索/删除与前端记忆页。working（Redis 短期态）、summary、case、auto_extract 自动提取、决策隐式注入（§6.2）、update_policy/decay/retention、PII 脱敏、memory_config 策略表单等**全部缓做**（14 D35，触发条件见该表）。工程契约以 docs/26 为准，03 已索引 `memory_item`/`memory_remember`。

### 2.1 核心概念
之前我们设计了记忆系统的存储和检索架构。现在补充的是编辑后台中面向用户的记忆配置组件，让用户能控制运营体的记忆行为。
### 2.2 记忆配置层级
## 运营体级记忆配置
├── 全局记忆策略（默认配置）
├── 节点级记忆配置（特定节点的记忆行为）
└── 运行时记忆管理（手动干预）
## 2.3 记忆策略配置 Schema（示例）
## memory_config:
# 短期工作记忆
working_memory:
max_turns: number            # 保留最近N轮对话/操作，默认20
max_tokens: number           # Token上限，默认8000
overflow_strategy: enum[summarize, truncate, error]

# 中期摘要记忆
summary_memory:
enabled: boolean
trigger_turns: number        # 每N轮触发一次摘要
trigger_tokens: number       # 超过Token阈值触发
summary_model: string        # 用于摘要的模型
retention_days: number       # 摘要保留天数

# 长期事实记忆
fact_memory:
enabled: boolean
auto_extract: boolean        # 自动从对话中提取事实
extract_confidence_threshold: number  # 提取置信度阈值，默认0.85
update_policy: enum[overwrite, version, ask]  # 冲突时策略
retention:
decay_enabled: boolean     # 是否启用时间衰减
decay_rate: number         # 衰减速率

# 案例记忆
case_memory:
enabled: boolean
record_success: boolean      # 记录成功案例
record_failure: boolean      # 记录失败案例
record_human_correction: boolean  # 记录人工修正
similarity_threshold: number # 检索相似度阈值

# 用户偏好记忆
preference_memory:
enabled: boolean
extract_from_interactions: boolean
auto_apply: boolean          # 决策时自动应用用户偏好
sensitivity: enum[conservative, balanced, aggressive]  # 提取敏感度

# 隐私与合规
privacy:

user_deletion_support: boolean  # 支持用户删除记忆

## 三、智能体协同
### 3.1 核心概念
当业务复杂度超过单个运营体的能力时，需要多个运营体分工协作。编辑器需要提供协同编排能力，让用户像设计组织架构一样设计AI团队。
### 3.2 协同拓扑结构

| 拓扑 | 说明 | 适用场景 |
| --- | --- | --- |
| 主从模式 | 一个主协调者分配任务给多个执行者 | 售后处理（主Bot分配退款、换货、咨询） |
| 流水线模式 | 各运营体按顺序处理，前一个输出是后一个输入 | 订单处理（客服→库存→物流） |
| 黑板模式 | 所有运营体共享一个数据空间，各自读写 | 复杂的跨领域协作 |
| 对等协商 | 运营体之间直接通信，无中心协调者 | 供应链上下游协商 |
| 层级模式 | 多层级的运营体组织结构 | 大型企业多部门协作 |

## 3.3 协同通信协议（示例）

## 3.4 编辑器中的协同组件
#### 协同节点

| 节点类型 | 功能 | 输入 | 输出 |
| --- | --- | --- | --- |
| 任务分发节点 | 将任务分配给其他运营体 | 任务描述、参数、目标运营体 | 任务ID、状态 |
| 消息接收节点 | 等待其他运营体的消息 | 监听条件 | 消息内容 |
| 结果汇总节点 | 收集多个运营体的执行结果 | 多个任务ID | 汇总结果 |
| 冲突仲裁节点 | 当多个运营体意见不一致时裁决 | 冲突内容 | 仲裁结果 |
| 广播节点 | 向所有订阅者发布事件 | 事件内容 | 确认状态 |

## 3.5 协同的冲突解决机制

| 冲突类型 | 自动解决 | 人工介入 |
| --- | --- | --- |
| 结果不一致 | 置信度高的结果优先 | 无法自动裁决时 |
| 操作冲突（同时改同一数据） | 锁机制+版本号 | 业务影响大时 |
| 循环依赖 | 设置最大传递层数 | 达上限后 |
| 资源竞争 | 优先级队列 | 持续竞争时 |

## 四、部署方式
## 4.1 核心概念
运营体搭建完成后，用户需要决定它在哪里运行、如何被触发、以什么形态与最终用户交互。
### 4.2 部署方式全景

| 部署方式 | 触发方式 | 交互载体 | 适用场景 |
| --- | --- | --- | --- |
| 云端托管 | 定时、Webhook、API | 平台控制台 | 大多数自动化场景 |
| IM嵌入 | 消息触发 | 钉钉/企微/飞书机器人 | 企业内部运营 |
| 网页嵌入 | 用户点击/页面事件 | 网页浮层/侧边栏 | 产品操作指引 |
| SDK嵌入 | 代码调用 | 自定义界面 | 深度集成到客户产品 |
| 邮件触发 | 收到邮件 | 邮件回复 | 邮件处理机器人 |
| 私有化部署 | 同上 | 同上 | 金融/政务等强合规 |
| 边缘部署 | 本地事件 | 本地设备 | IoT/门店 |

## 五、自定义前端模板（含交互卡片样式）
### 5.1 核心概念
运营体与最终用户交互时（审批卡片、引导浮层、结果通知、信息收集表单），需要可定制的交互界面。这个维度让用户能定义运营体的“脸面”。
### 5.2 交互场景与卡片类型

| 交互场景 | 卡片类型 | 关键元素 |
| --- | --- | --- |
| 人工审批 | 审批卡片 | 上下文摘要、AI建议、同意/拒绝/修改按钮 |
| 信息收集 | 表单卡片 | 输入框、下拉选择、文件上传、提交按钮 |
| 结果通知 | 通知卡片 | 状态图标、结果摘要、操作按钮 |
| 引导提示 | 引导浮层 | 高亮区域、步骤说明、上一步/下一步 |
| 进度汇报 | 进度卡片 | 进度条、当前步骤、预计完成时间 |
| 多选项决策 | 选择卡片 | 多个操作选项、推荐标记 |
| 异常告警 | 告警卡片 | 错误摘要、影响范围、处理按钮 |

## 5.3 交互模板 Schema（示例）

> **M8 工程化边界（2026-09-18 立项并三批落码收口，U53/U54 转正式；权威＝08 M8 立项条+落码条 + 03 `card_template` + 04 §5.6 追加段）**：下方含 style/layout/conditional_display/channel_adaptations 的大 Schema 与 §5.4 可视化编辑器、§5.6 模板市场均为**愿景形态**（P1/P2，见文末路线表）。M8（Demo 沙盘）只取回审批卡片的**双向最小子集** `card_template`：`{id,name,channels:[web,im,email],sections:[{type:"fields",bindings:[{label,value:"{{…}}"}]}|{type:"textarea"|"input",name,label?,required?}],actions:[{id,label,style,output:{decision,comment:"{{form.comment}}"}}],fallback?}`，落码承载 `src/atlas/cards/{catalog,render}.py`（内置只读目录，v1 一张 `refund-approval`，照 template 包模式）。三渠道降级：web 完整表单（CardRenderer 经 FormRenderer 渲染 form sections，SchemaRegistry 第三类来源 `kind:"card"`）、IM 文本+两按钮回调链接、邮件只读摘要+带 token 链接；bindings 走同一 ScopeIndex/L2（可见集＝审批节点 visibleAt），actions 经现有 `/api/approvals/{token}/decision` 回写 decision/comment。**不做**：style 主题/暗色、布局拖拽编辑器、conditional_display、模板市场/CRUD/版本化、真实 IM/邮件外发（D24）、邮件 GET 决策落地页、网页嵌入 SDK；进程内三渠道渲染 + message/send 落记录为沙盘语义，**不解除 D33**。
