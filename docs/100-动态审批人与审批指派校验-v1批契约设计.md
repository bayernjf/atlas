## 2. 动态审批人

### 2.1 声明形状（human_approval config 纯超集）

`config.approver` 现状为静态文本（≤128）——**新增支持 `{{变量}}` 插值**（复用 `interpolation.interpolate` 同一接缝，与 tool_call params 同规则）：
- 运行期（`_register_approval` 处）先 `interpolate(config.approver, context)` 求值；
- **求值结果为空串** → 按现状空 approver（任何人可决）处理；
- **求值含未命中占位**（插值后仍含 `{{` 形态）→ 显式 422/运行期错误？**裁定：运行期 fail-closed 太硬（模板笔误会让审批永远挂起）——改为编译期可静态识别时校验（纯字面量 `{{var}}` 且 var 不在图变量/上下文 → 编译 422 `APPROVER_REF_UNRESOLVED`），动态引用（求值后残留）→ 按空串处理并告警日志**（审批可决不因笔误永久挂起，语义与「无指定审批人=任何人」一致）。
- **求值形态**：支持 `{{变量名}}`（图变量/运行上下文）与 `user:<id>`/邮箱字面量混合（如 `{{operator_email}}` 求值出邮箱）。

### 2.2 持久化

`approver` 展开值照旧随挂起帧/已决历史持久化（现状列已够，**零迁移**）；config 原文（含 `{{}}`）随图保存不变。

## 3. 审批指派校验（决策端点）

### 3.1 匹配语义

`POST /api/approvals/{token}/decision` 在取到 pending 后、执行决策前新增指派校验：

- `pending.approver == ""` → **任何人可决**（现状逐字不变，租户内 operate 即可）；
- `pending.approver` 非空 → 解析操作者标识并匹配：
  - `approver` 形如 `user:<id>` → 与 `principal` 的用户标识精确匹配（`principal.user_id`/登录主体，按 iam 现状取）；
  - `approver` 为邮箱形态（含 `@`）→ 与 principal 邮箱精确匹配；
  - 其他形态 → **按"无匹配者"处理**（403，不泄漏存在性差异——approver 写错时任何人不可决，运营侧以 `APPROVAL_NOT_ASSIGNED` 发现配置错误）。
- **不匹配 → 403 `APPROVAL_NOT_ASSIGNED`**（params `{token}` 不必要——detail 不带 token，统一中文 `该审批仅限指定审批人处理`）；**匹配/空 → 照旧**（decision 逻辑、状态机、通知一字不动）。

### 3.2 兼容性

- **既有行为超集**：历史上 approver 为空/从未设置模板的图——任何人可决，不受影响；已配置静态 approver 的图——从此只有该人可决（**行为收紧，属本批预期**，docs/73 无对应判据，写进 CHANGELOG）。
- **通知侧已带 approver 行**（T2）——指派校验落码后"通知告诉你是谁、端点只认谁"对齐。
- 内存档与 PG 档同语义（approver 均随 pending 保存，恢复扫描器重建后校验同样生效——**挂起帧恢复路径必须带 approver 到 pending**，现状已有（frame.py:44））。

### 3.3 错误码

新增 `APPROVAL_NOT_ASSIGNED`（403）——进 runtime.json zh/en（`该审批仅限指定审批人处理`），进 docs/03 错误码取值集合。
