# Atlas 环境划分与分支策略

> **用途**：明确环境（DEV/TEST/PROD）划分、各环境职责与**分支 → 环境映射**。参照 agent-world 惯例，按「小公司/初创 3 套」方案，避免过度设计。
> **现状**：2026-09-13 仓库初始化（private GitHub `bayernjf/atlas`），本地开发为主，尚未有部署目标。

## 一、环境方案：小公司 / 初创 3 套

| 环境 | 中文 | 用途 | 数据来源 |
|---|---|---|---|
| **DEV** | 开发环境 | 开发人员日常调试、跑测试 | 构造的假数据 |
| **TEST** | 测试环境 | 功能测试、Demo 验收（08 文档 7.3 七条标准） | 构造的假数据 |
| **PROD** | 生产环境 | 真实用户使用 | 真实数据 |

演进节奏（按商业化里程碑，依据 08 文档）：

| 阶段 | 环境套数 | 说明 |
|---|---|---|
| **M0 当前** | 1 套合一 | 本地开发机（Windows + 可选 Docker），DEV/TEST/PROD 未拆分 |
| **M1 种子客户** | 2-3 套 | 拆 TEST，或直接 DEV → PROD |
| **M3 正式上线** | 3 套 | DEV / TEST / PROD 正式拆分 |

## 二、分支 → 环境映射

| 分支 | 给谁 | 说明 |
|---|---|---|
| `main` | 正式生产 PROD | 生产稳定版，只在稳定发布时更新，**不废弃** |
| `dev` | 集成 / 准生产 | 最新集成代码，feature 通过 PR 合并到这里（当前工作分支） |
| `feature/*` | DEV 本地开发 | 功能开发分支，合并进 dev 前 |

**规则**：

1. 开发在 `feature/*` 分支进行，通过 PR 合并到 `dev`；`dev` 稳定后合并到 `main`。
2. `main` 只接受稳定发布合并，不做日常开发。
3. 当前工作分支为 `dev`（跟踪 `origin/dev`）。

## 三、当前机器与环境对照

| 机器 | 角色 | 环境 | 部署分支 |
|---|---|---|---|
| 本地开发机（Windows） | 写代码 / 调试 / 跑测试 | **DEV** | `feature/*` / `dev` |
| （暂无） | — | 正式 **PROD** | `main`（M3 上线才拆） |

## 四、单副本硬约束（2026-09-25 登记，[docs/62](62-挂起帧一次性认领-单副本硬约束护栏-v1批契约设计.md) 打包 I L1）

**Atlas 目前只能单副本运行：一个进程、一台机器。** 这不是性能取舍，是正确性约束。

- **为什么**：PG 档下审批挂起帧、事件等待、急停句柄、入站 webhook 幂等环、登录节流、灰度运行态都是**进程内**状态。
  > **本行"入站 webhook 幂等环"一项就地订正（2026-09-25 落码批，读 `channels/webhooks.py:171-183` 核过）**：入站去重在 PG 档**已跨进程**（先查 `webhook_deliveries` 表，迁移 025），仅 store 不可用/未注入时才退回进程内环——列在本行是当时未逐行读代码的推断。其余各项（挂起帧的**续跑**、事件等待路由、急停句柄、节流、灰度态）仍然成立；其中挂起帧的重复续跑已由 docs/62 L2 认领门堵住，见下一条。第二个进程启动时 `recover_pending`（`api/main.py:154`）会为**第一个进程仍持有的活帧**重建 pending 并起自己的续跑线程——人工在任一进程点"通过"后，该进程沿通过分支执行下游，另一个进程收不到跨进程 Event、等到超时走 reject 分支，**同一条 run 的副作用被执行两遍且分支相反**，run 终态再互相覆盖。实测表与机制链见 [docs/34](34-MVP上线就绪评审-2026-09-22复审.md) 的 2026-09-25 复审更新注记；可重跑证据 `scripts/dev/multi_instance_resume_recon.py`（退出码非 0 即双跑实锤）与 `scripts/dev/w2_split_brain_recon.py`。
- **三道闸**（覆盖三条互不重叠的绕过路径）：`Dockerfile` 的 CMD 显式 `--workers 1`（此前是"没写才恰好为 1"的偶然安全）；`scripts/ops/docker-entrypoint.sh` 对 `ATLAS_WORKERS>1`、命令行 `--workers N`／`--workers=N`／`-w N`（N>1）以及非整数值一律 fail-closed 退出，**且判在跑迁移之前**——宁可起不来，也不要起来双跑；`docker-compose.yml` 钉 `deploy.replicas: 1`（第二副本今天还会先因 `8000:8000` 端口冲突起不来，那是**巧合保护**，不能当设计依赖）。
- **要扩容先做什么**：[docs/62](62-挂起帧一次性认领-单副本硬约束护栏-v1批契约设计.md) §3 的**帧一次性认领已于 2026-09-25 落码**（迁移 029 ＋ 原子 `UPDATE ... WHERE resumed_at IS NULL`，at-most-once；`af38176`/`593bed0`/`df5a18c`），也就是说上面那条"一次审批下游跑两遍"已经堵死——`scripts/dev/multi_instance_resume_recon.py` 从退出码 1 翻到 0。**但单副本约束本身不解除**：剩下要逐项处理的仍是登录节流与告警限流（每进程一份）、`/metrics` 聚合（单进程快照）、灰度运行态跨实例热同步、跨进程急停句柄（D27）与审批决策跨实例正题（D20），**做完认领绝不等于支持多副本**（残余三项实测见 docs/62 §8.2 的订正注，那条注同时收回其中"webhook 幂等环"的过实措辞）。三道闸因此一道都不撤：护栏防的是"没做完剩余几项就手工多开"。
- **口径影响**：docs/14 的 D19/D20/D27/D31/D32 触发条件由"随真实部署批"重述为"**上多副本前必须先完成**"，五条均不解除；新增缓做 **D36**（认领后崩溃会造成永久挂起帧、需人工重放／reconcile）与 **D37**（前端尚未认 `superseded` 终帧，输家流会被报成「SSE 流缺少最终运行结果」）。

## 五、prod 档位启动前置（2026-09-25 登记，docs/66 打包 L）

缺省档位是 `dev`（演示与测试形态，零密钥、种子账号照播）。要把 Atlas 按 **prod 档**起来，`ATLAS_ENV=prod` 时三样缺一不可，任一缺失或不合规则**进程拒绝启动**（`security/bootstrap.py:assert_prod_secrets`，fail-closed）：

1. `ATLAS_MASTER_KEY`、`ATLAS_APPROVAL_HMAC_SECRET`：各需 ≥32 字节随机值（docs/64 J-1a）。
2. `ATLAS_ADMIN_BOOTSTRAP_PASSWORD`：**首任管理员引导口令**，须过口令策略（8–128 位、非弱口令黑名单）。prod 下播种计划只播**各租户一条 ADMIN**（`admin-a@t1`／`admin-b@t2`）并用这个口令，**不再播种仓库内明文种子口令**；operator/viewer 由首位 admin 建（docs/66 §2）。
3. 真机部署演练尚未做过：上述收紧目前只有单测与进程级 import 验证，**没有一个真实 prod 实例跑过**（docs/63 §6 前置之一）。

另注：`ATLAS_ENV` 只接受 `dev|test|prod`，写 `development`/`production` 会让进程 import 即抛（`.env.example` 曾犯此错，docs/63 §0A N5，已修并有 U867 守护）。
