> 1. **包内文件是三份不是两份**：除 §2.1 列的 `cron/engine/models`，另有 `store.py`（`ScheduleStore` 协议＋内存档）与 `pg_store.py`。理由是两档必须共用同一个认领键归一（`models.slot_key`）与同一个投影函数，否则"逐键一致"只能靠两边各写一遍再对齐。

> 4. **端点路径用 `{graph_id}` 不是 `{graphId}`**：仓库其余路径全 snake（`/api/graphs/{graph_id}`、`/api/channels/{binding_id}`），本文 §2.4 的 camel 写法是从响应字段串了位。响应体仍是 camelCase。

> 6. **事件载荷沿用 webhook 的双层嵌套**：trigger 节点产出 `context.payload = {"event": {"channel": "api", "payload": {source, slot, cron}}}`（实测形状，已写进 04 §5.21）。刻意不"顺手纠正"成单层——那会改所有既有图对 `{{...payload...}}` 的引用口径，属另一件事。
> 7. **`ATLAS_SCHEDULE_TICK_SECONDS`**（缺省 30，clamp 1–300）是本文没提的运行期开关；只有 §2.3 的 `ATLAS_SCHEDULE_ENABLED`。两者口径与"测试默认关线程"的实测成因记在 docs/15 §六。
> 8. §4 的"两档一致"落成 `tests/test_scheduling_pg_integration.py` 5 例，其中**内存档易失性按契约方向断言为"重启后同一槽仍可再派发"**——把它断成 False 才是自欺（§1 D-7 的明示差异）。

## 1. 决策（七条，落码前照此实现，任何一条要改先改本文）

- **D-1 自研最小 cron 子集，零新依赖**。标准 5 字段（分 时 日 月 周），支持 `*`、`*/n`、`a-b`、`a-b/n`、逗号列表与显式数值；**不支持** `?`、`L`、`W`、`#`、秒字段、别名（`@daily` 等）。解析失败＝**保存期 422 中文报错**（新增错误码 `NODE_TRIGGER_CRON_INVALID`），不做"看不懂就当 `*`"的兜底——静默放宽调度频率比拒绝保存危险得多。理由与先例：ADR T16（自研最小子集不引 AJV）、T17（自研表单引擎零新依赖）。
- **D-2 只有 UTC**。槽位计算、`next_fire_at`、DB 比较一律 UTC（仓库主约定已是 `now_iso()` UTC ＋ `TIMESTAMPTZ`）。**不提供命名时区**——命名时区函数库本身还在 docs/08 B 组未做，先做调度器时区会逼出一条半吊子实现。控制台必须显式标 UTC，避免运营按本地时间理解。
- **D-3 只跑已发布版本，不跑草稿**。调度记录存 `(tenant_id, graph_id, version, cron, enabled)`，`version` 在**发布时**写入（复用 `publish()` 出口），派发走 `_webhook_run_worker` 同形路径（钉版＋租户服务＋审计），永不回落到 latest 草稿。
- **D-4 注册来源＝发布派生，不是用户另填一张表**。发布含 `schedule/cron` 触发节点的版本 ⇒ upsert 一条调度（默认 enabled）；同一 `graph_id` 再发布 ⇒ 更新为**新版本与新 cron**；`enabled` 由运营者翻页控制且跨重启保留。图被删除/demo reset ⇒ 调度行随之清理。
- **D-5 每个槽位至多触发一次，靠一次性认领（照 docs/62 L2 的同一条纪律）**。`schedule_fires (schedule_id, slot_utc)` 主键 `INSERT ... ON CONFLICT DO NOTHING`，rowcount==1 才派发。含义：① 崩溃/重启**不会补跑**错过的槽（宁漏不重跑，理由与挂起帧一致——下游副作用不幂等）；② 两个进程同时跑调度器也只会触发一次（这是本批**顺带**得到的性质，不等于支持多副本，见 D-7）。启动时不追赶历史槽位。
- **D-6 同图重叠＝跳过并计数**。tick 时若该 `graph_id` 已有 `running`/`suspended` 运行（D-3 的版本无关，保守取图粒度），本次槽位**不派发**，记 `skipped` 计数与一行 info，且**不消耗**该槽位的认领（认领表只在真要派发时写）——否则一次重叠会白白吃掉一个槽位。
- **D-7 不解锁多副本**。单副本硬约束、三道闸、docs/14 D19/D20/D27/D31/D32 全部不动。调度器在 lifespan 内起一条 daemon 线程，进程内后端（内存档）用进程内认领集合，两档语义一致但**易失**（重启丢历史认领＝可能重复触发一次），这一条明文写进两档差异说明，不藏。

### 1.1 D-1 的细则（落码前定死，不留给实现自由发挥）

契约原文只写了"支持哪些语法"，下面四条是写迁移和写测试前必须钉住的语义，逐条都是 cron 生态里"两种实现都给不同答案"的地方：

1. **日与周取并集（标准 cron 规则）**：`day-of-month` 与 `day-of-week` **都受限**时按 **OR** 匹配；只有一个受限时按那一个匹配；两者都是 `*` 时每天匹配。不采用"AND"实现（部分库这么干），因为那会让 `0 9 * * 1-5` 与 `0 9 15 * *` 的合并写法静默变成"几乎永不触发"。
2. **数值别名与 `7`**：接受 `7` 等价于 `0`（周日）并**归一化**——这是合法 cron，拒绝它＝假拒绝，会让从别处抄来的表达式存不进来。月份名/星期名（`JAN`/`MON`）**不支持**（属 D-1 明写的"别名"），报中文拒绝。
3. **`a/n` 不认**（只认 `*`、`*/n`、`a`、`a-b`、`a-b/n`、逗号列表）：`5/2` 在 Vixie 与 POSIX 之间语义不一致，宁缺勿猜。区间起点大于终点（`22-2`）同样中文拒绝——wrap 语义不是所有实现都有。
4. **"永不触发"在保存期就拒**：能解析但在 **5 年**内没有任何匹配分钟的表达式（如 `0 0 30 2 *`，以及"日受限＋周受限但交集为空"以外的极端组合）⇒ 同一错误码 `NODE_TRIGGER_CRON_INVALID`、中文消息说明"未来 5 年内不会触发"。理由：这类表达式保存成功后的表现是"图永远不跑"，与 docs/63 N4 要修的真空**完全同形**，不能自己造一个新真空。

## 2. 形状

**2.1 新模块 `src/atlas/scheduling/`**

```python
cron.py      # 纯函数：parse_cron(expr) -> CronSpec；matches(spec, dt)；next_fire_utc(spec, after)
engine.py    # tick(now, schedules, claim, dispatch, busy=None, ledger=None)：可全注入，纯逻辑无 IO
models.py    # ScheduleRecord / ScheduleFire 视图（pydantic，两档投影逐键一致）
```
`engine.tick()` 刻意不持线程、不 import 存储：IO 与线程归 API 层装配（照 `versioning/publish.py` 与 `storage/recovery.py` 的既有分层），这样调度语义可被完整单测覆盖而不起真时钟。

**回调形状（落码用，避免"claim 的键是什么"这种歧义）**：
`claim(record, slot_utc) -> bool`（**rowcount==1 才 True**，跨进程/跨重启的权威）、`dispatch(record, slot_utc) -> None`、`busy(record) -> bool`（同图有 `running`/`suspended` 运行）。引擎返回值只含**有动作**的条目，动作枚举 `fired | skipped_overlap | claim_lost`。

**进程内 ledger 的作用**（与 D-5 的区分要写清）：认领表是**跨进程**的权威，ledger 只是本进程"同一槽位不再做第二次决定"的去重（30s tick 会重复看到同一个分钟槽）。它不承担安全性：`skipped_overlap` 每槽只计一次数是 ledger 决定的，重启后 ledger 清空、当前分钟内的旧槽可再被评估一次——**这只影响计数观感，不影响"至多派发一次"**，因为派发权始终在认领表上。

**2.2 迁移 030（两表，幂等）**

键形态按仓库既有先例取**租户复合键**（`message_deliveries`/`approval_history`/`shadow_runs` 全部是 `(tenant_id, …)`），不引入 `schedule_id` 代理键——代理键会带来"谁来生成、graph 删除后如何回收"两件无收益的事：

```sql
schedules      PRIMARY KEY (tenant_id, graph_id)              -- version, cron, enabled, created_at, last_fired_at, last_skipped_at, skip_count
schedule_fires PRIMARY KEY (tenant_id, graph_id, slot_utc)    -- fired_at（只记实际派发）
```
认领键即 `(tenant_id, graph_id, slot_utc)`，与 D-5 的"每个槽位至多一次"等价，且天然租户隔离。
`schedule_fires` **不设 outcome 列、不记 skipped**：写"认领了但跳过"会破坏 D-6 的"不消耗槽位"，跳过计数另存 `schedules.last_skipped_at`/`skip_count`（重启后仍在，PG 档）。

**2.3 装配（`api/main.py`）**：`lifespan` 起 `SchedulerThread`（默认 30s tick，`ATLAS_SCHEDULE_ENABLED` 缺省开；进程退出即止，与 `recover_pending` 同一位置）。**启动顺序**：迁移 → recover_pending → scheduler（避免恢复未完就派发）。

**2.4 端点（新增 3 个，权限沿用现有 capability）**

| 方法路径 | 权限 | 语义 |
|---|---|---|
| `GET /api/schedules` | read | 列本租户调度（含 `nextFireAt`、`lastFiredAt`、`skipCount`、`enabled`） |
| `POST /api/schedules/{graphId}/enabled` | operate | 开/关（body `{enabled: bool}`）；图不存在 404 |
| `POST /api/schedules/{graphId}/run-now` | operate | 立即按钉版派发一次（**不写认领表**，不占槽位），供联调与验收；重叠时同样跳过并回 409 中文 |

**2.5 前端**：`schedules` 命名空间（zh＋en，纳入 `PARITY_PAIRS` 三条守护）＋控制台一张表（图/Cron/版本/下次触发(UTC)/最近触发/跳过数/开关/立即运行），触发节点配置面板的 `cron` 字段加**合法即时校验提示**（复用后端错误码文案）。

## 4. 测试与验收（U874 起；只许增测）

- **cron 子集**（U874–U879）：`*/5`、`a-b/n`、列表、字段越界拒绝、`?`/`@daily`/6 字段拒绝、`next_fire_utc` 跨小时/跨月/闰年 2 月 29、`matches` 与 `next_fire` 互逆一致（`next_fire` 返回的槽必 `matches`，且两槽之间不再有匹配）。
- **引擎语义**（U880–U885）：一个 tick 内同槽两次 `tick()` 只派发一次（注入假认领表）；错过槽位在启动时**不补跑**；`enabled=false` 不派发；同图 `running`/`suspended` ⇒ 跳过**且不消耗认领**（下一个干净槽仍派发）；`dispatch` 抛异常不杀引擎、只记日志。
- **两档一致**（U886）：同一时间线喂两档 store，派发序列与 `nextFireAt` 逐键一致；内存档易失性写成显式断言（不是"碰巧一样"）。
- **API/装配**（U887–U890）：发布带 cron 的图 ⇒ `GET /api/schedules` 出现该记录且 `version` 是发布号；再次发布 ⇒ 版本与 cron 更新、`enabled` 保留；`run-now` 不写认领表；越权与跨租户 404/403。
- **保存期校验**（U891）：坏 cron ⇒ 422 中文＋`NODE_TRIGGER_CRON_INVALID`，与既有 `NODE_TRIGGER_CRON_REQUIRED` 并存不冲突（前端 `validation` 命名空间两档补键）。
- **反向门（必做，防永真断言）**：① 把 `engine.tick` 的认领短路成恒真 ⇒ "同槽只派发一次"必须转红；② 把重叠跳过短路成直接派发 ⇒ 跳过用例转红；③ 启动追赶逻辑若被打开 ⇒ 不补跑用例转红。三条都要实跑贴结果，不是"应该能红"。
- **端到端（真进程）**：临时起 uvicorn，把某张已发布图的 cron 设成 `* * * * *`（每分钟）＋ `ATLAS_SCHEDULE_*` 缩短 tick，**等一次真实派发落 `runs` 表**，并**重启进程确认不补跑**。这是本批唯一能证明"图真的会自己跑"的证据，收口必须贴真跑输出（照 docs/62 端到端门的做法）。

## 6. 残余风险（写清楚，别当成修完了）

1. **不补跑是设计选择**：进程停 3 小时 ⇒ 这 3 小时的槽全丢。对"每天凌晨对账"这类任务，漏跑比补跑危险（补跑可能在业务高峰执行真实退款）。**运维可见性靠 `skipCount`/`lastFiredAt` ＋ 告警**，而"错过槽位的补跑开关"登记为新缓做（docs/14），本批不开。
2. **UTC-only** 对国内运营是真实的认知负担；控制台标注＋文档写明，命名时区调度留待 B 组"命名时区函数库"一起做。
3. **cron 子集没有别名与 `?`**：从别处迁移过来的表达式可能保存失败——这是有意的（拒绝优于猜）。
4. **内存档重启可能重复触发一次**（认领历史易失）。演示形态可接受，生产形态必须 PG 档——与仓库其余两档差异同构，不新造机制。
5. **派发出去的运行不受调度器生命周期管辖**：关调度只停未来触发，不取消在途 run（与 webhook 同语义）。
6. **本批不解锁多副本**：认领让"重复触发"安全，但审批 broker/事件等待/灰度态/急停句柄仍是进程内（docs/63 §3 残余清单一条没动）。**N3 也仍开**——核心闭环还差它和真外部资源。
7. **一图一条调度**：一张图里放两个定时触发节点（不同 cron）时，落码取**第一个**并对其余打 warning 日志（`api/main.py::_schedule_cron_of_published`）。刻意不做"多 cron 并存"——那要先回答"两条调度跑同一张图算几次并发"，而 D-6 的重叠判定是**按图**粒度的，多调度会立刻退化成"每分钟都在跳过"。DSL 也不阻止你画两个，所以这里靠 warning 兜住，登记 14 D41③。
