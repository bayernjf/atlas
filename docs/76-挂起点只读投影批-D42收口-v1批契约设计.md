## 1. 决策（七条，改任何一条先改本文）

- **D-1 只读，且只有读**。新增一个 `GET /api/interruptions`，不新增写路径、不新增端点动作（无重放／无清帧／无改状态）、不新增迁移、不新增错误码、不新增依赖。**明确不解除 D36**：本批做完，"崩溃后要不要重放"仍然没有答案，只是终于能看见它发生了几次。
- **D-2 新写一条租户内查询，不复用 `load_pending_frames`**。后者是**全局**扫描（`recovery.py:87-101` 无 `WHERE`），那是启动恢复的正确语义（一个进程要替所有租户恢复）；拿它做 HTTP 端点的数据源＝把别的租户的 token 先读进本进程内存再在 Python 里丢掉——**多一趟无谓的跨租户读，且没有索引优势**。故 `recovery.py` 新增 `list_tenant_frames(engine, tenant_id)`（`WHERE tenant_id = :t ORDER BY created_at`，走 P-4 那个索引），启动恢复路径继续用老函数，**两条路不合并**。
- **D-3 状态只描述、不判决**。每条帧投影出一行，`state` 取四个值之一，全部由"帧列值＋run 状态"**算出来**，不引入任何阈值或计时器：
  | `state` | 含义 | 判据 |
  |---|---|---|
  | `awaiting` | 还没人越过这个挂起点（正常等待中） | `resumed_at IS NULL` |
  | `claimed_executing` | 已被认领、run 正在跑（**正常在途**，不是故障） | 已认领 ∧ run status ∈ {`running`} |
  | `claimed_suspended` | 已被认领、run 却仍停在 suspended ⇒ **这就是 D36 说的那颗雷** | 已认领 ∧ run status ＝ `suspended` |
  | `frame_lingering` | 已被认领、run 已到终态而帧未清（P-6 那条实况） | 已认领 ∧ run status ∈ {`completed`,`failed`,`cancelled`,`interrupted`} |
  run 查不到（本租户 run 存储里没有该 runId）⇒ `runStatus: null` ＋ `state: "claimed_unknown_run"`，**不猜**它去哪了。
  ⚠️ **`claimed_suspended` 有已知的瞬时假阳**：一次正常续跑在"已写 `resumed_at`"到"run 落终态"之间，run 可能仍是 `suspended`。契约的处理方式**不是**加计时器（那要拍一个没人批准的秒数），而是把 `claimedAt` 与算出来的 `claimedSeconds` 一起给出去，让运营自己判读；页面文案明写"刚认领的可能是正在续跑"。
- **D-4 内存档必须自报"看不见"，而不是回一个漂亮空列表**。响应带 `backend`；内存档返回 `{backend:"memory", items:[], visibility:"frames-not-persisted"}`，前端据此渲染一条**警示**（"当前为内存档：挂起帧不入库，本表恒空——空列表不代表没有卡住的 run"）。理由：P-1 之下"空"与"没有卡住的 run"是两件不同的事，让运维把前者读成后者是本批最容易造的假绿。
- **D-5 鉴权档取 read（viewer 起）**，与 `/api/waits`、`/api/runs` 同族（只读运行态）；跨租户不可见由 D-2 的 `WHERE tenant_id` 保证，端点不接受任何 tenant/runId 入参（**没有可供越权的参数**）。
- **D-6 顺手把 `waits` 纳入 `PARITY_PAIRS`**：本批要给 waits 加两档文案，不加守护就是明知有洞还往里写。这一条是"多做的"，但它是**机检补强而非功能**，与本批同一提交段内做完，并单独成一个 test 原子。
- **D-7 不碰的三样**：① 不改 `clear_frame` 的调用时机（P-6 那处只显形、不修）；② 不动单副本三道闸与 D19/D20/D27/D31/D32 任何缓做；③ 不给"重放"留任何钩子（哪怕是一个未被调用的函数）——留了就等于替 D36 拍了板。

## 6. 残余风险（写清楚，别读成"D36 解决了"）

1. **本批一个字也没解决 D36**。它让"崩了几次、崩在哪条 run"可查，重放与否仍是 D36 的语义决策；**看见问题不等于有权处理问题**——这是本批最容易被人误读成收口的地方。
2. **`claimed_suspended` 有瞬时假阳**（D-3 那条 ⚠️）。没有阈值是刻意的：任何秒数都要有人拍，而没人拍过。页面把它写成"可能是正在续跑"，而不是藏起来。
3. **P-6 那处帧残留本批不修**：`api/main.py:271-276` 失败路径不清帧。修它属写路径改动（且会牵"失败后还能不能人工看一眼现场"的取舍），本批只把它显形为 `frame_lingering`。
4. **内存档永远是盲区**（P-1）：dev/沙盘形态下这张表压根不写，警示文案因此不是装饰——它挡的是"在 demo 档查了个空、回去汇报说没有卡住的 run"。
5. **列表无分页**：`interruptions` 每租户实际很小（retention 会清已认领帧，docs/65 K-A），且查询走 `idx_interruptions_tenant`；若真实数据量大到需要分页，那是随 D36 或运营报障再谈的事，本批不预设（预设了就是没有需求的复杂度）。
6. **本表有 30 天的"记忆上限"**〔码〕：retention 只淘汰 `resumed_at IS NOT NULL` 的帧（`storage/pg.py:104-105`），`interruptions` 默认保留 **30 天**（`storage/retention.py:21/31`，env `ATLAS_RETENTION_INTERRUPTIONS_DAYS`）。⇒ **`claimed_suspended`/`frame_lingering` 两类都已认领，30 天后会从这里消失**，本投影是"近期现场"不是历史台账；真要做长期审计属 D36／D28 长保留那一批。未认领帧与挂起态 run 永不淘汰（同一函数），所以"还在等的"不会因为保留期看不见——只有"已经崩过的"会。这一条必须写出来，否则"这周查过没有"会被读成"从来没有过"。

**落码与契约的偏差（逐条写清，防止后来者按契约文读代码）**：
1. **§4 那句"摘掉 `WHERE tenant_id` 必须红"没有以"改生产代码"的方式执行**——植入门被权限拦下，**未绕道**。改成了**同一库、同一批真帧上的差分对照**（U921 的第 3 例）：全局 `load_pending_frames` 确实看得见三条帧，租户查询只看得见自己两条。证明力等价（"绿"不来自"根本没数据可漏"），但**它证明的是查询语义，不是"谁改了 SQL 都会被抓住"**——真防复发靠 CI 每次跑 `-m integration`。
2. **`state` 从五档变六档**：多出一个 `claimed_other_state`，用于"帧已认领、run 状态是不认识的字符串"。契约没预留这一档，而 `runStatus` 是 TEXT 列、未来加状态就会撞上——**不猜**是这批的口径，所以宁可加一档。
3. **`visibility` 在 PG 档也有值**（`tenant-scoped`），契约里它只是内存档的可选标记。两个档位都自带标记，前端就不需要靠"哪个分支"去推断自己看到的空是什么空。

## 8. 追记（同日 2026-09-27，实测推翻 §0 P-6 与 §6.3 的归因，并已修：`d9cb60d`/`56eff7d`）

**测了什么**：收口当天把**最常见的路径**真跑了一遍——真 PG 档、真图、真 `human_approval` 挂起、**在同一个活进程里审批通过**、运行正常 `completed`。结果：表从 **0 行变 1 行**，那一行的档位正是 `frame_lingering`（`resumed_at` 已置位、认领者是本机进程、运行却早已终态）。

**于是 §0 P-6／§6.3 的归因是错的**（原文照留，以本节为准）：本文件说帧残留来自"`main.py:271-276` 续跑抛异常时不清帧"。**那条路径确实也不清，但它不是主因**——真实机制是**只有启动恢复的续跑成功路径清帧**（`_resume_run` 末尾那一处 `clear_frame`），而**审批在活进程里被决定才是常态**：`loader.py:763` 的 `_gate_resume` 把帧认领掉，运行随后正常终态，**没有任何人清它**。按 §6 的原写法，这张表会被"健康的运行"逐日填满，而它唯一要盯的 `claimed_suspended` 埋在中间——**本批的价值被这条泄漏直接吃掉**。今天没暴露是因为集成测全靠手工播种，播种机不会替我跑一遍真审批。

**改了什么（`d9cb60d`）**：`PgRunsStore.finish()` 在同一事务里 `DELETE FROM interruptions WHERE tenant_id = :t AND run_id = :r`。选这里而不是在各入口分散调用，理由是**终态只有一条路**：同步运行、流式 worker、后台 pin 运行、`_resume_run` 的成功与失败分支全经它；而**崩溃路径根本不调 finish** ⇒ 帧与雷照旧留下（docs/62 §2 D-1 的取舍一点没动）；**让位输家也不调 finish**（docs/62 §2 D-4）⇒ 不会误伤赢家的帧。

**正反两面都测（`56eff7d`）**：U923 两例真库——① 一条运行终态 ⇒ 它名下两条帧（一图挂起两次）全清、**另一条运行的帧一条没动**；② 认领了但从不到终态 ⇒ 帧仍在、`_interruption_state` 仍算出 `claimed_suspended`。**没有②，①可以靠"每次都清"骗绿**。反向门做在**本批我自己写的代码**上（不是已交付的护栏，不属"破坏他人依赖"）：把 DELETE 的 `run_id` 换成不存在的值，①当场红且三条帧全留；改回即绿。探测脚本加第 4 段跑真审批路径，四段全过、退出码 0。

**顺带学到的两条，写在这里防止再犯**：
1. **探测必须"先起服务再播种"**。启动恢复会把未认领的合成帧当成待续跑的真中断并起线程 ⇒ 合成帧没有 `graph_snapshot`，那次续跑必然失败、运行落 failed、帧按本节新规则一并了结——于是第 2 段少一行。**这是"产品行为正确、探针写法错"的实例**，不是 bug，已把顺序与原因写进脚本注释。
2. `ok()` 在成功时也打同一句话，所以"失败句式"的文案会输出成 `OK 运行到终态后仍留 1 行挂起帧`（吓人）。第二批文案已改陈述式——**证据输出的措辞也是产物**（同 §7 偏差 5，这次又多一处，说明它是习惯性错误而非偶发）。

**改完之后 `frame_lingering` 还有意义吗**：有，但**应当极少**——它从"常见"变成"只有有人绕过 `finish()` 直改 `runs` 表、或将来新增终态路径漏接时才出现"。留着这一档仍是因为**不猜**：多一个枚举值比把未知塞进已知便宜也更诚实。
