## 1. 背景与范围

`message/send` 现支持 email（SMTP 真实发信）与 webhook（单 URL POST JSON），但真实客服流程最常用的 IM 机器人通知（钉钉/企业微信/飞书群机器人）仍只落进程内记录，用户接图无法真正触达值班群。三家群机器人都是「Webhook URL + JSON 文本消息」形态，与既有 webhook 渠道同构，差异仅在包体字段与可选取号签名。

本批取 **channel=dingtalk | wecom | feishu 的进程内 v1**：`to` 为机器人 Webhook 单个 URL（过既有 SSRF egress 校验），新增可选参数 `secret`（钉钉/飞书加签），按各家协议构造文本消息并 POST；HTTP/平台错误码失败时 **确定性失败（IM_SEND_FAILED），不写记录**。旧渠道与旧图零回归。

### 范围内

1. Runtime：新模块 `message/im.py`（三家协议包体/加签/响应判定）与 `MessageService` 渠道接入（§2）。
2. Capability 契约：`message/send` input schema 的 channel 口径与新增可选 `secret`（§2.3）。
3. 前端：message/send 参数字段经 Schema 自动渲染新字段（零/最小改动，§4）。

### 显式非目标（仍缓做，收口时回写 D24 注记）

- **短信渠道**：需短信平台账号与计费，仍随真实触达业务。
- **富文本/Markdown/卡片消息、@指定人、图片文件**：v1 仅 text 消息（subject + body 拼接为纯文本）。
- **多 Webhook URL 群发**：IM 渠道 `to` 仅单个 URL，与 webhook 渠道同约束。
- **真实 IM 应用（企业内部应用 access_token、消息回执/已读、入站消息消费）**：v1 只覆盖自定义群机器人。
- **消息模板系统、限流退避队列、投递状态追踪、重试**：仍随 D24 余部。
- **secret 的密钥信封管理 UI**：v1 的 secret 与 webhook URL 同为运行时节点参数；生产应从 secret provider 注入（T26 信封），本批不做绑定管理。

## 2. 运行时语义（实现 `atlas.message`）

### 2.1 参数与渠道校验（service.py）

`MessageService.send` 签名增可选 `secret: object = None`（MessageHarnessAdapter 透传 `params.get("secret")`）：

- `channel` 增合法值 `dingtalk`/`wecom`/`feishu`；三渠道与 webhook 一致，`to` 为数组（即使单元素）→ `INVALID_PARAMETER`；`to` 必须为单个非空 URL 字符串。
- `secret`：仅 `dingtalk`/`feishu` 允许传入；非空字符串、≤200 字符。其他渠道（含 wecom/email/webhook/进程内渠道）传非空 secret → `INVALID_PARAMETER`（避免误以为已加签）；钉钉/飞书留空则不加签（两家均支持无签名机器人安全设置）。
- `subject`/`body` 必填规则不变；消息文本 `text = subject + "\n" + body`。
- 未注入 IM 投递器（demo/测试）时三渠道仍写进程内记录、`delivered="in_process"`，旧行为不回归。

### 2.2 投递（message/im.py）

新模块 `atlas.message.im`，零新依赖（`hmac`/`base64`/`urllib.parse`/`httpx`，复用 `security.egress.EgressGuard`）：

```python
class ImSender(Protocol):
    def send(self, channel: str, url: str, text: str, secret: str | None) -> None: ...

class DefaultImSender:
    def __init__(self, guard=None, post=None, clock=None): ...  # 均可注入，测试不触网
```

1. 出向：`guard.check(url)`（http(s)，私网/环回/元数据地址拦截）；`EgressDenied` 不包装、由 service 透传其 code。
2. 时间戳取注入时钟（默认 wall clock），保证回放可确定。
3. 各渠道协议：

| 渠道 | URL 处理 | 请求体 |
|---|---|---|
| dingtalk | secret 时拼接 `&timestamp=<ms>&sign=<urlencode(base64(HMAC_SHA256(key=secret, msg=f"<ms>\\n<secret>")))>` | `{"msgtype":"text","text":{"content": text}}` |
| wecom | 不变 | `{"msgtype":"text","text":{"content": text}}`（v1 不签名） |
| feishu | 不变 | `{"timestamp":"<sec>","sign":"<base64(HMAC_SHA256(key=b"", msg=f"<sec>\\n<secret>"))>","msg_type":"text","content":{"text": text}}`；secret 缺省时无 timestamp/sign 两键 |

4. 响应判定：HTTP 状态须 2xx；响应 JSON 中：
   - dingtalk / wecom：`errcode == 0`；
   - feishu：`code == 0`（或 `StatusCode == 0` 的兼容形态，以 code 为准）；
   - 非 2xx、非 JSON 或平台错误码非 0 → `ImDeliveryError`（消息含平台码与 errmsg）。
5. 网络错误/超时（10s，不跟随重定向）→ `ImDeliveryError`。

### 2.3 成功/失败语义

- 成功：记录 `delivered` 标渠道名（`dingtalk`/`wecom`/`feishu`）。
- `EgressDenied` → service 折算 `MessageSendError(exc.code, ...)`（同 webhook 路径）。
- 其他投递异常 → `MessageSendError("IM_SEND_FAILED", f"IM 投递失败：{exc}")`；**不写消息记录**（非幂等写能力）。
- trace 无新增（经 tool_call 既有路径）。
