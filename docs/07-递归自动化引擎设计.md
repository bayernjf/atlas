# 递归自动化引擎设计（Atlas）

## 一、总体架构与设计原则
### 1.1 递归自动化的核心定义
在现有平台中，用户手动配置 Harness 适配器、Graph 流程、知识库。递归自动化引擎使平台具备自我构建、自我修复、自我优化、自我管理的能力——即用运营体来创建、维护和进化其他运营体。
### 1.2 总体架构分层
### ┌──────────────────────────────────────────────────────────┐
│                   递归自动化引擎（Meta Layer）              │
│  ┌─────────────┐ ┌─────────────┐ ┌─────────────┐        │
│  │ 平台探索器   │ │ 行为挖掘器   │ │ 诊断修复器   │        │
│  │ (Adapter    │ │ (Agent      │ │ (Self-Healing│        │
│  │  Auto-Build)│ │  Auto-Gen)  │ │  Engine)     │        │
│  └─────────────┘ └─────────────┘ └─────────────┘        │
│  ┌─────────────────────────────────────────────────┐    │
│  │              元运营体（Meta-Agent）                │    │
│  │        监控、调度、优化所有运营体的“管理者”        │    │
│  └─────────────────────────────────────────────────┘    │
│  ┌─────────────────────────────────────────────────┐    │
│  │          自我进化模块（Platform Evolution）       │    │
│  │     从用户行为中自动提炼模板、配置、最佳实践       │    │
│  └─────────────────────────────────────────────────┘    │
├──────────────────────────────────────────────────────────┤
│            基础执行层（原有 Harness+Loop+Graph）           │
│    Harness 适配层 | Loop 引擎 | Graph 知识/流程层          │
│    评估 Harness | 记忆系统 | 知识库 | 模型路由             │
└──────────────────────────────────────────────────────────┘
### 1.3 递归自动化的关键特性
- 自举性：引擎本身由运营体实现，可以操作平台自身的 API 和界面。
- 可观测性：所有递归操作都有完整审计日志，可追溯、可回滚。
- 人机协同：自动生成的产物默认是“草稿”，需人工审核后发布，关键操作需确认。
- 渐进自主：随着置信度提升和人工批准积累，系统逐步获得更多自主权。
## 二、模块一：平台探索器（Adapter Auto-Builder）
### 2.1 目标
用户提供一个目标平台的 URL 和登录凭证，系统自动探索该平台，识别可操作元素和业务对象，生成 Harness 适配器定义（工具列表、输入输出 Schema、认证配置）。
### 2.2 核心流程
### 用户输入平台信息（URL、账号）
↓
【探索运营体启动】
↓
1. 自动登录（使用预置的登录技能，处理常见登录表单）
↓
2. 界面爬取：遍历可见页面，识别菜单、按钮、表单、列表
↓
3. 业务对象识别：从 URL 模式、页面标题、表格结构中推断实体（订单、商品、用户）
↓
4. 操作试运行：对典型操作（查询、创建、更新）进行试执行，观察结果
↓
5. 工具定义生成：为每个有效操作生成工具 Schema
↓
6. 验证测试：自动运行工具，校验输入输出
↓
7. 输出适配器定义（草稿）
↓
用户审核 → 发布为正式适配器
### 2.3 技术实现细节
#### 2.3.1 探索运营体设计
该运营体本身是一个标准的 Harness+Loop+Graph 智能体，其 Graph 包含：
- 登录节点：使用通用的登录技能，自动填充用户名/密码，处理验证码（人工辅助或 OCR）。
- 导航节点：遍历所有可点击链接/菜单，构建站点地图。
- 元素识别节点：使用视觉模型（OmniParser/GPT-4V）分析每个页面的可交互元素。
- 操作推断节点：LLM 分析元素语义，推断可能的动作（如“点击‘新建订单’按钮”）。
- 工具生成节点：将推断出的操作组装成工具定义（输入参数、输出 Schema）。

- 使用 Playwright 加载页面，获取 DOM 和可访问性树。
- 截图并调用 OmniParser 解析出带语义标签的元素（按钮、输入框、表格等）。

- LLM 归类：判断哪些页面属于 CRUD 操作，哪些是列表/详情。
- 输出实体关系草图，供后续 Graph 生成使用。

### 三、模块二：行为挖掘器（Agent Auto-Generator）
### 3.1 目标
从用户在目标系统中的操作日志中，自动识别高频重复操作序列，生成运营体草稿，建议用户自动化。
### 3.2 核心流程
### 用户授权监控操作日志
↓
【行为挖掘运营体】定期运行
↓
1. 收集操作日志（来自 Harness 录制、浏览器插件、系统事件）
↓
2. 序列模式挖掘：识别频繁出现的操作序列
↓
3. 候选流程生成：将序列转换为 Graph 草稿（触发器+步骤+条件）
↓
4. 业务语义分析：LLM 理解操作序列的业务含义
↓
5. 生成运营体建议卡（展示预期节省时间、自动化可行性）
↓
用户一键生成 → 进入编辑器微调 → 发布
### 3.3 技术实现细节
#### 3.3.1 操作日志来源
- 浏览器插件捕获用户点击、输入、页面跳转。
- Harness 录制器（当用户使用平台的手动模式时）。
- 集成系统的审计日志（如果用户提供）。
- 日志格式
### 3.3.2 序列模式挖掘
- 使用序列挖掘算法（PrefixSpan、GSP）识别频繁子序列。
- 设置支持度阈值（如：同一用户一周内执行 5 次以上相同序列）。
- 将操作序列按业务对象分组（如同一订单号的操作序列）。
#### 3.3.3 Graph 草稿生成
- 将操作序列映射为节点：触发器（如收到退款申请）→ 工具调用（点击退款按钮）→ 条件（金额判断）等。
- LLM 分析操作序列，补充缺失的逻辑（如异常处理、审批分支）。
- 生成 DSL 草稿，渲染到编辑器。
### 3.4 触发机制
- 定时运行（每天/每周），分析新增日志。
- 实时检测：当用户重复执行同一操作超过阈值时，立即提示。
### 四、模块三：诊断修复器（Self-Healing Engine）
### 4.1 目标
运营体执行失败时，自动派发诊断运营体，分析失败原因并生成修复方案。
### 4.2 核心流程
### 运营体执行失败（节点报错/超时/结果异常）
↓
自动触发诊断运营体（或由元运营体调度）
↓
1. 收集失败上下文：日志、截图、变量快照、执行轨迹
↓
2. 复现失败：在沙盒中重放失败步骤
↓
3. 根因分析：LLM + 规则引擎分析失败类型
↓
4. 生成修复方案：
- 元素定位失效 → 更新选择器（视觉重定位）
- API限流/超时 → 调整重试策略或切换备用API
- 参数错误 → 修正参数映射
- 流程逻辑错误 → 建议修改 Graph 分支
↓
5. 沙盒验证修复方案
↓
6. 生成修复建议卡 → 人工审批 → 应用
### 4.3 技术实现细节
#### 4.3.1 诊断运营体设计
诊断运营体是一个专门处理“修复任务”的智能体，其 Graph 包含：
- 收集证据节点：调用平台 API 获取失败日志、截图。
- 复现节点：使用 Harness 在沙盒中重试失败步骤。
- 分析节点：LLM 综合分析，输出根因分类和修复建议。
- 验证节点：在测试环境执行修复后的流程，检查是否通过。

### 五、模块四：元运营体（Meta-Agent）
### 5.1 目标
一个“管理者”运营体，监控所有运营体的健康状况，自动处理常见问题，生成报告。
### 5.2 核心职责
- 健康监控：定期检查每个运营体的运行指标（成功率、延迟、错误率）。
- 异常响应：发现异常时，自动调用诊断修复器。
- 资源调度：根据负载调整运营体的并发数、模型路由。
- 知识更新：从运营体运行数据中提炼新知识，更新知识库。
- 日报/周报生成：汇总运营数据，发送给管理员。
### 5.3 技术实现
元运营体是一个特殊的长期运行运营体，拥有更高权限。其 Graph 包含多个子图：
- 监控子图：定时查询指标数据库，与阈值对比。
- 诊断调度子图：调用诊断修复器。
- 报表子图：生成自然语言报告。
元运营体本身也受递归自动化管理：它也可以被诊断和优化。
### 六、模块五：自我进化模块（Platform Evolution）
### 6.1 目标
从平台所有用户的使用数据中，自动提炼最佳实践，生成模板、配置预置、甚至新功能建议。
### 6.2 核心机制
- 配置智能推荐：分析用户频繁修改的配置项，自动生成默认值或预置选项。
- 模板自动生成：当某类运营体的创建模式重复出现时，自动封装为模板。
- 适配器市场优化：分析适配器的使用率和成功率，推荐高质量适配器，淘汰低质量。
- 提示词工程优化：从高效运营体的提示词中学习，自动优化默认提示词模板。
### 6.3 实现方式
- 使用数据分析管道（批量处理用户使用日志）。
- 采用聚类、频繁模式挖掘、LLM 总结。
- 产出候选改进项，由产品团队审核后发布。
## 七、与现有架构的集成
### 7.1 新增服务

| 服务名称 | 功能 | 技术栈 |
| --- | --- | --- |
| Exploration Service | 平台探索器核心 | Python + Playwright + OmniParser |
| Mining Service | 行为挖掘器 | Python + 序列挖掘库 |
| Healing Service | 诊断修复器 | Python + LangGraph |
| Meta-Agent Runtime | 元运营体运行环境 | 复用 LangGraph 引擎 |
| Evolution Pipeline | 自我进化数据管道 | Spark/Flink + LLM |

### 7.2 数据流
### 用户操作日志 → Mining Service → Agent Draft
运营体执行 → 日志/指标 → Meta-Agent → Healing Service
探索任务 → Exploration Service → Adapter Draft
平台使用数据 → Evolution Pipeline → 模板/配置更新
### 7.3 权限与安全
- 所有递归自动化操作默认在沙盒中运行。
- 元运营体拥有“管理”权限，但关键操作（删除运营体、批量修改）需二次人工确认。
- 自动生成的产物均为草稿，需人工审核发布。
### 八、关键技术挑战与应对

| 挑战 | 应对方案 |
| --- | --- |
| 自动探索可能触发危险操作 | 在沙盒中探索；白名单限制操作类型（只读优先）；对写操作需确认 |
| 行为挖掘误报 | 设置置信度阈值；用户可关闭挖掘；生成草稿仅作建议 |
| 诊断修复可能引入新错误 | 修复方案必须沙盒验证；保留回滚；人工审批 |
| 元运营体自身故障 | 元运营体也受监控；可采用多实例冗余；简单规则兜底 |
| 递归深度失控 | 设置最大递归深度（如诊断运营体不能再被自动修复，需人工介入） |

### 九、实施路线图
### Phase 1
- 实现平台探索器 MVP：支持常见 Web 平台的只读探索和工具生成。
- 实现行为挖掘器简单版：基于浏览器插件的操作序列识别和提示。
- 实现基础诊断修复：元素定位失效的自动修复。
### Phase 2
- 完善探索器：支持 API 平台、数据库、移动端。
- 元运营体上线：健康监控、自动调度诊断。
- 自我进化模块：配置推荐和模板自动生成。
### Phase 3
- 全自主探索：极少人工干预。
- 递归深度扩展：允许诊断运营体被自动修复（受限）。
- 平台自我进化：自动提炼新功能需求。
### 递归自动化引擎将平台从“用户驱动的工具”升级为“自组织的智能体生态系统”。差异化核心壁垒：用户接入新平台的成本趋近于零，运营体的维护成本大幅降低，平台自身能够持续进化。
