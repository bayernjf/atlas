## 1. 背景与范围

监控告警 v1 已能在运行失败/越阈时产站内告警（合并、静默、升级、值班），但告警只存在于页面列表：值班人员不打开监控页就看不到问题。docs/51 落码后，钉钉/企微/飞书群机器人已可真实投递，告警出口的最后一块拼图就是「新告警自动发到租户配置的通知渠道」。

本批取 **租户级单一告警通知渠道 v1**：租户配置一个通知目标（dingtalk/wecom/feishu/webhook/email）+ 最低告警级别，**仅新建告警时**自动经既有 `MessageService` 投递一条固定格式文本；通知失败一律 fail-safe（不影响运行记录、不丢告警），并在配置状态里暴露最近投递结果。旧行为零回归。

### 范围内

1. Runtime：`monitoring/notify.py`（`AlertChannel` 配置模型 + `AlertNotifier` 过滤/构造/投递/失败计数）；内存与 PG 两档存储接入（§2）。
2. REST：`GET/PUT /api/monitoring/alert-channel`（§2.4）。
3. 前端：监控页告警通知配置卡（§3）。

### 显式非目标（仍缓做，收口时回写 D28 注记）

- **按规则/按图多渠道、通知路由策略**：v1 每租户一个渠道、一个最低级别。
- **告警合并再通知、升级通知、解决通知、恢复通知**：v1 只在新建告警时发一次；合并计数天然降噪，升级/解决事件不触发。
- **通知模板系统、变量化、富文本/卡片、@值班人**：固定纯文本格式（与 notify_decided 同口径）；模板随 D24 余部。
- **通知限流/退避/重试/投递历史页**：仅保留最近一次投递状态（时间/成败/错误码）；合并语义即 v1 限流。
- **OTel/Prometheus/Grafana 正式栈**：与本批无关，仍随 D11。

## 2. 运行时语义（实现 `atlas.monitoring` / `atlas.api`）

### 2.1 配置模型（monitoring/notify.py）

```python
class AlertChannel(BaseModel):          # 租户单例；默认全空＝未配置（不发任何通知）
    enabled: bool = False
    channel: Literal["dingtalk", "wecom", "feishu", "webhook", "email"] = "dingtalk"
    to: str = ""                        # IM/webhook＝单个 URL；email＝单个邮箱
    secret: str = ""                    # 仅 dingtalk/feishu：加签密钥，≤200
    minSeverity: Literal["critical", "warning"] = "critical"  # warning ＝ warning+critical 都发
    updatedAt: str = ""                 # 最近配置保存时间（服务端填）
```

配置校验（PUT 时）：`enabled=true` → `to` 必填且按渠道匹配形态（IM/webhook 须 http(s) URL、email 须含 `@`，违例 422 中文聚合）；secret 非空时仅 dingtalk/feishu 允许、≤200；`enabled=false` 不校验内容（允许先存草稿再启用）。channel/to/secret 运行时语义与 docs/51 完全一致（SSRF、加签、失败码），本批不另立投递路径。

### 2.2 投递（AlertNotifier）

`AlertNotifier(message_service)`：

- `notify(alert: Alert, channel_cfg: AlertChannel) -> None`：
  ① cfg 未配置/enabled=false → 直接跳过；
  ② severity 过滤：`minSeverity=critical` 时 warning 告警跳过（critical 才发）；
  ③ 构造固定文本，调 `message_service.send(channel=cfg.channel, to=cfg.to, subject=..., body=..., secret=cfg.secret or None)`；
  ④ 任何 `MessageSendError`/异常 **只捕获不抛出**，记录 `last_error_code`/`last_error_message`/`last_notified_at`（投递成功时错误字段清空、记成功时间）；返回值供 GET 状态展示。
- 固定文本（纯文本；不含链接/凭证）：
  - subject：`[Atlas告警][{severity}] {rule_label}`（rule_label 取 rule_name → rule_id 三级回退，与监控页一致）
  - body：`{alert.message}\n图：{graph_id}\n运行：{last_run_id}\n级别：{severity}\n值班：{assignee 或 未指派}\n首次：{first_seen}`
- 触发点（**仅新建告警**，两处存储实现共用本模块）：
  - `MonitoringStore._raise_or_merge`：新 Alert append 之后调用 notifier（合并路径不调用）。
  - `PgMonitoringStore.record_run` 的新告警分支同样调用；`raise_rollout_gate_alert` 新建分支也调用（rollout_gate critical 属真实事故，必须触达）。
- notifier 经 setter 注入（`store.set_notifier(...)`）：TenantRegistry 先建 message_service/monitoring，再装配 AlertNotifier 回注，消解「notifier 需 service、store 需 notifier」环。未注入（旧测试）时零行为、零回归。

### 2.3 持久化与 reset

- 迁移 020：表 `alert_notify_settings`（`tenant_id TEXT PK, enabled BOOL, channel TEXT, to TEXT, secret TEXT, min_severity TEXT, updated_at TEXT`）；secret 与 SMTP 口令同信任边界（env/运行时配置；生产应走 secret provider，v1 明文落库仅 Demo，写入非目标注记）。
- MonitoringRepository Protocol 增 `get_alert_channel() -> AlertChannel`、`update_alert_channel(raw: dict) -> AlertChannel`；内存档进程内保存、PG 档 upsert。
- `reset_tenant`：监控重置时本配置一并清空回默认（与 rules 同语义；属运行时配置，录制/反馈不动规则不变）。

### 2.4 REST

| 方法 | 路径 | 鉴权 | 语义 |
|---|---|---|---|
| GET | `/api/monitoring/alert-channel` | read（viewer+） | 返当前配置 + 最近投递状态（`lastNotifiedAt`/`lastError`：code+message；未配置/从未投递为 null） |
| PUT | `/api/monitoring/alert-channel` | administer（admin only，同 rules 门） | 整体替换；校验失败 422 中文聚合；成功回显服务端 `updatedAt` |

角色不足 403、viewer 只读语义与既有监控端点一致。
