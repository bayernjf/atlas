四、三位一体架构设计：如何系统性融合
整体采用 “三层四环”架构：
三层：
1. 接入表示层（Harness）：实现多模态操作能力
2. 认知执行层（Graph + Loop Core）：大脑与剧本
3. 用户DIY层：配置与输出面
四环（Loop的核心，贯穿于Graph之上）：
`Observe（感知）→ Orient（定位）→ Decide（决策）→ Act（执行）`，并增加 `Reflect（反思）` 外环。
1. Harness层：原子化能力编织网
设计为插件化适配器工厂，每个平台对应一个适配器，向上提供统一接口：
- 界面操作适配器：基于视觉模型+可访问性树，输出“可点击/可输入元素”的统一空间。类似UI.Vision、Playwright的能力，但由模型驱动。
- API适配器：将OpenAPI/Swagger自动转换为工具描述，供Loop调用。
- 数据适配器：对接数据库/数据仓库，输出结构化上下文。
- 外设适配器：IoT、机器人等物理操作。
关键设计：能力注册发现机制。每个适配器启动时，会用自然语言+图模式声明自己的能力（如“我能点击，需要一个元素描述”），这成为Graph节点与Harness的粘合剂。
2. Graph层：从流程到因果图谱
这是框架的刚性骨架，保证运营不跑偏：

有向流程子图：定义正常业务路径（如商品上架的12个步骤）。

- 状态机子图：定义业务对象生命周期（如订单的待支付→已支付→已发货）。
- 决策事件图：当触发条件满足时，跳转到对应处理子图（如出现差评，进入挽回流程）。
- 知识图谱：存储产品关系、规则、FAQ，用于推理。
Graph用可扩展的DSL定义，并支持可视化编辑。例如一个“电商促销”图的片段：
```
start -> select_products(harn: product_api.search, params: {category:"美妆"})
select_products -> calc_discount_price(memory: profit_margin_rule)
calc_discount_price -> send_to_channel(harn: channel_publisher, params: {platform:"all"})
send_to_channel -> monitor_sales(loop: true, exit_condition: "time > 2 hours")
monitor_sales -- on: "stock <10" --> urgent_replenish
```
3. Loop层：智能体即持久运行的过程
Loop并不独立存在，它寄生在Graph和Harness之上：
- 动态导航：基于当前Graph节点、实时观察和历史记忆，用LLM决定走哪条边、调用Harness的哪个工具、传入什么参数。
- 异常兜底：当Graph未覆盖的情况发生，Loop将目标转为“调用大模型自由生成动作序列，同时请求专家标注，以自动生长Graph分支”。
- 反思进化：周期性将“动作序列+结果”喂给反思模型，总结策略优劣，调整Graph中的决策阈值或提示词模板。
核心技术：采用强化学习（RLHF）或DPO思想，当运营目标达成时（如GMV提升），整个Loop的决策轨迹被作为正样本微调小模型，让运营策略持续“长”在系统里。

│                      GRAPH 图谱层                    │

├──────────────────────────────────────────────────────┤
│                     HARNESS 适配层                   │
│   Web操作 | API调用 | 移动端 | 桌面端 | 数据库 | IoT   │
└──────────────────────────────────────────────────────┘
### 2.2 系统分层架构
┌───────────────────────────────────────────┐

├───────────────────────────────────────────┤

├───────────────────────────────────────────┤

## 第三部分：技术选型总览

| 层级 | 选型 |
| --- | --- |
| 后端主语言 | Python 3.11+（AI引擎）/ Go（Harness网关、高性能服务；Demo 阶段网关以 Python/FastAPI 实现同构接口，ADR-2026-09-13 T5，见 10 文档 §3） |
| 前端语言 | TypeScript + React 18+ |
| AI框架 | LangChain + LangGraph（核心）、LiteLLM（模型网关） |
| Web自动化 | Playwright + OmniParser（视觉定位） |
| 移动端自动化 | Appium + ADB |
| 数据库 | PostgreSQL（主库+Checkpointer）、pgvector（向量）、Redis（缓存） |
| 消息队列 | NATS（Demo 阶段用进程内事件总线替代，ADR-2026-09-13 T4，见 10 文档 §3） |
| 容器编排 | Kubernetes |
| 模型部署 | 用户自定义（Demo 阶段：LiteLLM 对接主流商业 API，供应商经 `.env` 切换，ADR-2026-09-13 T1，见 10 文档 §3） |
| 可观测性 | OpenTelemetry + Prometheus + Grafana + Loki + Tempo |
| 前端编辑器 | React Flow（图编辑）、Zustand（状态）、Ant Design/Shadcn UI；Demo 落码 `@xyflow/react` 12 + AntD 6 + Vite 8，前端单测 vitest 5（ADR-2026-09-13 T6，见 10 文档 §4） |

## 二、编辑后台组件全景图

| 组件类别 | 核心作用 | 典型实例 |
| --- | --- | --- |
| 节点 | 执行单元，组成流程图 | 触发器、AI决策、工具调用、条件分支、循环、子图 |
| 工具 | 操作外部平台的能力 | 浏览器点击、API调用、数据库查询、发送邮件 |
| 逻辑 | 控制流程走向与状态 | 条件表达式、循环、并行、等待、异常处理、状态机 |
| 适配器 | 连接具体平台/系统 | Shopify适配器、钉钉适配器、企业微信适配器 |
| 数据 | 存储与传递业务信息 | 业务对象、数据表、上下文数据流 |
| 变量 | 存储临时/持久数据 | 全局变量、节点变量、环境变量、秘密变量 |
| 上下文 | 当前运行环境信息 | 用户上下文、会话上下文、系统上下文 |
| 知识 | 提供领域知识与文档 | FAQ知识库、SOP文档、产品手册 |
| 测试/发布 | 验证运营体正确性 | 沙盒测试、回放测试、灰度发布 |
| 运行时 | 实际执行与监控 | Loop引擎、Harness网关、日志中心 |

## #  与整体架构的映射关系
编辑后台的每个组件，都对应到产品底层架构的一个模块：

| 编辑后台组件 | 对应底层模块 |
| --- | --- |
| 节点 → 流程图 | LangGraph StateGraph 的节点和边 |
| 工具 → 适配器 | Harness 层的统一操作接口 |
| 逻辑 → 条件/循环 | Graph 的条件边、循环子图 |
| 变量/上下文 → 状态 | LangGraph State / Checkpointer |
| 知识 → 向量库/图谱 | RAG 检索 + 知识图谱 |
| 测试/发布 → 评估Harness | 借鉴 lm-evaluation-harness 的评估流水线 |
| 运行时监控 → Loop引擎 | OODA 循环 + 反思模块 |
