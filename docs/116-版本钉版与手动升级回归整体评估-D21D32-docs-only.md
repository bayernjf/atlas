## 1. 评估目的

任务清单中「版本钉版＋手动升级回归」（task #93）长期挂 pending。本件从权威文档与代码实证核对：**这条能力链到底还欠不欠工程动作？**

docs/04 §14 对该能力的原始定义是三段：**子图版本钉版 → 手动升级 → 升级后回归测试**。

## 2. 三段能力的落码实证

| 段 | 落码批次 | 状态 |
|---|---|---|
| **子图版本钉版**（发布时递归把 subgraph 引用钉为 `graphId@vN`，版本不可变故钉号即冻结引用） | M6（docs/20 §4.1 / ADR T19，2026-09-17） | ✅ |
| **升级体检**（发布前只读对比「草稿将钉版本 vs 父图最新快照所钉」） | docs/28 批 4⑪（`versioning/upgrades.py` ＋ `GET /api/graphs/{id}/subgraph-upgrades`，2026-09-20） | ✅ |
| **手动升级动作**（把草稿顶层 subgraph 引用显式改写为 `sub_id@to_version` 并存回草稿，不产版本） | 打包 ZU2（docs/104，`apply_subgraph_upgrades` ＋ `POST /api/graphs/{id}/subgraph-upgrades`，2026-10-08） | ✅ |
| **升级后回归**（升级后跑发布门禁确认兼容） | 复用 ReleaseModal 既有「运行门禁」`run_release_gate`（docs/104 §非目标明确不新增回归端点） | ✅ |

**结论：docs/04 §14 的「钉版＋手动升级＋回归」完整闭环已具备，不欠工程动作。**
