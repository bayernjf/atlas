# 96 · 认领后崩溃挂起帧的人工收敛（reconcile）v1 批契约设计（打包 BL）

> **立项 2026-10-06**（承接 docs/73 W3-3.2 与 docs/14 **D36**；docs-only 先行，落码另立原子）。形状权威＝本文；与 docs/62 冲突处以本文为准（docs/62 是 at-most-once 的**选型**契约，本文是它代价条款的**收敛**契约）。

---

## 1. 背景：那颗雷现在"看得见、摸不着"

docs/62 §2 D-1 选了 **at-most-once**：挂起帧（approval／wait）只允许被续跑一次，`claim_frame_for_resume` 用一条 `UPDATE ... WHERE resumed_at IS NULL` 的行锁承担互斥。代价写在 docs/62 §8.1 第②种：

> 进程在**认领之后、下游执行完成之前**崩溃 → 帧已 claimed，任何进程都不再驱动它，该 run 永久停在 `suspended`。宁可永久卡住，也不重复扣款。

打包 Q（docs/76）已让这颗雷**显形**：`GET /api/interruptions` 投影出 `claimed_suspended` 档位（已认领 ∧ run 仍 suspended），但该端点是**只读**的——不重放、不清帧、不改状态。运营查到后**没有任何受契约支持的处理手段**，只能直连数据库。

本批给这颗雷一条**安全的人工收敛出口**，但**不推翻 at-most-once**。

## 2. 为什么不能"自动/重新续跑"

最直觉的做法是"发现 claimed_suspended 就把帧重置、再续跑一次"。本批明确**不做**，理由就是 D-1 本身：

1. 认领点位于"越过挂起点、执行下游之前"。认领后到崩溃之间，下游可能**已经执行了零个、一个或多个节点**——其中可以有真实退款、真实发消息（`create_refund` 是 FINANCIAL 权限）。
2. 帧的 `resume_state` 记录的是**挂起节点**的现场，不记录"崩溃前下游跑到了哪一步"。从挂起点重放＝把已执行的非幂等节点再执行一遍，把"两个进程同时跑"换成"崩溃后隔段时间再跑一遍"，风险同类（docs/62 §2 D-1 原话）。
3. 真正安全的自动重放需要**下游副作用幂等键＋逐节点检查点**，那是多副本/at-least-once 的工程量（docs/62 §8.2、docs/73 W3-3.3），不在单副本 MVP。

故 v1 只给**人工了结（abandon）**，不给重放；运营确认下游状态（钱退没退、消息发没发，这些在监控/审计/外部店铺后台可查）后，显式把这条"事实上已经没有驱动者"的 run 收敛到终态。**重复执行的口子仍然不开**。

## 3. 决策点

- **D-1 v1 只做一个动作：`abandon`（人工了结），不做 resume/retry。** 语义＝运营确认该 run 不再有执行资格，把 run 置终态 `interrupted`（docs/24 §3.3 已定义的"失败档：执行现场不可恢复、不重放副作用"），并删除其挂起帧。不是 `failed`（没有代码异常）、不是 `cancelled`（取消是协作式急停、作用于活 run），`interrupted` 正是为这类"外部中断后不可恢复"准备的状态。
- **D-2 严格前置：只收敛 `claimed_suspended`。** 可操作的唯一条件＝帧 `resumed_at IS NOT NULL` **且** run 当前状态恰为 `suspended`。其余档位一律拒绝：`awaiting`（未认领，重启恢复扫描器仍会驱动它，人工介入会抢跑）409；`claimed_executing`（run 正在 running，可能只是续跑进行中的瞬时态）409；`frame_lingering`（run 已终态、帧残留）不属本批（正常路径由 `PgRunsStore.finish()` 同事务清帧，残留说明有别的 bug，只观测不静默删）；run 不存在/跨租户 404（不泄漏）。
- **D-3 权限＝`administer`。** 这是不可逆的终态改写（把一条 suspended run 判死），不是日常 operate；审计必须记录谁、对哪条 run、认领者是谁、认领多久。viewer/operator 403。
- **D-4 原子性＝一个 PG 事务**：`UPDATE runs SET status='interrupted' ... WHERE id=:run AND tenant_id=:tenant AND status='suspended'` 与 `DELETE FROM interruptions WHERE resume_token=:token AND tenant_id=:tenant AND resumed_at IS NOT NULL` 同一事务提交；任一谓词不命中（状态已变／帧已不在／帧未认领）整体回滚并按 D-2 折算 404/409。**禁止"先查 REST 再改"两步走**（那会重新打开竞态）。
- **D-5 内存档不提供该能力**：内存档不写帧表（`visibility="frames-not-persisted"`），没有跨崩溃帧；端点在内存档返回 409 `INTERRUPTIONS_NOT_PERSISTED`（与只读投影的自报口径一致），不伪造成功。
- **D-6 不做自动扫描/自动收敛/定时器**：不引入后台 reconciler、不按 `claimedSeconds` 阈值自动处置（任何秒数都没人拍过板，docs/76 D-3 同口径）。处置永远是人点按钮触发。

## 4. 形状

### 4.1 REST

```
POST /api/interruptions/{resume_token}/resolve
Body: {"action": "abandon", "reason"?: string ≤500}   # v1 action 仅接受 "abandon"
权限: require("administer")
```

响应（200）：

```json
{"resumeToken": "...", "runId": "...", "resolved": "interrupted", "frameDeleted": true}
```

错误（结构化 `{code,message[,params]}`，经现有异常折算面，zh/en 进 runtime.json）：

| HTTP | code | 触发 |
|---|---|---|
| 404 | `INTERRUPTION_FRAME_NOT_FOUND` | 本租户无此 token 的帧（跨租户同码，不泄漏） |
| 409 | `INTERRUPTION_FRAME_NOT_CLAIMED` | 帧仍 `awaiting`（未认领），重启扫描仍可能驱动 |
| 409 | `INTERRUPTION_RUN_NOT_SUSPENDED` | 帧已认领但 run 不是 `suspended`（running/已终态），params 带 `{status}` |
| 409 | `INTERRUPTIONS_NOT_PERSISTED` | 内存档（帧不持久化，无此能力） |
| 422 | `INTERRUPTION_ACTION_UNSUPPORTED` | action ≠ `abandon`（为未来 resume 预留判别，v1 不实现） |

审计动作：`interruption.resolve`（记录 token、runId、action、reason、claimedBy、claimedAt）。

### 4.2 存储

`storage/recovery.py` 新增 `abandon_claimed_suspended_frame(engine, *, tenant_id, token) -> tuple[str, str] | None`（返回 `(run_id, kind)`；不命中返回 None，由 API 层用**只读预查**折算具体 404/409 码——预查只为给对人看的错误码，**承重的是 D-4 事务谓词**，与 docs/62 "谓词承重、读数只是友好"同构）。`storage/base.py` 的 RunsStore 终态 Literal 已含 `interrupted`，无 Schema 变更、**零迁移**。

### 4.3 前端（Waits 页 frames tab）

- `claimed_suspended` 行新增操作按钮「了结」（其余档位不渲染按钮）；点击弹确认框，明示「该 run 将被标记为 interrupted 且不会重新执行下游；请先在外部系统确认退款/消息状态」，必填或可选备注（reason）。
- 仅 `administer` 角色可见按钮（operate 只读）；成功后刷新列表，该行消失（帧已删）。
- 新 i18n 键落 `waits.json`（zh/en，过 PARITY）：按钮、确认标题/正文、reason 输入占位、成功提示；5 个错误码落 `runtime.json`（zh/en）。

## 5. 测试（docs/13 打包 BL 小节，U1171 起编号）

- **PG 集成（`-m integration`，真库）**：写帧→认领（`claim_frame_for_resume`）→run suspended ⇒ `abandon` 后 run 终态恰为 `interrupted`、挂起列零行、审计有 `interruption.resolve`；同事务断言（手动把 run 改成 running 后调用 ⇒ 409 且帧仍在）。
- 未认领帧 ⇒ 409 `INTERRUPTION_FRAME_NOT_CLAIMED`，帧与 run 都不变。
- run 已终态（claimed＋completed 造 `frame_lingering`）⇒ 409 `INTERRUPTION_RUN_NOT_SUSPENDED`，帧不删（不静默吞残留）。
- 跨租户/未知 token ⇒ 404；viewer/operator ⇒ 403；内存档 ⇒ 409 `INTERRUPTIONS_NOT_PERSISTED`；非法 action ⇒ 422。
- **并发反向门**：两个并发 abandon 调用同一帧，恰一个 200、另一个 404/409（证明事务谓词承重，不靠先查后改）。
- 错误码守护：5 码进 U1162 `http_facing`（zh/en 双份、单答案）；U1149 目录门自动认。
- 前端：Waits frames 表仅 `claimed_suspended`＋admin 渲染按钮；abandon 成功刷新；非 admin 无按钮；确认文案存在。

## 6. 不做（照实）

不做自动/手动 **resume/retry**（D-1，下游非幂等）；不做后台 reconciler 与阈值计时（D-6）；不处理 `frame_lingering` 残留（只观测）；不动 at-most-once 认领协议与 docs/62 任何现有行为；不解锁多副本（D20/D36 的多实例半边仍缓做）；**零新依赖、零迁移、无 ADR**。

## 8. 落码收口注记（2026-10-06）

原子：① 立项 docs（`928be28`）→ ② 落码（`storage/recovery.py`＋`api/main.py`＋前端 Waits/apiClient/两档文案＋测试）→ ③ 收口 docs（本注记）。

- **承重实现**：`abandon_claimed_suspended_frame(engine, *, tenant_id, token) -> (code, info)`，码 `RESOLVE_OK`／`FRAME_NOT_FOUND`／`FRAME_NOT_CLAIMED`／`RUN_NOT_SUSPENDED`。互斥由同一 `engine.begin()` 事务里的两条谓词承担——`UPDATE runs … WHERE status='suspended'`（CTE 先把「本租户＋本 token＋已认领」的帧行 `FOR UPDATE` 锁出）与 `DELETE FROM interruptions … WHERE resumed_at IS NOT NULL`；不命中时**同事务内**只读折算具体码，只读预查不承担互斥（与 docs/62「谓词承重、读数只是友好」同构）。run 置 `interrupted` 时同句清 `kind/node_id/deadline_at/resume_token`，与 `PgRunsStore` 终态写入口径一致。
- **端点**：`POST /api/interruptions/{resume_token}/resolve`，`require("administer")`；内存档 409 `INTERRUPTIONS_NOT_PERSISTED`；`action != "abandon"` 422 `INTERRUPTION_ACTION_UNSUPPORTED`。
- **前端**：Waits frames tab 仅 `claimed_suspended` ＋ `administer` 渲染「了结」按钮，确认框明示"不会重新执行下游、请先核实退款/消息"＋ reason（≤500）；`waits.json` zh/en 过 PARITY，5 个错误码进 `runtime.json`。
- **用例**：U1171–U1175（常跑，`tests/test_api_interruptions.py`）＋ U1176–U1179（PG 集成，`tests/test_interruptions_pg_integration.py`），含 §5 要求的**并发反向门**（两个并发 abandon 恰一个 200）与审计行断言。

**一处与契约的偏差（照实）**：§4.1 写审计要「记录 token、runId、action、reason、claimedBy、claimedAt」，但 `audit_events`（迁移 013）只有 `tenant_id/id/seq/actor/action/status_code/path/ip/at` 九列、**没有 detail 列**，加列＝迁移，与本批「零迁移」冲突。实际落到的：**token 在 `path`**（URL 自带）、`actor`／`action`／`status_code`／`at`／`ip` 齐全；**runId／reason／claimedBy／claimedAt 不入审计行**。其中 claimedBy／claimedAt 在**处置前**可由 `GET /api/interruptions` 投影读到（docs/76），处置后随帧删除消失。补全须给审计表加列（新迁移），**留作后续决策，不在本批**。

**明确未做（与 §6 一致）**：不做 resume/retry；不做后台 reconciler 与阈值计时；不处理 `frame_lingering`；不动 at-most-once 认领协议；不解锁多副本（D20 的多实例半边仍缓做）。零新依赖／零迁移／无 ADR。
