# 首启就绪竞态有界重试批（打包 S）v1 批契约设计

> **立项 2026-09-28**：起因＝ [docs/73](73-自主上线MVP缺口清单追踪.md) 明细项 **4.2**——[docs/77](77-项目级上线复审-2026-09-27第六次.md) §8 在 prod＋空卷第一次真跑时量出的**首启就绪竞态**。用户拍板**口径 (a)：应用与迁移各自加有界重试**（不依赖 compose 重启策略、**不改探针**、compose 的 healthcheck 一行不动，`restart: unless-stopped` 保留作兜底）。形状权威＝本文；与 01–08 冲突以规格文档为准，落码偏差在收口注记回填。
>
> **一句话**：空卷首启时 PG 在 initdb 之后有一段约 **90s** 的 recovery 窗口，其间一切连接被 `FATAL: the database system is in recovery mode` 拒绝；而 compose 给 `db` 的探针是 `pg_isready`，**在这段窗口里判过了 healthy** ⇒ atlas 被 `depends_on: service_healthy` 放行 ⇒ 入口脚本的 `python -m scripts.ops.apply_migrations`（`set -e`）连库即抛、容器退出，**靠 `restart: unless-stopped` 第二次才起来**。本批让迁移与应用启动各自**有界等待**连通性，使"一次就到 ready"不再依赖重启策略。

## 1. 决策（六条，改任何一条先改本文）

- **D-1 口径＝(a) 有界重试：不动探针、不动 compose**。`db` 的 healthcheck（`pg_isready`）、`depends_on: service_healthy`、`restart: unless-stopped` **一行不改**。用户否掉 (b)（把探针换成 `SELECT pg_is_in_recovery()`）——探针改成 SQL 会把"能不能连"与"是不是主库/恢复中"两种语义混在一起、且 PG 版本行为差异要另算；而应用侧的有界重试是**无论哪种原因导致连不上都成立**的收敛做法。`restart` 保留作**兜底**，不再是首启路径的依赖。
- **D-2 只重试连通性类错误，真错误立即失败**。可重试＝ SQLAlchemy `OperationalError` / `InterfaceError` **且**消息命中冷启/恢复/连接类标记（`recovery mode` / `starting up` / `connection refused` / `could not connect` / `connection failed` / `connection reset` / `server closed the connection` / `terminating connection`）。**SQL 语法、约束冲突、权限、认证失败等一律不重试**（它们是 `ProgrammingError` 等，立即原样抛出）——重试一个语法错误只会把失败延后到预算耗尽，还会掩盖真缺陷。
- **D-3 有界预算＋固定间隔**：总预算缺省 **120s**、间隔缺省 **2s**，可用 `ATLAS_DB_READY_TIMEOUT_SECONDS` / `ATLAS_DB_READY_INTERVAL_SECONDS` 覆盖。120s 覆盖实测 **90.21s** 窗口并留余量；**必须是有界的**——试到预算耗尽仍不通就拋最后一次异常，绝不无限等。非数字/负值 env 回退缺省（与仓库既有容错口径一致）。
- **D-4 两处接入点按各自的既有失败语义分档**：
  - **迁移 CLI（`scripts/ops/apply_migrations.py`）＝ fail-closed 不变**：预算耗尽仍抛 ⇒ 非零码退出（容器退出，`restart` 兜底仍是最后一层）。**重试的是整个 `apply_pending`**，不是一次预检 `ping`——连接可能在任何一次 `engine.begin()` 上失败，而 `apply_pending` 每次入口都重算 `applied_versions`、每个迁移文件在单事务内执行，已应用的会被跳过，故重试是幂等安全的。
  - **应用 lifespan ＝不阻断启动（保住既有语义）**：在 `recover_pending()` 之前先做一次有界连通性等待；成功 ⇒ 继续（恢复扫描与 retention 因此**不再被静默跳过**）；预算耗尽 ⇒ **记 warning 后继续**（与 `recover_pending` / `run_retention_once` 今天"清扫绝不挡服务起"的语义一致；`/api/ready` 仍对 PG 做真 `SELECT 1` 并返 503）。**理由**：app 的失败语义今天就是"不阻断"，本批不趁机改它；首启路径上迁移已先 fail-closed，lifespan 这一层是防"扫描被静默跳过"的降级，不是新的硬失败点。
- **D-5 零新依赖、零迁移、零新端点、零新错误码、无新 ADR**。只用 `time` ＋ 既有 SQLAlchemy 异常类型 ＋ logger；新增两个 env 名（**非 ADR 级**，1/3 文档不涉及选型变更）。
- **D-6 不改的东西**：不动 `ping()` 的返回契约（仍返回 `True`，重试复用它作探针）；不动 `apply_pending` / `ensure_schema_migrations` 的签名与事务语义；不动 compose（见 D-1）；不解除任何缓做项与单副本三道闸；前端零改动。

## 2. 形状

- `src/atlas/memory/database.py`（新函数，与既有 `ping` 同处）：
  - `CONNECTIVITY_RETRY_MARKERS: tuple[str, ...]`；
  - `is_retryable_connectivity_error(exc: BaseException) -> bool`；
  - `wait_for_database(operation, *, timeout_seconds=None, interval_seconds=None, logger=None)`：在自己的有界窗口内重复调用 `operation()`；每次可重试失败记一条 **warning**（含已等秒数、尝试次数、下次间隔）；成功且等待 >0 时记一条 **info**（含等待时长，即"成功打等待时长"）；预算耗尽 ⇒ **原样抛出最后一次异常**；非可重试异常 ⇒ 立即原样抛出。返回 `operation()` 的返回值（迁移 CLI 取回 `processed`）。
  - `database_ready_timeout_seconds()` / `database_ready_interval_seconds()`：读 env、非数字/负值回退缺省的纯函数。
- `scripts/ops/apply_migrations.py`：`processed = wait_for_database(lambda: apply_pending(engine, default_migrations_dir(), mark_existing=args.mark_existing))`。
- `src/atlas/api/main.py`：新增模块级 `_wait_for_database_ready()`（仅 `STORAGE_BACKEND == "pg"` 生效，吞异常 warning）；`lifespan` 在 `recover_pending()` **之前**调用它。
- 新测试 `tests/test_db_connect_retry.py`（U944–U950）。
- `.env.example`：新增两个变量与说明（与代码实际读取一致）。

## 6. 残余风险（写清楚，别当成"4.2 收干净了"）

1. **compose 探针仍是 `pg_isready`（D-1 有意如此）**：若有一天应用侧的重试被移除或预算被调小，竞态会重新出现。守护在 U944/U948——它们锁的是"重试确实接在两处入口"。
2. **`restart: unless-stopped` 仍是最后一层**：预算耗尽时迁移仍 fail-closed，容器仍会退出并由 restart 兜底。本批**降低了**对它的依赖，不是**移除**它。
3. **应用侧预算耗尽只 warning 不阻断（D-4）**：极端情况下（PG >120s 不可达）应用仍会起、`/api/ready` 返 503、恢复扫描与 retention 被跳过——与今天同形，不是本批引入的降级，但也未被本批关闭。
4. **D-2 的可重试集合基于消息子串**：这是对 psycopg/libpq 文案的工程化近似，不是协议级判定。误判方向是安全的——**把不该重试的当可重试**只是延后到预算耗尽才失败（仍有界、仍 fail-closed）；把该重试的当不可重试则会立即失败（由 U947 的正反例钉住常见文案）。
5. **未验的边界**：本批只覆盖"迁移 CLI＋应用启动钩子"两处；`/api/ready` 的探针语义、调度线程首轮评估、以及运行期任何一次临时断连都不在有界重试范围内（它们各自有既有语义）。

### 7.1 真机 〔跑〕 证据：prod＋空卷首启一次到 ready

- **做法**：`docker compose -p s79 --env-file <一次性随机密钥文件> up -d --build`，**project 命名空间隔离**（自己的卷 `s79_atlas-pgdata`，收尾 `down -v` 后核对为 `Removed`；机器上另一套 `atlas_atlas-pgdata` 卷与 `atlas-db-1`／`ja-pg-repro`／`zeus-b1` 容器全程未触碰）。镜像重建（build 494s，含依赖层）以带上本批代码。
- **结果**：`up -d` 后 **`GET /api/ready` 在 T+9s 返 200**；`docker inspect` ＝ atlas `RestartCount=0 Status=running`、db `RestartCount=0 Status=running`（**未靠 `restart` 兜底**）；容器日志逐条 `applied 001…030`（30 条迁移全过）、`[entrypoint] ATLAS_ENV=prod：跳过种子账号播种`、`Started server process`、`/api/ready 200 OK`。⇒ Done-when ①「一次就到 ready、不依赖重启策略兜底」与 ②「新卷首启计时」两问均有实跑落点。
- **但本次没触发竞态，照实说**：迁移与启动都是**首连即成功**（日志 `数据库连通性恢复：等待 0.0s、尝试 1 次后成功`），即本批的重试**没有被用到**。原因是当时机器 load ≈ 4.4（对比 docs/77 §8 那次 **385／427／393**），空卷 PG 起得很快。**故 7.1 是"首启正向路径 + 零重启"的证据，不是"重试救了它"的证据**；后者由下一节的窗口观测与判别器验证补。

### 7.2 竞态窗口与消息形态的直接观测〔跑〕

- **做法**：`docker run --rm --network s79_default --entrypoint python atlas-demo:latest -c "…psycopg 连 db:5432…"`——绕开 entrypoint，直连**刚建的空卷 PG**，每秒探一次、打印异常原文。
- **结果**：`+0.00s OperationalError: connection failed: connection to server at "172.22.0.2", port 5432 failed: Connection refused`、`+1.01s OK`。⇒ 本机这副卷＋低负载下启动窗口只有约 **1s**（docs/77 的 90.21s 是失控负载下 fsync 的时长，不是常数）；**真实 libpq／psycopg 消息形态已量到**：`OperationalError` ＋ `connection failed: … Connection refused`，与 `CONNECTIVITY_RETRY_MARKERS`（`connection failed`／`connection refused`）吻合。
- **判别器对真异常的验证**（`.venv/bin/python`，**走 SQLAlchemy 引擎、与 app 同路径**）：对一个被拒的连接，异常为 `sqlalchemy.exc.OperationalError`，`is_retryable_connectivity_error(e) == True`。
- **一个容易踩的坑（记下来免得下一位误判）**：直接用 **`psycopg.connect`** 抛的是 psycopg 自己的 `OperationalError`（**不继承** SQLAlchemy 的），本判别器会判 `False`——这不是缺陷，而是 D-2 有意只认 SQLAlchemy 的 `OperationalError`／`InterfaceError`；app 侧一律经 SQLAlchemy 引擎，故生产路径不受影响。**这也说明为什么 U947 的判别对照不可省**。

### 7.3 未做／边界照实

- **未在失控负载下重演 docs/77 的 90s 窗口**：本批只证明"窗口存在、真实消息可被判别、重试接在两处入口、首启零重启"；把窗口拉长到分钟级需要造负载，本机不值得（也怕扰动同机其它容器）。
- **compose 一行未动**（D-1／D-6）：`pg_isready` 探针与 `restart: unless-stopped` 原样保留，即 §6 第 1、2 条残余风险照旧成立——本批是**降低**对兜底的依赖，不是移除。
