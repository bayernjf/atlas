## 0. 已核实缺陷（〔码〕＋〔跑〕）

- `graph/loader.py` 的工具路由只把 `{http, database, message, memory}` 与 `openapi:` 前缀送进**通用 JSON 参数通道**；渠道适配器的 id 是 `channel:shopify:<bindingId>`（`channels/adapter.py:63`），于是落进**demo shop 的按能力硬编码装配**（原 `:1729-1754`）。
- 该装配只认识 `process_refund`/`execute_refund`/`request_human_approval`/`login`/`list_pending_refunds`，`create_refund` 落进 `else: parameters["note"] = params_text`。
- 真适配器随后取 `params["order_id"]`/`params["amount"]`（`channels/adapter.py:110-114`）⇒ KeyError ⇒ 被 catch 成 `CHANNEL_INVALID_PARAMETER` ⇒ **节点必失败，图里无法执行真实 Shopify 退款**。
- 测试面同证：全仓 `channel:shopify` 只出现在 `tests/test_api_channels.py:148/153` 的"能否被发现"断言里，**没有一条把图跑到过它**〔跑〕。

## 1. 决策与形状（一句话：让 `channel:` 走通用通道，别再造第二套装配）

`_execute_tool` 的前缀判断从 `startswith("openapi:")` 改为 `startswith(("openapi:", "channel:"))`（`loader.py:1701`，全仓**仅此一处**路由门〔跑〕）。

**为什么不选另两种**：
- 给渠道适配器再写一段按能力硬编码装配＝第三套参数装配，且每加一个渠道就要再写一遍；
- 让渠道适配器自己解析 `note` 字符串＝把 JSON 契约下沉到每个适配器，破坏"params 是 JSON 对象"这一条已在 docs/04 §4.6-4.9 定死的约定。

**为什么语义正确**：渠道能力的 `input_schema` 本来就是对象形状（`_REFUND_INPUT` 要求 `order_id`/`amount`），通用通道的"插值后必须是 JSON 对象并整体透传"与之天然一致；`_tool_input_schemas`/`_tool_output_schemas`/`_tool_permissions` 三张编译期表都按 `registry.list_adapters()` 通用遍历，**渠道适配器一直在里面**，只是运行期路由没认它。

**顺带保持不变的**：`GENERIC_JSON_ADAPTERS` 仍是四个精确 id 的 frozenset（渠道 id 带 binding 后缀，只能按前缀判，不能塞进集合）；demo `shop` 适配器继续走硬编码装配（它的 `process_refund` 需要上游 AI 决策与 trigger 载荷，形状不同）；影子模式短路点、`INVALID_PARAMETER` 判定顺序均不改。

## 4. 残余风险

1. **`amount` 仍是字符串/数字两可的外部输入**：通用通道透传后由真客户端格式化 `"299.00"`；若图里写成 `"amount": "299"`（字符串），当前会走到客户端内部转换或失败——本批不加新校验，留给真实客户数据暴露后再定（避免凭想象收紧）。
2. **部分退款仍不支持**：`create_refund` 的 `full_refund:false` 路径按行项目分摊，客户端里是既有实现；本批只接通"能带着正确参数到达"，不验证分摊策略。
3. **未做真机 Shopify 冒烟**：需要一个真实店铺凭据（docs/08 D 组外部资源），因此 N2 的关闭证据是"真适配器＋真客户端＋假 HTTP"，不是"真 Shopify 返回 200"。诚实边界写在这里。
4. **N3（`web-playwright` 未接入运行期）与 N4（定时触发无调度器）本批不做**：N3 动的是 PRD 范围（要么接浏览器自动化、要么把它移出 MVP 口径），属产品决策；N4 要引调度器与并发语义。
