## 第六部分：运行时引擎设计
### 6.1 Loop 主循环实现
基于 LangGraph StateGraph 构建持久运行的状态机（代码示例）：
class LoopState(TypedDict):
goal: str
messages: list          # 对话/执行历史
current_node: str
observations: list      # 感知结果
variables: dict         # 会话变量
status: str             # running/paused/completed/error
memory_id: str
# 构建主循环
graph = StateGraph(LoopState)
graph.add_node("observe", observe_node)      # 调用Harness感知当前状态
graph.add_node("orient", orient_node)        # 分析数据，定位进展
graph.add_node("decide", decide_node)        # LLM决策下一步
graph.add_node("act", act_node)              # 执行工具/操作
graph.add_node("reflect", reflect_node)      # 阶段性反思
graph.add_edge("observe", "orient")
graph.add_conditional_edges("orient", should_continue)
graph.add_conditional_edges("decide", should_act_or_wait)
graph.add_conditional_edges("act", should_reflect_or_continue)
```

> **Graph condition 节点执行语义（Phase 2 首版，2026-09-14；契约权威见 04 §5.2）**：编辑后台 Graph 中的 condition 节点编译为 LangGraph conditional edges——同一 condition 节点的出边**全部**走 `add_conditional_edges`（不得与普通边混用，否则双路激活）。执行器按 config.branches 数组顺序短路求值（第一个为真者胜出），全假或求值异常时走 defaultTarget；求值只发生一次并写入 `outputs[condition_id]`，路由函数仅读取其中的 `target`。含变量的运行时类型错误/缺失变量 fail-safe 走 defaultTarget，错误进 `expression_errors`；trace（messages）追加一行 `condition-x: branch=<label|__default__> → target=<node_id>`。表达式首版白名单（比较/逻辑/括号/字面量/`{{路径}}`，无算术与函数、禁止 eval）见 04 §5.1。

> **Graph loop 节点执行语义（Phase 2 第二项，2026-09-14；契约权威见 04 §5.3）**：v1 仅条件循环（while）。loop 节点的两条出边（bodyTarget/exitTarget）全部走 `add_conditional_edges`，router 只读 `outputs[loop_id]["target"]`；循环体末端以**普通回边**连回 loop 节点，形成 LangGraph 原生环（回边白名单由 dsl 静态校验保证，非法环保存时拒绝，见 13 U7）。执行器可重入：每次进入读取自身上次产出的 `iterations`，达 `maxIterations` 或表达式求值异常时 **fail-safe 路由 exitTarget**（exitReason 分别为 `max_iterations`/`expression_error`，运行整体仍 completed），表达式为真则计数加一路由 bodyTarget，为假路由 exitTarget（`condition_false`）。循环体节点经 `{{loop-x.index}}` 引用当前 1-based 轮次。LangGraph 默认 recursion_limit=25 会中断循环，`run_graph` 按 `2*节点总数 + 2*maxIterations*(循环体节点数+1) + 10` 派生并经 `invoke(..., config={"recursion_limit": n})` 传入。trace 行：`loop-x: continue (i/max) → body` / `loop-x: exit (reason) after N → exit`。遍历循环与 break/continue 缓做（14 登记表 D16/D17）。

> **Graph parallel 节点执行语义（Phase 2 第三项，2026-09-14；契约权威见 04 §5.4）**：v1 静态扇出/扇入，合并策略仅 `all_success`/`all_completed`（any_success 真 OR-join 需取消其他分支，缓做 14 D18；动态 map-reduce 不做）。parallel 节点的 N 条出边全部走 `add_conditional_edges`，router 返回**分支目标列表**（`list[str]`）实现同超步静态扇出；分支末端全部汇聚到 config.joinTarget——**编译期注入合成网关节点 `__join__<parallel-id>` 做汇聚屏障**（spike 实测 LangGraph 对普通静态多入边不做 barrier、不会等待全部前驱）：分支末端 retarget 到网关，网关每超步检查各分支末端产出，未齐则空 messages 自我循环等待，齐后聚合一次再路由真 joinTarget，joinTarget **只执行一次**（不等长分支亦成立）；`__join__` 事件不外泄，汇聚完成以 parallel 节点自身补发第二次 node_end。支撑并发写的横切变更：`GraphState.outputs` 由无 reducer 的 LastValue 通道改为 `Annotated[dict, _merge_outputs]` **按键合并**通道，各执行器只返回自己的分片 `{"outputs": {node_id: output}}`（同 key 后者覆盖）；`messages` 仍为 `operator.add`，`status` 为 last-write。扇出不增加递归深度，recursion_limit 公式不变。分支成败判定：该分支路径上任一节点产出出现 `result.status == "FAILED"` 即失败（工具失败只写 FAILED 不抛错）。**fail-safe 汇聚**：all_success 下即便有分支 FAILED，joinTarget 照常执行、parallel 产出 `status="failed"` 与逐分支错误、运行整体仍 completed；下游可用 condition 判 `{{parallel-x.status}}`。聚合产出（写入 `outputs[parallel_id]`，入口先写 running 占位、汇聚时覆盖为终态）形状与 trace（`parallel-x: fork N branches → a, b` / `parallel-x: joined (all_success) success` / `… failed: <label>（<error>）`）见 04 §5.4、12 文档。

> **Graph wait 节点执行语义（Phase 2 第四项，2026-09-14；契约权威见 04 §5.5）**：v1 仅定时等待（`waitType:"duration"`，`durationSeconds` 为 1-600 整数常量，不支持变量/表达式动态时长）。执行器在发出 node_start 后同步 `time.sleep(durationSeconds)` 阻塞，到时发 node_end，沿唯一普通边继续（不经 conditional 边、不增加递归深度）。SSE 同步流生成器运行于 Starlette 线程池工作线程，阻塞不卡事件循环但占用一个工作线程，故上限 600 秒；等待不失败、不重试。节点产出 `{mode:"wait", waitType:"duration", durationSeconds}`（可经 `{{wait-x.durationSeconds}}` 引用），trace 行 `wait-x: waited 5s`。事件等待（挂起等外部信号/回调，需 LangGraph interrupt/checkpointer 与持久化）缓做 14 D19。

> **Graph human_approval 节点执行语义（Phase 2 第五项，2026-09-14；契约权威见 04 §5.6）**：v1 为**进程内审批信号**——执行器在 `atlas.collaboration.approvals.ApprovalBroker` 登记 pending 请求（uuid4 token + `threading.Event`），node_start 事件 data 携带 `approval:{token, summary, approver, timeoutSeconds}`，随后阻塞等待，决策到达后发 node_end 并以 `add_conditional_edges` 按 `outputs[id].target` 路由（双出口，同 condition/loop 路由族；不增加递归深度）。决策三来源：① `POST /api/approvals/{token}/decision` 人工放行（resolvedBy="human"，首决生效、重复提交 409）；② run inputs 预置 `{"approvals":{"<node-id>":"approved"|"rejected"}}` 秒过（resolvedBy="input"，非交互/测试）；③ 等待满 `timeoutSeconds`（10-3600 整数）按 `onTimeout`（approve|reject，默认 reject）自动决策（resolvedBy="timeout"），运行仍 completed。阻塞发生在 Starlette 线程池工作线程，故 `/run/stream` 必须**真流式**（后台线程跑 run_graph、事件经 queue 实时下发；旧的「跑完再回放」实现会在审批节点死锁）。broker 为进程内单例、重启即失、不支持跨实例；真正的 interrupt/checkpointer 中断-恢复、多实例、IM 通知、动态审批人/鉴权缓做 14 D20。节点产出 `{mode:"human_approval", decision, target, token, summary, approver, resolvedBy}`，trace 行 `human-x: approved (human) → tool-refund`。

> **Graph subgraph 节点执行语义（Phase 2 第六项，2026-09-14；契约权威见 04 §5.7）**：v1 为**进程内引用式**——执行器按 config.graphId 经注入的 `graph_resolver`（Demo 为 GraphStore.get）取得子图 GraphDSL，把 config.inputs 各值用父图上下文渲染后作为子图 run inputs，**同进程重入 `run_graph`** 整体执行子图：子图 trigger `context.payload` 接收映射入参（语义同 webhook 载荷），复用父图同一套适配器注册表、决策客户端与审批 broker。编译期跨图校验由 `compile_graph(graph_resolver=...)` 递归完成：graphId 必须可解析，禁直接自引用与跨图引用环，**嵌套深度上限 3**（对齐 07 §8 递归深度护栏），被引用图递归过完整图校验。子图执行传 `emit=None`——子图内部 node/run 事件不外泄父图 SSE（避免子图节点 id 污染画布状态），子图 trace 完整收入节点产出。子图阻塞于 Starlette 线程池工作线程（同 wait/human_approval），不产生父图超步、父图 recursion_limit 公式不变（子图 invoke 有独立限额，深度参数随重入传递）。**fail-safe**：子图解析/编译/运行期任何异常均捕获为节点产出 `status:"failed"`+error，父 run 仍 completed、沿唯一普通出边继续（不做成功/失败双出口），下游可用 condition 判 `{{subgraph-x.status}}`。子图内含 human_approval 时审批 REST 端点可用，但因子图 node_start 不外泄，Demo v1 子图审批只能靠 inputs 预置或超时自动决策。节点产出 `{mode:"subgraph", graphId, status, error?, outputs:<子图 outputs>, trace}`，trace 行 `subgraph-x: graph-7 success (N nodes)` / `… failed: <error>`。版本钉版/手动升级回归、子图市场/共享、远程运营体引用缓做 14 D21。
### 6.2 决策节点实现（代码示例）
def decide_node(state: LoopState):
# 1. 从记忆中检索相关上下文
relevant_memory = memory_retriever.query(state.goal, state.messages[-5:])
# 2. 构建提示词（含思考缓冲区）
prompt = f"""
【目标】{state.goal}
【当前状态】{state.messages[-10:]}
【相关记忆】{relevant_memory}

请先进行内部推理（思考：
1. 当前进展如何？
2. 下一步应该做什么？
3. 有什么风险？
然后输出结构化决策。
# 3. 调用LLM，强制结构化输出
decision = llm.with_structured_output(DecisionSchema).invoke(prompt)

# 4. 置信度检查
if decision.confidence < 0.6:
return {"status": "paused", "request_human": True, ...}

return {"current_node": decision.next_action, ...}

### 6.4 Harness Gateway（代码示例）
type HarnessAdapter interface {
ListCapabilities(ctx context.Context) ([]Capability, error)
Execute(ctx context.Context, req ActionRequest) (ActionResult, error)
Observe(ctx context.Context, req ObserveRequest) (Observation, error)
}
type ActionRequest struct {
CapabilityName string
Parameters     map[string]interface{}
Context        map[string]interface{}
Timeout        time.Duration
}
type ActionResult struct {
Status     string          // SUCCESS / PARTIAL / FAILED
Output     interface{}

}
### 6.5 Web 操作适配器（Demo 核心）
三层定位冗余：（代码示例）
class WebHarnessAdapter:
def click(self, element_desc: str, selector: str = None):
# 第一层：精确选择器
if selector:
try:
self.page.click(selector, timeout=3000)
return success()
except:
pass

# 第二层：视觉语义定位
screenshot = self.page.screenshot()
elements = omni_parser.parse(screenshot)  # 返回元素列表+描述
target = llm_match(element_desc, elements)
if target.confidence > 0.7:
self.page.mouse.click(target.x, target.y)
self.update_selector_cache(element_desc, target.selector)
return success()

# 第三层：LLM全图推理
result = vision_llm.analyze(screenshot, f"找到{element_desc}并返回坐标")
if result.coordinates:
self.page.mouse.click(*result.coordinates)
return success()

return failed("元素未找到，三层定位均失败")
