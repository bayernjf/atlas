## 3. 批 2：D26 影子模式（线上旁路录制，进程内 v1）

### 3.1 语义

契约依据：docs/04 §补充10「可配置运营体以『仅记录不执行』模式运行，与实际人工操作并行对比」（愿景级一句，详细契约由本文档定稿）。

一次影子运行＝对同一输入旁路跑完整决策链路并记录「系统本会怎么做」，但：

- **读透传、写短路**：READ 能力照常执行（沙盘里即模拟 shop 读，不改状态）；WRITE/DELETE/FINANCIAL 能力不触达适配器，返回意图回执；
- **不弹审批**：human_approval 节点由 API 层预置 approved 秒过（现有 `inputs.approvals` 机制，零 loader 行为改动），「本应请求审批」作为意图记录；
- **不进生产观测面**：不写 run_store/RunRecord、不触发告警与灰度门控、不产生 tool_metric 监控样本；
- 影子运行有独立 tracer（trace_id 记入影子记录），但 span 树不落 RunRecord（无 RunRecord 可挂），v1 不提供影子 trace 钻取。

### 3.2 引擎改动（graph/loader.py）

- `run_graph`/`compile_graph`/`_make_executor`/`_execute_tool`/`_execute_subgraph` 全链新增内部参数 `shadow: bool = False`（透传方式照 tool_mocks 闭包链；**与 tool_mocks 不同，子图重入透传 shadow**——影子是运行级语义，子图内写能力同样必须短路）。
- `compile_graph` 编译期建 `tool_permissions: dict[str, str]`（键 `adapter/capability`，值 permission 字符串；照 `_tool_output_schemas` 遍历 `registry.list_adapters()`），随执行器闭包透传。
- `_execute_tool` 在 registry 解析成功后、`adapter.execute` 前插入 shadow 分支：
  - SIMULATED（无 `/` 或 registry None）：照常（本就无外部副作用）；
  - `shadow and permission != "read"`：返回
    `{"result": {"status": "SHADOW_DRY_RUN", "tool": tool_name, "capability": capability_name, "permission": <permission>, "parameters": <最终参数 dict 或渲染串>}, "action_status": "SHADOW_DRY_RUN"}`；
    专用通道（shop）parameters 构造逻辑前移到短路点之前（process_refund 的 decision 参数、order_id/note 照常组装后被回执截获）；GENERIC_JSON 通道 parameters 为解析后 JSON 对象；
  - `shadow and permission == "read"`：透传执行，节点输出与正常运行同形。
- shadow 运行的 node_end 事件照常 emit（API 层据此收集决策与意图）；tool 节点三出口 monotonic 计时/tool_metric 事件在 shadow 下**不发**（API 层不挂 metric 收集器即可，引擎不特殊处理；若引擎内 metric emit 无条件发出，则 shadow 短路分支不发 metric——落码时以实测 emit 位置为准，原则＝影子零监控污染）。

### 3.3 影子记录模型（新模块 recording/shadow.py）

```
ToolIntent:
  node_id: str
  tool: str                 # adapter/capability；SIMULATED 为裸工具名
  permission: str | None    # read/write/delete/financial；SIMULATED 为 None
  dry_run: bool             # True＝写能力被短路；False＝READ 透传
  parameters: dict | str | None   # 脱敏后参数（v1 沙盘无密钥，原样记录；密钥脱敏随 D22）
  action_status: str        # SHADOW_DRY_RUN / SUCCESS / FAILED / SIMULATED
ShadowDecision:
  node_id: str
  node_type: str            # condition/human_approval/loop
  target: str | None        # 路由产出
HumanOutcome:               # 人工实际处理（创建时可带，或事后补录）
  action: str               # refunded | human_review | 其他自定义动作串
  note: str | None
ShadowRun:
  id: str                   # sr-N，租户级单调计数
  graph_id: str
  inputs: dict | None
  status: str               # completed | error
  error: str | None
  decisions: list[ShadowDecision]
  tool_intents: list[ToolIntent]
  trace_id: str
  auto_action: str | None   # 纯函数推断，见下
  human_outcome: HumanOutcome | None
  comparison: {match: bool | None, auto_action: str | None, human_action: str | None, diffs: list[str]}
  created_at: str           # UTC ISO
```

- `infer_auto_action(tool_intents, decisions) -> str | None`（纯函数）：写意图中命中 `shop/process_refund|execute_refund`（或 parameters.action ∈ refund 类）→ `refunded`；命中 `shop/request_human_approval`（或 parameters.action=human_review）→ `human_review`；都没有 → None。
- `compare_shadow(run, human_outcome) -> comparison`（纯函数）：human_action 归一（去空格小写映射），auto 存在且相等 match=true 并 diffs=[]；auto 存在不等 match=false 并 diffs 记一条；auto 为 None match=null（无法判定，diffs 说明）。
- `ShadowStore`：ring 100/租户、单锁、`add/get/list(graph_id?,limit?)/attach_outcome(sid, outcome)/reset`；挂 `TenantServices.shadow_store`（**memory/PG 两档均挂进程内实例**，照 report_store），`reset_tenant` 加 `shadow_store.reset()`（resettable，用例不涉及）。

## 4. 批 3：D28 Trace 时间线钻取（M10 span 持久化 + 瀑布）

### 4.1 后端

- `monitoring/records.py`：`RunRecord` 增 `spans: dict | None = None`（纯超集；存 `tracer.to_tree()` 根 dict，形状即 `Span.to_dict`：traceId/spanId/name/kind/startedAt/durationMs/status/children…）；`record_run(...)` 增同名参数；内存档 ring 直存。
- 两个真实运行入口（api/main.py）五个 `record_run` 调用点传 spans：

## 5. 批 4：D28 告警静默 / 未确认升级 / 值班轮换（进程内 v1）

### 5.1 静默（silences）

- 模型（monitoring/alerts.py 内或新 monitoring/silences.py，落码时定；存储并入 MonitoringStore 单锁）：

### 5.2 未确认升级（escalation，惰性）

- `RuleConfig` 增纯超集 `escalation_ack_minutes: int | None = None`（None/缺省＝关闭；范围 1–10080 分钟；规则 PUT 已存在，config JSONB 自动兼容无 DDL）。

### 5.3 值班轮换（on-call，手动）

## 10. 风险与注意

1. **影子短路参数构造顺序**：shop 专用通道 process_refund 参数依赖上游 decision，短路点必须在参数组装之后、execute 之前；GENERIC_JSON 通道 params JSON 解析失败语义在 shadow 下保持原样（返 INVALID_PARAMETER FAILED，不伪造 dry-run）。
2. **影子零污染是硬语义**：评审/测试必须断言影子运行后 RunRecord 数不增、告警不增、灰度门控不触发、DemoShopService 待处理列表不变、approval broker 无 pending；任一被污染即缺陷。
3. **http/request 保守短路**：permission 声明为 WRITE，影子下 HTTP GET 也不会发出——v1 宁可漏旁路读取不可漏真实写外呼；动作分级（D22）落地后再细化。
4. **惰性升级的重启语义**：PG 档 escalated_at 不持久化，重启后 open warning 重新按 first_seen 评估（幂等升级，不重复通知因 v1 无通知）；assignee 同理读回 null。
5. **spans 体积**：单运行 span 树为节点数线性、环回/并行有限，ring 200 内存可接受；列表端点务必剔除 spans，前端懒加载；PG JSONB 无索引需求（v1 按行读）。
6. **i18n 零视觉差异**：中文值必须逐字搬迁（含标点/空格/全角），插值重构时保持拼接结果不变；浏览器截图逐页比对；动态英文枚举（status/severity/rule id）不 key 化。
7. **Monitoring.tsx 单文件已 811 行**：批 3/4 UI 新增优先放独立组件（TraceWaterfall、SilenceManager、OnCallBar），页面文件只做挂载与数据装配，避免继续膨胀。
