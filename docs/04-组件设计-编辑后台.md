# 编辑后台组件设计（Atlas）

## 一、编辑后台的核心定位与通用化原则
编辑后台的本质： 它是一个低代码/无代码的“运营智能体工厂”，让用户把自己平台的页面、API、文档、SOP、客服话术等，配置成一个可自主运行、可自我进化的 AI 运营体。
要完全通用化，必须满足以下原则：
1. Schema 驱动：所有节点、工具、逻辑、变量都用结构化 Schema 描述，而不是硬编码。
1. 插件化与热插拔：适配器、节点类型、逻辑组件可以动态注册和卸载。
1. 声明式配置：用户只需声明“要做什么”，不需要写代码；系统自动生成可执行的 Graph 和 Loop。
1. 可组合性：任意节点/子图可以像乐高一样被组合、嵌套、复用。
1. 可观测与可审计：每一步操作、每一次决策、每一个变量变化都可追踪、可回放。
1. 人机协同默认开启：所有高风险操作默认需要人工确认，用户可以逐步“授权”给 AI。
## 二、编辑后台组件全景图

| 组件类别 | 核心作用 | 典型实例 |
| --- | --- | --- |
| 节点 | 执行单元，组成流程图 | 触发器、AI决策、工具调用、条件分支、循环、子图 |
| 工具 | 操作外部平台的能力 | 浏览器点击、API调用、数据库查询、发送邮件 |
| 逻辑 | 控制流程走向与状态 | 条件表达式、循环、并行、等待、异常处理、状态机 |
| 适配器 | 连接具体平台/系统 | Shopify适配器、钉钉适配器、企业微信适配器 |
| 数据 | 存储与传递业务信息 | 业务对象、数据表、上下文数据流 |
| 变量 | 存储临时/持久数据 | 全局变量、节点变量、环境变量、秘密变量 |
| 上下文 | 当前运行环境信息 | 用户上下文、会话上下文、系统上下文 |
| 知识 | 提供领域知识与文档 | FAQ知识库、SOP文档、产品手册 |
| 测试/发布 | 验证运营体正确性 | 沙盒测试、回放测试、灰度发布 |
| 运行时 | 实际执行与监控 | Loop引擎、Harness网关、日志中心 |

## 三、节点组件详细设计
节点是编辑后台最基础的积木。为了通用化，节点必须类型明确、参数可配置、输入输出可定义。
### 3.1 节点类型划分

| 节点类型 | 功能 | 输入 | 输出 | 典型配置项 |
| --- | --- | --- | --- | --- |
| 触发器节点 | 启动运营体 | 外部事件/定时 | 初始上下文 | 定时Cron、Webhook URL、手动触发 |
| AI决策节点 | 让LLM分析并决定下一步 | 当前上下文 | 决策结果/动作指令 | 提示词模板、输出Schema、模型选择 |
| 意图识别节点 | 判断用户意图 | 用户消息 | 意图分类+槽位 | 意图列表、示例、置信度阈值 |
| 信息抽取节点 | 从文本/页面提取结构化数据 | 文本/页面内容 | 字段值 | 抽取字段Schema、示例 |
| 内容生成节点 | 生成回复/报告/文档 | 上下文+模板 | 文本内容 | 模板、风格、长度 |
| 工具调用节点 | 执行Harness操作 | 动作参数 | 执行结果 | 选择工具、参数映射、超时 |
| 条件分支节点 | 根据条件走不同路径 | 变量/表达式 | 分支选择 | 条件表达式、默认分支 |
| 循环节点 | 重复执行子流程 | 条件（v1） | 循环结果 | 继续条件表达式、最大次数、循环体/退出目标（v1 仅条件循环，见 §5.3） |
| 并行节点 | 同时执行多个分支（v1：全部成功/全部完成两策略，见 §5.4） | 无 | 汇总结果 | 分支列表、joinTarget、合并策略 |
| 等待节点 | 挂起指定时间或等待事件（v1 仅定时等待，见 §5.5） | 时间 | 继续信号 | 等待时长（事件监听 v1 不做） |
| 子图节点 | 引用另一个运营体/子流程（v1 进程内引用已保存图，见 §5.7） | 子图入参 | 子图出参 | 子图ID、入参映射 |
| 人机协作节点 | 暂停并请求人工（v1 进程内审批信号，见 §5.6） | 审批请求 | 人工决策 | 审批说明、审批人、超时策略、通过/拒绝目标 |

### 3.2 节点的通用化接口设计
每个节点都遵循统一接口：
node:
id: string
type: string
name: string
description: string
config: object          # 节点类型专属配置
inputs:                 # 输入映射
- name: string
source: string      # 变量名/上下文路径
required: boolean
default: any
outputs:                # 输出声明
- name: string
type: string
retry:                  # 重试策略
max_retries: number
backoff: string
timeout: number
on_error: string        # 失败处理：stop/continue/跳转节点
### 3.3 节点参数配置面板
- 基础属性：名称、描述、图标、颜色（区分类型）。
- 输入参数：从变量选择器中选择来源（上游节点输出、全局变量、上下文）。
- 输出参数：定义输出变量名，供下游节点引用。
- 高级配置：超时、重试、失败处理、是否断点暂停。
- 节点校验：实时检查配置完整性，缺失必填项时高亮提示。
## 四、工具/适配器组件详细设计
工具是运营体“操作外部平台”的能力来源，适配器是工具的载体。要实现完全通用化，需要把“适配器”和“工具”分层设计。
### 4.1 适配器分层模型

| 层级 | 作用 | 示例 |
| --- | --- | --- |
| 连接层 | 管理认证、会话、网络 | OAuth2、API Key、Cookie、浏览器会话 |
| 能力层 | 定义可执行的操作 | 点击、输入、查询订单、发送消息 |
| 数据层 | 定义操作输入输出的数据结构 | 订单对象、用户对象 |

### 4.2 适配器类型

| 适配器类型 | 对接方式 | 典型工具 | 通用化设计要点 |
| --- | --- | --- | --- |
| API适配器 | OpenAPI/Swagger/自定义HTTP | create_order, get_user | 自动生成工具定义，参数Schema化 |
| 浏览器操作适配器 | Playwright + 视觉模型 | click, type, screenshot | 元素定位三层冗余，操作录制生成 |
| 移动端适配器 | Appium + 视觉 | tap, swipe | 元素库管理，屏幕识别 |
| 桌面端适配器 | 图像识别 + 键鼠模拟 | click_image, send_keys | 模板匹配，OCR辅助 |
| 数据适配器 | JDBC/ODBC/数据仓库 | query_sql | 只读/读写权限控制，结果集摘要 |
| 消息适配器 | IM/邮件/短信 | send_email, reply_message | 消息模板，群发限制 |
| IoT适配器 | MQTT/Modbus | read_sensor, control_device | 设备影子，协议解析 |

### 4.3 工具定义 Schema
每个工具必须包含：
tool:
id: string
name: string
description: string          # 自然语言描述，供LLM理解
adapter_id: string           # 所属适配器
action: string               # 具体动作
input_schema: object         # 输入参数JSON Schema
output_schema: object        # 输出参数JSON Schema
permission: string           # 所需权限
timeout: number
retry_policy: object
is_idempotent: boolean       # 是否幂等
### 4.4 适配器注册与发现
- 注册中心：每个适配器启动时向 Harness Gateway 注册，声明自己的能力和工具列表。
- 动态发现：编辑后台通过网关查询可用适配器，用户拖拽到画布即可使用。
- 健康检查：适配器定期心跳，不可用时后台置灰并提示。
### 4.5 自定义适配器创建方式
为了让用户能自己对接平台，编辑后台提供四种创建适配器的方式：
1. API导入：粘贴 OpenAPI/Swagger 文档链接或JSON，自动生成适配器和工具。
1. 操作录制：用户在自己平台上手动操作，系统用浏览器插件/录制器记录步骤，自动转化为工具。
1. 自然语言生成：用户描述“我要对接XX平台，能查询订单”，系统调用LLM生成适配器配置。
1. 开发者SDK：高级用户用SDK编写自定义适配器，上传到平台。

### 4.6 API 适配器（通用 HTTP）v1 契约

> 本条为 API 适配器 v1 的唯一权威契约，03 契约索引指向此处。v1 对应 §4.2 的「自定义HTTP」形态；OpenAPI/Swagger 自动导入（§4.5 方式 1）为后续形态。

**标识与包位**：channel 包 `src/atlas/httpapi/`（`api/` 为 FastAPI 服务端包位，09 待定项 5，不可复用；包名决策见 09 待定项 7），`adapter_id="http"`、`adapter_type="api"`，Demo 注册进同一进程内 AdapterRegistry，发现/心跳/权限/审计沿用 §4.4 与 06 §6.4。

**能力**：v1 仅一个工具 `http/request`，permission=write、is_idempotent=false、timeout 默认 30s。节点 tool_call 的 `config.tool="http/request"`，`config.params` 为字符串，经 04 §6.3 `{{路径}}` 插值后必须是 JSON 对象：

```json
{"method": "POST", "url": "/orders/123/receipt",
 "headers": {"X-Trace": "{{trigger-1.context.payload.order_id}}"},
 "body": {"note": "自动处理"}, "timeout": 10}
```

- `method`：GET/POST/PUT/PATCH/DELETE 之一，缺省 GET；非法值 FAILED（INVALID_PARAMETER）。
- `url`：必填；相对路径拼连接默认 baseUrl（以 `/` 为界做 urljoin），绝对 URL 直接使用。
- `headers`：可选 JSON 对象，与连接默认 headers 键级合并（同名键节点优先）；非对象 FAILED。
- `body`：可选；对象/数组按 JSON 序列化（自动带 application/json，除非默认/节点 headers 显式指定 content-type），字符串原样发送。
- `timeout`：可选正数秒，缺省取能力默认 30s。

**连接默认值（混合配置）**：adapter 构造或环境变量 `ATLAS_HTTPAPI_BASE_URL` / `ATLAS_HTTPAPI_HEADERS`（JSON 对象）/ `ATLAS_HTTPAPI_TOKEN`（注入 `Authorization: Bearer <token>`）提供默认 baseUrl 与公共 headers；节点 params 可覆盖/补充。v1 无加密存储、无连接 CRUD UI；秘密变量（§6.2）运行时注入随后续迭代。

**结果语义（fail-safe 对齐）**：

- 只要收到 HTTP 响应（含 4xx/5xx）→ ActionResult SUCCESS，output 固定为 `{"status": <int>, "headers": <dict>, "body": <object|string>}`；body 优先按 JSON 解析，失败返回文本。下游用 condition 判 `{{tool-x.result.status}}` 自行分支，图整体 run 仍 completed。
- 传输层失败（DNS/连接拒绝/读写超时）→ ActionResult FAILED，StructuredError code 为 `HTTP_CONNECT_ERROR` / `HTTP_TIMEOUT`；参数类错误为 `MISSING_PARAMETER`（缺 url）/ `INVALID_PARAMETER`（坏 method/headers/timeout/params 非合法 JSON）。
- v1 不自动重试（§4.3 retry_policy 形状未定），不做重定向外的特殊处理。

**安全边界**：v1 不做 SSRF 防护（egress 白名单、私网/元数据地址拦截均未实现），绝对 URL 可指向进程可达的任意地址；Demo mock 目标与后端同进程。出站安全策略、凭证加密、OAuth2 刷新统一缓做 docs/14 D22。

**Demo mock 目标**：后端内置 `GET /api/demo/mock/orders`（校验 `X-Demo-Token: demo-token`，缺失/错误返回 401 JSON；成功返回演示订单数组）与 `POST /api/demo/mock/orders/{id}/receipt`（回显请求体并标记 received），供离线端到端验证。

### 4.7 数据适配器（通用 SQL）v1 契约

> 本条为数据适配器 v1 的唯一权威契约，03 契约索引指向此处。v1 对应 §4.2 的「数据适配器 / query_sql / 只读读写权限」形态；JDBC/ODBC、数据仓库与 Schema 表单为后续形态（缓做 docs/14 D23）。

**标识与包位**：channel 包 `src/atlas/database/`（与平台自身存储 `memory/database.py` 分离——后者锁 postgresql+psycopg 且服务于记忆层，不可复用），`adapter_id="database"`、`adapter_type="database"`，Demo 注册进同一进程内 AdapterRegistry，发现/心跳/权限/审计沿用 §4.4 与 06 §6.4。

**能力（两个工具）**：节点 tool_call 的 `config.params` 为字符串，经 §6.3 `{{路径}}` 插值后必须是 JSON 对象。

1. `database/query`，permission=read、is_idempotent=true、timeout 默认 30s：

```json
{"sql": "SELECT order_id, amount FROM orders WHERE amount > :min",
 "params": {"min": 1000}, "limit": 500}
```

   - `sql`：必填字符串；`params`：可选对象或数组，作为 SQLAlchemy **绑定参数**传入（防注入的推荐路径，插值只用于动态结构）；`limit`：可选 1-1000 整数，缺省 500。
   - 输出 `{"columns": [..], "rows": [{...}], "row_count": <int>, "truncated": <bool>}`——结果集摘要，超 limit 截断并置 truncated=true。
   - 只读保障：PostgreSQL 连接以 `execution_options(postgresql_readonly=True)` 开启只读事务，查询结束 rollback；SQLite demo 无服务端只读，隔离依赖能力权限门（read）。
1. `database/execute`，permission=write、is_idempotent=false：`{"sql": "INSERT ... ", "params": {...}}`，提交事务，输出 `{"rowcount": <int>}`。v1 不做语句类型审查（DDL 亦允许），读写边界完全由 write 权限门与数据库账号承担。

**连接默认值**：环境变量 `ATLAS_DATABASE_URL`（**适配器专用，与平台自身 `DATABASE_URL` 隔离，防止图操作误伤平台库**）；允许 scheme：`postgresql+psycopg`、`sqlite`。adapter 自建 SQLAlchemy engine（scheme 白名单校验），不复用 memory 层工厂。未配置且未注入 engine 时调用返回 `DB_NOT_CONFIGURED`；SQLAlchemy 执行异常 → `DB_SQL_ERROR`（错误与 observe 中的连接 URL 一律 `hide_password=True` 脱敏）；缺 sql、params 非对象/数组、limit 越界 → `MISSING_PARAMETER`/`INVALID_PARAMETER`。

**安全边界**：sql 文本经图 `{{路径}}` 插值，拼接式插值存在 SQL 注入面——v1 不做 SQL 审查/只读账号强制，契约要求参数值走绑定 `params`；真实外部库接入前须先落 D23（账号最小权限、审计、egress 同 §4.6）。

**Demo 形态**：`ATLAS_DATABASE_URL` 缺失时，后端内置 SQLite 单连接内存库（StaticPool），seed 一张 `orders(order_id, reason, amount, status)` 两笔演示订单（与 §4.6 mock 订单同形）；`/api/demo/reset` 重新 seed（显式配置的外部库不被 reset 触碰）。

### 4.8 消息适配器（进程内消息服务）v1 契约

> 本条为消息适配器 v1 的唯一权威契约，03 契约索引指向此处。v1 对应 §4.2「消息适配器 / 消息模板 / 群发限制」的**进程内演示形态**：只记录、不真实投递；IM/邮件/短信/webhook 真实渠道为后续形态（缓做 docs/14 D24）。

**标识与包位**：channel 包 `src/atlas/message/`，`adapter_id="message"`、`adapter_type="message"`，注册/权限/审计同 §4.4 与 06 §6.4。

**能力**：v1 仅一个工具 `message/send`，permission=write、is_idempotent=false、timeout 默认 30s：

```json
{"channel": "email", "to": ["ops@example.com", "boss@example.com"],
 "subject": "退款审批通知：{{trigger-1.context.payload.order_id}}",
 "body": "金额 {{trigger-1.context.payload.amount}}，请处理"}
```

- `channel`：必填非空字符串（email/sms/im 或任意渠道标识，v1 不路由）；`to`：必填字符串或字符串数组，**数组上限 20**（群发限制，超出 INVALID_PARAMETER）；`channel=="email"` 时每个地址须含 `@`；`subject`/`body`：必填非空字符串。模板能力由 §6.3 `{{路径}}` 插值承担，不另建模板系统。
- 输出消息记录 `{"id": "<uuid4>", "channel", "to": <展平数组>, "subject", "body", "sent_at": "<iso8601>"}`；记录保存在进程内 MessageService（重启清空），`GET /api/demo/messages` 陪同查看，`/api/demo/reset` 清空。
- 参数错误（缺字段/空值/超群发/坏 email 形状）→ `MISSING_PARAMETER`/`INVALID_PARAMETER`。

**边界**：v1 **无真实投递**（不连 SMTP/IM/短信/webhook），写入记录即 SUCCESS；规格中的 `send_email`/`reply_message` 分渠道专名、回复线程、入站消费/订阅型触发、消息模板系统、限流退避与重试统一缓做 docs/14 D24（与 D20 IM 通知同批评估）。

## 五、逻辑组件详细设计
逻辑组件负责流程的控制和状态管理，是运营体从“线性脚本”走向“智能决策”的关键。
### 5.1 表达式引擎
- 用途：条件判断、变量计算、参数映射。
- 语法：支持常见表达式，如 {{user.age > 18 && order.total > 100}}。
- 内置函数：日期处理、字符串处理、数学计算、数组操作、JSON解析。
- 类型安全：表达式解析时做类型检查，错误即时提示。

> **首版语法白名单（Phase 2，2026-09-14 落地）**：条件表达式中 `{{路径}}` 只包裹变量引用，运算符写在花括号外，例如 `{{trigger-1.context.payload.amount}} > 1000 && {{status}} == 'paid'`（与 13 文档 U5 的裸表达式口径一致）。支持：比较运算 `> >= < <= == !=`、逻辑 `&& || !`、括号、数字（含负号）、单/双引号字符串、`true`/`false`/`null`；`{{x}} == null` 用于判缺失。**不支持**算术运算与内置函数（即上方完整表达式引擎目标缓做，触发见 14 登记表）；求值器为手写递归下降解析，禁止 eval。语法错误与纯字面量类型错误（如 `'a' > 1`）在保存/校验期一次性中文报错。
### 5.2 条件分支
支持类型：
- 表达式判断（A > B）
- 多条件组合（AND/OR/NOT）
- LLM智能判断（当条件无法用规则表达时，交给LLM输出分支）
- 默认分支：必须配置，防止未覆盖情况。
- 可视化：分支连线标注条件，鼠标悬停查看详情。

> **condition 节点 config 契约（Phase 2 首版，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> ```yaml
> type: condition
> config:
>   branches:                          # 有序分支，按数组顺序短路求值，第一个为真者胜出
>     - label: string                  # 分支名，非空，同节点内唯一；命中后写入 outputs.branch
>       expression: string             # 5.1 首版语法白名单内的布尔表达式，非空
>       target: node_id                # 目标节点 id，必须存在、非自环、且有对应出边
>   defaultTarget: node_id             # 必填；全部分支为假或求值失败时走此分支，须有出边
> ```
>
> 约束：`target` 在节点内互不重复且不得等于 `defaultTarget`；condition 节点的**每条出边必须被 branches∪default 覆盖**（不允许无标签死边），condition 不允许直连 END（终态由目标分支末端节点接 END）。边仍是 `{id, source, target}`（03 graph_definition），条件不挂边上、不进 edge 字段；画布上分支标签由 source 节点 config 反查渲染，多输出端口仅为编辑期视觉。
>
> 运行时语义（实现 `atlas.graph.loader`，经 LangGraph conditional edges）：执行器顺序求值一次并写产出，路由函数只读取值结果（不重复求值）。节点产出 `{branch, target, evaluation:[{label, expression, result}], expression_errors:[string]}`，默认分支 `branch="__default__"`；trace 增一行 `condition-x: branch=… → target`。含变量的类型错误或变量缺失无法静态发现时，**fail-safe 走 defaultTarget**，错误进 `expression_errors` 与 trace（安全默认：退款类场景默认分支应指向人工审核）。
> LLM 智能判断分支首版不做（缓做见 14 登记表 D14）；并行等其他节点仍按校验拒绝（循环节点见 §5.3，并行节点见 §5.4）。
### 5.3 循环
- 遍历循环：对列表/数组逐项执行子流程。
- 条件循环：满足条件时持续执行，直到不满足或达到最大次数。
- 中断与跳过：支持break、continue逻辑。
- 循环变量：自动生成index、item变量。

> **loop 节点 config 契约（Phase 2 第二项，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> v1 只实现**条件循环（while）**；遍历循环（列表逐项、item 变量、结果聚合）与 break/continue 缓做（见 14 登记表 D16/D17），循环变量 v1 仅暴露 `index`。
>
> ```yaml
> type: loop
> config:
>   mode: "while"                    # v1 固定 while
>   continueExpression: string       # §5.1 首版语法白名单内的布尔表达式，非空
>   maxIterations: 10                # 整数 1-100，必填
>   bodyTarget: node_id              # 表达式为真 → 进入/再次进入循环体
>   exitTarget: node_id              # 为假 / 达上限 / 求值异常 → 退出循环
> ```
>
> 拓扑约束（保存时静态校验，错误聚合中文报错）：
> - bodyTarget / exitTarget 必填、存在、非自环、互不相同；loop 节点**恰好两条出边**且目标集合 = {bodyTarget, exitTarget}，不允许直连 END（终态由退出路径末端节点接 END）。
> - **循环体**：从 bodyTarget 出发按出边 BFS（遇本 loop 节点与 exitTarget 停止）可达的全部节点。必须存在至少一条「回边」：某条边 target=本 loop 节点且 source ∈ 循环体（循环体末端连回 loop）；循环体不得泄漏到 exitTarget（退出路径只能由 loop 节点出发）。
> - 循环体内不得含 trigger 节点或其他 loop 节点（v1 不支持嵌套循环）。
> - **合法环白名单**：「loop → 循环体 → 回到同一 loop」的回边是唯一允许的图环。校验时把白名单回边临时移除后做环检测，剩余图中仍存在环 → 按 U7「循环依赖检测」拒绝（非法循环依赖）。
>
> 运行时语义（实现 `atlas.graph.loader`，经 LangGraph conditional edges + 回边）：loop 出边全部走 `add_conditional_edges`（与 condition 同约束，不与普通边混用），执行器可重入，每次进入读取自身上一次产出的 `iterations` 计数：
> 1. `iterations >= maxIterations` → 路由 exitTarget，exitReason=`max_iterations`（**fail-safe 退出**，trace 警告，运行仍 completed）；
> 2. 否则求值 continueExpression：求值异常/非布尔/变量缺失 → 路由 exitTarget，exitReason=`expression_error`，错误进 expression_errors（fail-safe）；
> 3. 表达式为真 → iterations 加 1 路由 bodyTarget（exitReason=null）；为假 → 路由 exitTarget，exitReason=`condition_false`。
>
> 节点产出 `{mode, iterations, index, target, exitReason, expression_errors:[string]}`：`iterations` 为循环体已执行次数，`index` 为当前一轮的 1-based 序号（首次进入前两者皆 0），循环体内节点可直接 `{{loop-x.index}}` 引用。trace 行：继续 `loop-x: continue (i/max) → bodyTarget`；退出 `loop-x: exit (reason) after N → exitTarget`。LangGraph recursion_limit 按 `2*节点总数 + 2*maxIterations*(循环体节点数+1) + 10` 派生传入，避免超步上限中断长循环。
### 5.4 并行与合并
- 并行分支：同时执行多个子流程，等待全部完成或部分完成后合并。
- 合并策略：全部成功、任一成功、全部完成（无论成功失败）。
- 数据合并：将各分支输出汇总为数组或对象。

> **parallel 节点 config 契约（Phase 2 第三项，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> v1 实现**静态扇出/汇聚**：分支在编译期固定，合并策略只支持 `all_success`（全部成功）与 `all_completed`（全部完成，无论成败）；`any_success`（任一成功，真 OR-join 需提前汇聚并取消其他分支）缓做（见 14 登记表 D18）。动态 map-reduce（运行期按数据生成分支）v1 不做。
>
> ```yaml
> type: parallel
> config:
>   joinStrategy: all_success   # v1: all_success | all_completed
>   branches:                   # 2-10 个；label 非空且唯一；target 互不相同
>     - { label: "分支A", target: node_id }
>     - { label: "分支B", target: node_id }
>   joinTarget: node_id         # 汇聚后唯一出口节点
> ```
>
> 拓扑约束（保存时静态校验，错误聚合中文报错，前缀「并行节点 {id}」）：
> - branches 2-10 个；label 非空且节点内唯一；target 必填、存在、≠自身、互不相同；joinTarget 必填、存在、≠自身且不属于任一 branch target。parallel 节点**出边数 = 分支数**且目标集合 = branches targets，不允许直连 END（汇聚后由 joinTarget 路径接 END）。
> - **分支区域**：从所有 branch target 出发按出边 BFS（遇 joinTarget 与本 parallel 节点停止）可达的全部节点。区域内不得含 trigger 节点或其他 parallel 节点（v1 不支持嵌套并行）；区域内允许 condition 与自包含 loop（loop 回边白名单规则同 §5.3，其出口须留在区域内或指向 joinTarget）。
> - **不得交叉/外泄**：区域内节点的每条出边 target 必须 ∈ 区域 ∪ {joinTarget}（禁止分支之间交叉串接或绕到区域外）；每个分支入口都必须存在到达 joinTarget 的路径；joinTarget 的入边只能来自区域内。
> - parallel 本身不引入环；环检测仍按 U7（loop 白名单回边先摘除再 DFS）。
>
> 运行时语义（实现 `atlas.graph.loader`，经 LangGraph conditional edges 返回多目标扇出）：parallel 出边全部走 `add_conditional_edges`（router 返回 branches targets 列表，不与普通边混用），各分支同超步并发执行。**汇聚屏障由编译期注入的合成网关节点 `__join__<parallel-id>` 实现**（spike 实测 LangGraph 对普通多入边不做 barrier，不会等待全部前驱；冒号为 LangGraph 节点名保留字符故用双下划线前缀）：各分支末端编译期 retarget 到网关，网关每超步检查每个分支是否已有末端产出——未齐则返回空 messages 写自我循环（"wait" 超步，不发事件），齐后聚合一次并经 conditional edge 路由到真 joinTarget，故 joinTarget **只执行一次**（不等长分支同样成立）。`__join__` 节点事件不外泄；汇聚完成时网关以 parallel 节点自身补发第二次 `node_end`（fork 时第一次为 `status:"running"`）。为支持并发写状态，GraphState 的 outputs 通道使用 dict 合并 reducer（`_merge_outputs`，key 级合并），status 通道 last-write，节点只回写自身分片。
>
> **失败语义（fail-safe）**：分支路径上节点产出出现 `result.status=="FAILED"` 即记该分支失败。`all_completed` 总是汇聚；`all_success` 下若存在失败分支，parallel 产出 `status="failed"` 与失败明细，但 **joinTarget 照常执行、运行整体仍 completed**（不做短路终止；下游可用 condition 判 `{{parallel-x.status}}` 决定人工兜底，与 condition/loop 的 fail-safe 风格一致）。
>
> 节点产出 `{mode:"parallel", joinStrategy, status:"success"|"failed", branches:[{label,target,status:"success"|"failed",error}], result:{<分支入口节点id>: <该分支路径末端节点产出>}, joinTarget}`；`result` 以分支入口节点 id 为键（label 可能含中文/空格，不作为变量路径键），可经 `{{parallel-x.result.<node-id>.…}}` 或数组下标引用（路径规则同 §6.3）。trace 行：扇出 `parallel-x: fork N branches → a, b`；汇聚 `parallel-x: joined (all_success) success` 或 `parallel-x: joined (all_success) failed: <label>（<error>）`。扇出不增加 LangGraph 递归深度，§5.3 的 recursion_limit 公式无需为本节点调整。
### 5.5 等待
- 用途：流程挂起一段时间后继续（节流、轮询间隔、外部系统冷却）。
- v1 仅定时等待；事件等待见缓做 D19。

> **wait 节点 config 契约（Phase 2 第四项，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> ```yaml
> type: wait
> config:
>   waitType: duration        # v1 唯一合法值
>   durationSeconds: 5        # 整数常量，1-600；v1 不支持变量/表达式动态时长
> ```
>
> 拓扑约束（保存时静态校验，错误聚合中文报错，前缀「等待节点 {id}」）：恰好 **1 条出边**，目标必须是已存在节点且≠自身、不允许直连 END（等待后须有后继）；入边数量不限。wait 是纯透传节点，可位于 condition 分支、loop 循环体（回边白名单规则同 §5.3）、parallel 分支区域（同 §5.4）内，自身不引入环也不增加 LangGraph 递归深度，recursion_limit 公式无需调整。
>
> 运行时语义（实现 `atlas.graph.loader`）：node_start 发出后执行器同步 `time.sleep(durationSeconds)` 阻塞，到时发 node_end，沿唯一普通边继续（不经 conditional 边）。SSE 同步流生成器运行于 Starlette 线程池工作线程，阻塞不卡事件循环，但会占用一个工作线程，故 v1 上限 600 秒；分钟级以上或事件驱动等待须走 D19 的中断-恢复模型。等待本身不失败、不重试（retry 配置保留不生效）。
>
> 节点产出 `{mode:"wait", waitType:"duration", durationSeconds: 5}`，可经 `{{wait-x.durationSeconds}}` 引用（路径规则同 §6.3）。trace 行：`wait-x: waited 5s`。事件等待（waitType=event，外部信号/回调恢复，需 LangGraph interrupt/checkpointer 与持久化）、动态时长、等待到指定时刻均缓做（见 14 登记表 D19）。
### 5.6 人机协作
- 用途：流程暂停，等待人工对当前事项作出决策（同意/拒绝），按决策走不同分支。
- v1 为进程内审批信号（审批 REST 端点放行执行线程）；真正的中断-恢复（LangGraph interrupt/checkpointer + 持久化、多实例、IM 通知、动态审批人/角色鉴权）见缓做 D20。

> **human_approval 节点 config 契约（Phase 2 第五项，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> ```yaml
> type: human_approval
> config:
>   summary: "订单 {{trigger-1.context.payload.order_id}} 退款，AI 建议人工复核"  # 必填非空，支持 {{路径}} 运行时插值（语法同 §6.3）
>   approver: "客服主管"          # 可选自由文本（角色/人名），仅展示与审计，v1 不做鉴权
>   timeoutSeconds: 300           # 必填整数常量，10-3600；v1 不支持变量/表达式
>   onTimeout: reject             # approve | reject，默认 reject；超时按此自动决策
>   approvedTarget: tool-refund   # 通过目标：已存在节点 id
>   rejectedTarget: tool-escalate # 拒绝目标：已存在节点 id，须与 approvedTarget 不同
> ```
>
> 拓扑约束（保存时静态校验，错误聚合中文报错，前缀「人机协作节点 {id}」）：恰好 **2 条出边**，目标必须分别等于 `approvedTarget`/`rejectedTarget`（两者非空、互异、均为已存在节点且≠自身），均不允许直连 END（两个决策方向都须有后继）；入边数量不限。节点可位于 condition 分支、loop 循环体（回边白名单规则同 §5.3）、parallel 分支区域（同 §5.4）内；两条出边均为 conditional 边（同 §5.2/§5.3 路由族），阻塞等待不产生 LangGraph 超步，recursion_limit 公式无需调整。
>
> 运行时语义（实现 `atlas.graph.loader` + `atlas.collaboration.approvals.ApprovalBroker`）：执行器渲染 summary 后在进程内 broker 登记 pending 请求（token=uuid4 hex），发出的 node_start 事件 data 携带 `approval:{token, summary, approver, timeoutSeconds}`，随后阻塞等待决策；决策到达后发 node_end，按 `decision` 经 conditional 边路由。决策三来源（首决生效）：① 人工经 `POST /api/approvals/{token}/decision` 放行（`resolvedBy:"human"`）；② run inputs 预置 `{"approvals": {"<node-id>": "approved"|"rejected"}}` 秒过（`resolvedBy:"input"`，非交互运行/测试用）；③ 等待满 `timeoutSeconds` 后按 `onTimeout` 自动决策（`resolvedBy:"timeout"`）。同一 token 重复提交决策返回 409；未知 token 返回 404。阻塞发生于 Starlette 线程池工作线程（SSE 必须真流式实时下发 node_start，见 12 文档），不卡事件循环但占用一个工作线程，故上限 3600 秒；跨重启/多实例的中断-恢复须走 D20。审批本身不失败、不重试（retry 配置保留不生效）。
>
> 节点产出 `{mode:"human_approval", decision:"approved"|"rejected", target:<被路由节点id>, token, summary, approver, resolvedBy:"human"|"input"|"timeout"}`，可经 `{{human-x.decision}}`、`{{human-x.resolvedBy}}` 引用（路径规则同 §6.3）。trace 行：`human-x: approved (human) → tool-refund` / `… rejected (timeout) → tool-escalate`。
### 5.7 子图
- 用途：引用一张已保存的子流程（复用节点 Schema 的独立 Graph），在当前位置整体执行一遍，实现流程的组合、嵌套与复用。
- v1 为**进程内引用式**（按已保存图 id 解析，同进程重入执行）；版本钉版与手动升级回归（§14）、子图市场/组织共享、跨运营体远程引用见缓做 D21。

> **subgraph 节点 config 契约（Phase 2 第六项，2026-09-14；本条为唯一权威，03 契约索引指向此处）**：
>
> ```yaml
> type: subgraph
> config:
>   graphId: "graph-7"            # 必填非空，已保存 Graph 的 id
>   inputs:                       # 可选，默认 {}；子图入参映射
>     order_id: "{{trigger-1.context.payload.order_id}}"  # 子图入参键 → 父图 {{路径}} 或字面量
> ```
>
> 拓扑约束（保存时静态校验，错误聚合中文报错，前缀「子图节点 {id}」）：恰好 **1 条普通出边**（同 §5.5 wait，不经 conditional 路由），目标为已存在节点且≠自身、不直连 END；入边数量不限。节点可位于 condition 分支、loop 循环体、parallel 分支区域内。
>
> 引用校验（编译期，需图解析器；实现 `atlas.graph.loader` 经 `graph_resolver` 注入，Demo 由 GraphStore 提供）：graphId 必须可解析；禁止直接自引用；跨图引用环（A→B→A）拒绝；**嵌套深度上限 3**（父图为深度 0，即最多父→子→孙→曾孙三层引用，对齐 07 §8 递归深度护栏）；被引用图递归过完整图校验，错误以「子图 {graphId}：」前缀聚合。`inputs` 限对象：键非空且节点内唯一，值为字符串（运行时按父图上下文做 §6.3 `{{路径}}` 插值，缺失引用原样保留）。
>
> 运行时语义（实现 `atlas.graph.loader`）：执行器把渲染后的 inputs 作为子图 run inputs 进程内重入 `run_graph`（子图 trigger `context.payload` + 同名全局变量覆盖，语义同 W9-W10 webhook 载荷），复用父图同一套适配器注册表/决策客户端/审批 broker；子图 node 事件**不外泄到父图 SSE**（子图执行不发事件），子图 trace 完整收入节点产出。阻塞执行于 Starlette 线程池工作线程（同 §5.5/§5.6），不产生父图 LangGraph 超步，父图 recursion_limit 公式不变，子图有独立编译限额。子图运行期异常（含解析/编译失败与深度守卫）按 **fail-safe**：节点产出 `status:"failed"` 与 error，run 仍 completed，沿唯一出边继续，下游可用 condition 判 `{{subgraph-x.status}}`（同 §5.4 汇聚 fail-safe 哲学，不做成功/失败双出口）。子图内含 human_approval 时审批端点可用，但因子图 node_start 不外泄，Demo v1 只能靠 run inputs 预置决策或超时自动决策（交互上屏随 D21）。retry 配置保留不生效。
>
> 节点产出 `{mode:"subgraph", graphId, status:"success"|"failed", error?:<失败时>, outputs:<子图 outputs dict>, trace:[<子图 trace 行>]}`，可经 `{{subgraph-x.status}}`、`{{subgraph-x.outputs.<子图节点id>.<键>}}` 引用（路径规则同 §6.3）。trace 行：`subgraph-x: graph-7 success (N nodes)` / `… failed: <error>`。
### 5.8 状态机
- 用途：管理业务对象生命周期（如订单的待支付→已支付→已发货→已完成）。
- 定义方式：在编辑器中定义状态节点和转移条件。
- 运行时行为：运营体根据当前状态和事件决定下一步操作。
- 与Graph的关系：状态机是Graph的一种特殊子图，可以嵌入流程中。
### 5.9 异常处理
- 局部异常：节点级on_error，可配置重试、跳过、跳转到指定节点。
- 全局异常：运营体级异常处理器，捕获所有未处理异常，执行统一降级策略。
- 自愈机制：操作失败时触发“诊断子图”，尝试修复后继续。

## 六、数据与变量系统设计
数据是运营体的血液，变量是数据的载体。通用化要求变量系统具备强类型、作用域、生命周期、可追踪特性。
### 6.1 变量类型

| 类型 | 说明 | 示例 |
| --- | --- | --- |
| 字符串 | 文本 | "订单已发货" |
| 数字 | 整数/浮点 | 100, 39.9 |
| 布尔 | 真假 | true |
| 对象 | 键值对 | { "name": "张三", "age": 25 } |
| 数组 | 列表 | ["A", "B", "C"] |
| 文件 | 图片/PDF等二进制 | 用户上传的截图 |
| 富文本 | 带格式文本 | 邮件正文 |

### 6.2 变量作用域

| 作用域 | 生命周期 | 可见范围 | 示例 |
| --- | --- | --- | --- |
| 全局变量 | 运营体定义期 | 所有节点 | 企业ID、品牌名称 |
| 节点变量 | 节点执行期 | 当前节点内部 | 临时计算结果 |
| 子图变量 | 子图执行期 | 子图内及调用方 | 子图入参/出参 |
| 会话变量 | 单次运行期 | 整个运行实例 | 当前用户ID、订单号 |
| 环境变量 | 平台/租户级 | 所有运营体 | 数据库地址、模型密钥 |
| 秘密变量 | 加密存储，运行时解密 | 授权节点 | API Token、支付密钥 |

### 6.3 变量引用语法
在编辑器中统一使用 {{变量路径}} 引用，例如：
- {{user.name}}：引用用户上下文中的姓名
- {{order.items[0].price}}：引用数组第一个元素的属性
- {{global.company_name}}：引用全局变量
- {{node_3.result.status}}：引用节点3输出结果中的status字段
### 6.4 数据流设计
- 节点输入：从变量/上游输出中映射。
- 节点输出：执行后写入指定变量，供下游引用。
- 数据持久化：关键变量持久化到数据库，支持断点续跑。
- 数据脱敏：日志和截图中自动脱敏敏感字段（手机号、身份证、银行卡）。
## 七、上下文与知识组件设计
### 7.1 上下文类型

| 上下文类型 | 内容 | 来源 |
| --- | --- | --- |
| 用户上下文 | 当前交互用户的身份、历史、偏好 | 会话初始化、CRM查询 |
| 会话上下文 | 当前运行实例的临时状态 | Loop运行时 |
| 运营体上下文 | 运营体的配置、版本、变量 | 运营体定义 |
| 平台上下文 | 租户信息、环境配置 | 平台级 |
| 系统上下文 | 时间、日期、语言、时区 | 系统 |

### 7.2 知识组件

| 知识类型 | 用途 | 存储方式 |
| --- | --- | --- |
| FAQ知识库 | 回答常见问题 | 向量库 |
| SOP文档 | 指导标准操作流程 | 文档库+向量化 |
| 产品手册 | 提供产品功能说明 | 文档库 |
| 业务规则 | 定义约束和决策条件 | 规则引擎/Graph |
| 历史案例 | 提供参考经验 | 案例库+向量检索 |

### 7.3 知识接入方式
- 文档导入：上传 PDF、Word、网页链接，自动解析并向量化。
- 结构化知识：通过表格/JSON定义 FAQ 对。
- 人工标注：在会话中标记优质回答，自动加入知识库。
- 知识更新：运营体运行中积累的新知识可自动沉淀，但需人工审核。
## 八、适配方式设计
为了让用户用最自然的方式配置运营体，编辑后台应提供多种适配方式，并支持随时切换。

| 适配方式 | 适用用户 | 操作方式 | 生成结果 |
| --- | --- | --- | --- |
| 模板一键安装 | 新手 | 选择行业模板，填写参数 | 完整运营体 |
| 自然语言描述 | 业务人员 | 用中文描述需求 | DSL草稿+画布预览 |
| 可视化拖拽 | 进阶用户 | 拖拽节点、连线 | 可执行的Graph |
| 操作录制 | 无技术背景 | 在平台手动演示一遍 | 适配器+流程节点 |
| API导入 | 技术人员 | 导入OpenAPI/Swagger | 适配器+工具列表 |
| 开发者SDK | 开发者 | 编写代码 | 自定义适配器/节点 |

关键设计：这些方式不是孤立的，而是可互转的。例如用户用自然语言生成初稿后，可以在画布上手动微调；操作录制生成的流程也能进一步用拖拽方式补充逻辑。

# #  **通用化标准与关键机制**
要真正达到“完全通用化”，编辑后台必须落实以下标准和机制：
### 9.1 Schema 驱动
- 节点、工具、变量、知识、适配器全部使用 JSON Schema 定义。
- 前端根据 Schema 自动生成配置表单，后端根据 Schema 做校验。
- 新增组件类型时，只需上传 Schema，无需改代码。
### 9.2 版本化
- 每个运营体、适配器、节点类型、知识库都有版本号。
- 支持回滚、对比、灰度发布。
- 模板和适配器可独立升级，不影响已发布运营体。
### 9.3 可观测性
- 每一步操作、决策、变量变化都记录日志。
- 提供可视化回放，定位问题。
- 实时监控运行状态，异常自动告警。
### 9.4 安全与权限
- 所有适配器连接使用加密存储。
- 高风险操作默认需要人工审批。
- 多租户隔离，数据权限控制。
- 敏感信息自动脱敏。
### 9.5 可测试性
- 内置沙盒环境，可模拟运行。
- 支持录制回放测试。
- 发布前必须通过预置挑战集。
- 运行时定期抽检，质量下降自动熔断。

**#  ****补充项**
补充细节主要集中在协作、调试、性能、安全、版本、AI 辅助配置、生态扩展等维度。
## 一、配置体验与编辑后台的“开发者体验”
### 1. 实时校验与错误提示
- 即时 Schema 校验：用户每填写一个字段，前端立即根据节点/工具的 JSON Schema 校验类型、必填、格式，错误就地提示。
- 依赖完整性检查：当变量引用上游节点输出时，系统自动检查上游节点是否存在该输出，不存在则高亮。
- 流程死锁检测：保存时检测是否存在不可达节点、循环依赖（loop 白名单回边除外，见 §5.3）、无条件分支缺失、并行分支交叉/无法汇聚（见 §5.4）。
- 一键修复建议：对于常见配置错误（如超时未设置、重试策略缺失），给出“一键应用推荐值”按钮。
### 2. 智能推荐与自动补全
- 节点推荐：根据当前流程上下文，AI 助手推荐接下来可能需要的节点（如“你已经获取了订单，是否要添加‘发送邮件’节点？”）。
- 工具推荐：当用户拖入“工具调用”节点时，根据节点名称或描述推荐匹配的 Harness 工具。
- 变量自动补全：在输入框中输入 {{ 时，弹出当前作用域下可选变量列表，支持模糊搜索。
### 3. 内联文档与引导
- 组件说明：每个节点/工具都有悬停提示和“查看详情”链接，展示用途、参数说明、示例。
- 新手引导：首次进入编辑器时，以分步任务引导用户完成“创建触发器 → 添加工具 → 设置回复”的完整流程。
- 视频/示例嵌入：在每个模板或适配器上提供 30 秒演示视频或交互式示例。
### 4. 画布性能优化
- 虚拟化渲染：当画布节点超过 500 个时，只渲染可视区域，滚动时动态加载。
- 聚合节点：将长串连续节点折叠为“聚合块”，点击展开。
- Web Worker 计算：将表达式解析、流程校验等 CPU 密集操作移到 Worker 线程，避免 UI 卡顿。

## 二、多租户与权限细节
### 5. 组件级权限控制
- 节点权限：敏感节点（如“执行退款”）可设置仅特定角色可编辑、可执行。
- 工具权限：每个 Harness 工具可声明所需权限等级（只读/写/删除/资金操作），用户在配置时需具备对应权限。
- 变量权限：秘密变量（如 API Token）仅对创建者和管理员可见，其他用户无法查看或复制。
### 6. 跨租户组件共享
- 组织内共享：租户可将自己的适配器、子图、模板分享给组织内其他成员，设置“只读/可编辑”权限。
- 跨租户市场：通过审核后可发布到公共市场，其他租户付费或免费使用。
- 使用统计与计费：共享组件被其他租户使用时，平台记录调用量，用于收益分成。
### 7. 审计与合规
- 配置变更审计：记录谁在何时修改了哪个运营体的哪个节点、变量、工具，支持对比和回滚。
- 执行审计：所有运行时操作（工具调用、LLM 决策、人工审批）都有不可篡改的日志，可导出。
- 数据地域控制：租户可指定数据存储和处理的地域，满足 GDPR、等保等合规要求。

## 三、调试与测试增强细节
### 8. 单步执行与断点
- 节点断点：用户可点击节点左侧设置断点，运行时暂停在该节点。
- 逐步执行：在调试模式下，可手动点击“下一步”逐个执行节点，观察变量变化。
- 条件断点：可设置在表达式满足时才暂停（如 {{order.amount > 500}}）。
### 9. 变量实时查看
- 变量面板：调试时右侧显示当前所有作用域变量（全局、会话、节点），支持搜索和筛选。
- 变量追踪：点击变量可查看其来源节点和值的变化历史。
### 10. 模拟数据与 Mock
- Mock 工具响应：测试时为工具调用配置模拟返回，避免真实影响。
- 模拟用户输入：在触发器节点可输入模拟用户消息/事件。
- 影子模式：可配置运营体以“仅记录不执行”模式运行，与实际人工操作并行对比。
### 11. 回放测试
- 操作录制回放：将一次真实运行或手动操作录制下来，作为回归测试用例。
- 批量回放：对多个测试用例自动回放，输出每个步骤的通过/失败状态。
- 差异对比：模型版本或配置更新后，自动回放同一批用例，对比行为差异。

## 四、版本与发布管理细节
### 12. 运营体版本化
- 语义版本控制：自动生成版本号（主版本.次版本.修订号），支持对比任意两个版本的差异。
- 草稿与发布分离：编辑时保存为草稿，不影响线上运行；发布后生成不可变版本。
- 发布说明：要求填写本次修改内容，供团队审阅。
### 13. 灰度发布与 A/B 测试
- 流量分配：可将新版本分配给 5%、10% 等比例的触发事件，与旧版本并行运行。
- 指标对比：实时对比新旧版本的关键指标（成功率、响应时间、用户满意度）。
- 自动回滚：若新版本指标显著恶化，系统自动回滚到旧版本并通知。
### 14. 模板与组件的独立版本
- 适配器版本：适配器升级后，已发布运营体继续使用旧版本，直到用户手动切换。
- 子图版本：子图更新不影响引用它的已发布运营体，用户可在编辑器中手动升级并回归测试。

## 五、运行时与性能细节
### 15. 冷启动与预热
- 浏览器实例预热：对于 Web 操作适配器，提前启动无头浏览器并缓存登录状态，减少任务执行延迟。
- 模型推理预热：模型服务保持常驻，避免请求时的冷启动。
### 16. 资源配额与限流
- 租户级配额：限制每个租户的并发运营体实例数、工具调用频率、存储空间。
- 节点级超时：每个节点可单独设置超时时间，避免单点阻塞整个流程。
- 降级策略：当资源不足时，自动将低优先级任务降级为排队或延迟执行。
### 17. 事件驱动与异步处理
- 消息队列：Harness 操作通过消息队列异步发送，前端通过 WebSocket 实时接收执行状态。
- 长任务处理：对于超过 1 分钟的任务，以异步任务形式执行，用户可离开页面稍后查看结果。

## 六、安全与合规补充
### 18. 提示注入防御
- 上下文隔离：系统指令与用户输入严格分离，使用特殊标记。
- 输入过滤：对来自外部的数据（用户消息、邮件内容）进行注入检测，发现可疑模式则警告或拦截。
- 工具输出过滤：LLM 生成的工具参数在执行前经过规则引擎校验，禁止执行危险操作。
### 19. 数据脱敏与加密
- 日志脱敏：自动识别并模糊手机号、身份证、银行卡、密码等 PII。
- 存储加密：敏感数据（密钥、用户数据）在数据库和传输中全程加密。
- 数据保留策略：可配置日志和记忆的自动清理周期，支持用户数据删除请求。
### 20. 高风险操作保护
- 二次确认：资金支付、数据删除、权限变更等操作必须人工确认。
- 金额阈值：可设置金额阈值，超过则需高级审批。
- 操作白名单：可定义允许执行的工具和动作列表，其他一概拒绝。

## 七、AI 辅助配置与自动化细节
### 21. 自然语言生成流程的准确性提升
- 意图拆解：将用户的一句话需求拆解为多个子任务，逐个生成节点。
- 确认式生成：生成草稿后，用自然语言总结流程，让用户确认无误再进入画布编辑。
- 交互修正：用户可继续用对话修正流程（如“去掉发送邮件的步骤”）。
### 22. 自动修复配置错误
- 错误诊断：当保存失败或测试失败时，AI 助手分析原因并给出修复建议。
- 一键修复：对于简单错误，用户点击“应用修复”自动修改配置。
- 学习用户偏好：记录用户的常见修改，逐渐优化推荐。

## 八、生态与市场细节
### 23. 组件市场
- 适配器市场：用户可发布自定义适配器，设置免费/付费/订阅，平台抽成。
- 模板市场：发布完整运营体模板，其他用户可一键安装并修改。
- 子图市场：发布可复用的子流程（如“电商退款处理”），供他人集成。
- 评分与评价：组件有评分、下载量、评论，优质组件获得推荐位。
### 24. 开发者 SDK 与文档
- SDK 支持多语言：Python/JS/Go 的 SDK，用于开发自定义适配器、节点类型。
- 本地调试工具：SDK 内置模拟环境，开发者可本地测试组件。
- 文档与教程：详细的 API 文档、示例代码、最佳实践。

## 九、协作与团队功能细节
### 25. 多人协作编辑
- 实时协同：多个用户可同时编辑同一运营体，采用 OT/CRDT 算法解决冲突。
- 评论与提及：在节点或连线上添加评论，@同事解决问题。
- 角色分配：可为运营体设置负责人、审核人、编辑权限。
### 26. 变更通知
- 订阅通知：用户可订阅运营体的变更、发布、异常事件，通过邮件/IM 接收。
- 日报/周报：系统自动生成运营体运行摘要，发送给团队成员。

## 十、移动端与多端支持
### 27. 移动端管理
- 监控与告警：在 App/小程序上查看运营体状态、接收告警、一键审批。
- 轻量编辑：支持在移动端修改简单参数（如阈值、开关），复杂流程仍在 PC 端编辑。

- 界面多语言：编辑后台支持中/英切换，可扩展。
- 自然语言多语言：用户可用多种语言描述需求，系统自动翻译为统一内部表示。
- 组件描述多语言：适配器和模板的说明支持多语言。
