## 1. 范围

两包：

| 包 | 内容 | 外部资源 |
|---|---|---|
| **A 邮件一键决策** | 邮件内含签名决策链接；无登录态的审批人打开公开落地页，查看审批详情、一键同意/拒绝（命中交互卡片时渲染 email 渠道卡片与动作/表单） | 零：真实投递仍随 SMTP 配置，离线全程可测 |
| **B 审批队列页（Inbox）** | 应用内新增「审批」页：聚合本租户全部 pending 审批，支持查看、同意/拒绝、卡片动作；手动 + 定时刷新 | 零 |

**不做（保留缓做，写入 14 D20 边界）**：

- 决策结果通知申请人（无申请人邮箱字段）；IM（钉钉/企微/飞书）/短信渠道；
- 审批挂起帧持久化余部、多实例/外部审批信号、动态审批人与节点级审批权限、审批评论流；
- 已决策历史页（broker 不保证保留策略）；邮件决策链接的限流/风控（沿用登录滑动节流模式的扩展留待真实使用）；
- 审批人与平台账号的邮箱绑定、SSO（随真实账号体系）。

## 2. 现状基线（已核实）

- `collaboration/approvals.py`：`ApprovalBroker`，`_Pending` 字段 summary/approver/timeout_seconds/node_id/graph_id/decision/resolved_by/comment/card_template_id/card_context/action_id；`request/restore/wait/resolve/complete_timeout/get/get_card_context/list_pending/reset`。
- `collaboration/notifications.py`：`EmailApprovalNotifier(message_service, public_url)`，邮件末两行固定为「请前往应用查看并处理：{public_url}」「本邮件仅为通知，不包含一键决策链接」。
- `api/main.py`：`GET /api/approvals`（read）、`POST /api/approvals/{token}/decision`（operate；支持 decision/comment 与 actionId/form 两路，卡片映射走 `map_action_output`）、`GET /api/approvals/{token}/card`（read）。
- `connections/oauth.py`：HMAC-SHA256 签名 base64url payload 模式（state），缺主密钥用固定 dev key + WARNING——本批邮件 token 复用同一模式与编码约定。
- 前端：`App.tsx` page union `'dashboard'|'editor'|'monitoring'|'memory'|'connections'|'users'`；登录页为独立外壳先例；无 react-router，切页靠 state；deep link 路由目前不存在。
- 质量门：后端 1141 passed/36 skipped；前端 557 passed/2 skipped/44 文件；oxlint 0/0；build 过。

## 3. A 包：邮件签名决策 token

### 3.1 token 结构

新模块 `src/atlas/collaboration/email_token.py`：

- 形状：`base64url(json).base64url(hmac_sha256)`（与 oauth state 完全同构，编码工具复用或同构复制，不引新依赖）。
- payload：

```json
{"v": 1, "tenant": "t1", "at": "<approval token>", "iat": 1780000000, "exp": 1780003900}
```

- `at` = `ApprovalBroker.request` 返回的审批 token；token 本身是不记名秘密，签名层再绑定租户与有效期。
- 有效期：`ttl = min(timeout_seconds, 3600) + 300`（宽限 5 分钟，供落地页查看；审批超时后图已按 onTimeout 自决，决策端点首决生效返回 409，语义安全）。
- 签名密钥：环境变量 `ATLAS_APPROVAL_HMAC_SECRET`；未配置时退回**固定 dev 常量并 WARNING**（与 oauth dev state key 同策略；.env.example 补生成命令）。
- API：`issue(tenant, approval_token, timeout_seconds, *, clock) -> str`；`verify(token, *, clock) -> payload`。失败分类：`TokenMalformed` / `TokenBadSignature` / `TokenExpired`（验签先于过期判断，过期只在签名合法后判定）。

### 3.2 邮件改造

`EmailApprovalNotifier` 构造器改为持 `tenant_id` 与 `TokenIssuer`（落码签名对齐：`EmailApprovalNotifier(message_service, public_url, tenant_id, issuer)`）；`notify_pending` 签名不变（tenant 不再每次透传）。

邮件正文末段替换为：

- `一键处理：{public_url}/approvals/{signed_token}`
- 保留应用入口一行；删除「不包含一键决策链接」旧文案。
- 签名/构造异常属于通知旁路：与 T2 既有 fail-safe 一致，吞异常、不阻断图。

### 3.3 公开端点（无登录）

装配需要 `TenantRegistry.peek(tenant_id)` 新方法：**只返回已存在的租户服务，绝不惰性创建**（现有 `get()` 会创建空租户，不可用于公开端点）。

| 方法与路径 | 语义 |
|---|---|
| `GET /api/approvals/email-view?token=<signed>` | 只读、无副作用（邮件预取/防病毒扫描安全）。verify → peek → `broker.get(at)`。200 返回视图（见下）；签名坏/格式错/过期/租户或审批不存在 → 统一 **404** 中文文案，不回显 token、不区分原因（不泄漏存在性） |
| `POST /api/approvals/email-decision` | body `{token, decision?, comment?, actionId?, form?}`（与现有决策请求同形，`token` = 签名 token）。verify → peek → 复用与登录态决策端点**同一决策应用函数**（落码从 `decide_approval` 抽出共享 helper，防双路漂移）：卡片动作走 `map_action_output`；首决生效；未知 404、已决 **409**、卡片错配 422 |

`email-view` 200 载荷：

```json
{
  "status": "pending",
  "summary": "…", "nodeId": "…", "graphId": "…",
  "approver": "…", "timeoutSeconds": 600,
  "createdAt": 1780000000, "remainingSeconds": 512,
  "card": { "channel": "email", "…": "email 渠道渲染结果，仅 cardTemplateId 命中时存在" }
}
```

审批已决时 `status="resolved"` 且带 `decision/resolvedBy`（落地页展示最终态，不再显示操作按钮）。`createdAt` 依赖 broker 新字段，见 §5。

### 3.4 审计

`email-decision` 成功时显式写一条审计（与登录成功显式审计同模式）：`actor="email-link"`、`action="approval.email_decision:{decision}"`（审计 schema 无 metadata 列且本批不扩列，decision 编进 action；graph_id/node_id 不落审计）；**不记签名 token、审批 token、comment 正文**。GET email-view 不记审计（预取噪声）。

## 4. B 包：审批队列页

- 数据复用现有 `GET /api/approvals`（read）：items 增 `createdAt`（§5），其余字段不变。
- 决策复用 `POST /api/approvals/{token}/decision`（operate）；卡片详情复用 `GET /api/approvals/{token}/card?channel=web`。
- 新页 `frontend/src/pages/Approvals.tsx`：
  - 顶部说明 + 手动刷新 + 10s 轮询（仅在页面可见时）；空态中文提示。
  - 表格列：审批说明 / 指定审批人 / 图 / 节点 / 创建时间 / 剩余时间（超时后显示「已超时」，不影响图的自决语义）/ 操作。
  - 操作：同意、拒绝（Popconfirm 二次确认，comment 选填）；命中卡片行显示「查看卡片」，弹出 Modal 复用现有 web 卡片渲染与动作提交组件。
  - 权限：viewer 可看不可操作（按钮隐藏，与既有角色门一致）；operator/admin 可决策。
- 入口：Dashboard 增「审批队列」入口（viewer 可见进入只读）；App page union 增 `'approvals'`。不做跨页角标计数。

## 5. Broker 小改

`_Pending` 增 `created_at: float`（UTC epoch，`request` 与 `restore` 均赋值；restore 用恢复扫描时刻）。`list_pending`/`get` 公共投影增 `createdAt`；剩余时间由消费方按 `created_at + timeout_seconds - now` 计算。无 DSL/EdgeDSL/Graph 版本变更，无迁移。

## 6. 前端 A 包落点

- 深链路由：`App.tsx` 启动期先判 `window.location.pathname`，前缀 `/approvals/` 时渲染独立外壳页 `pages/EmailApproval.tsx`（在登录恢复逻辑之前，无登录可访问）；末段路径即签名 token。
- `EmailApproval.tsx`：拉 email-view → 展示审批详情与剩余时间；pending 显示同意/拒绝（卡片时渲染 email 卡片动作与表单，提交 actionId/form）；二次确认后 POST；成功转最终态；404/过期 → 中文 Alert 并给应用入口链接；全程不写 localStorage 会话。
- `apiClient` 增 `getEmailApprovalView(token)` / `decideByEmail(payload)`（不带 Bearer 也可，签名 token 即凭证）。
- 文案：新增 i18n 走 `approvals` namespace（zh-CN 填实，en-US 空骨架 `{}` 随 D12），对齐 M12 既定模式。

## 8. 契约同步与 ADR

- **ADR T27**（docs/10 §4）：邮件决策采用「签名 capability URL」而非「登录 + 邮箱绑定」。理由：当前无用户-邮箱绑定结构；capability URL 与密码重置链接同形（HMAC + 短有效期 + 首决生效 + 显式审计 + GET 只读防预取）；零新依赖，复用 oauth state 签名。密钥/绑定的生产化（KMS、账号邮箱唯一约束）随真实账号体系。
- 三处同步：10 ADR → 02（认证/审批能力行）→ 09（email_token 模块、Approvals 页）。
- 落码收口回填：03（email decision token、email-view 载荷、pending.createdAt）、04 §5.6（邮件决策权威补注）、06（公开决策路径与 peek 边界）、12（2 新端点 + 前端 /approvals 路由）、13（测试行）、14（D20 再次部分取回，不解除）、00（地图 36）、08（落码条）、handoff、CHANGELOG。
