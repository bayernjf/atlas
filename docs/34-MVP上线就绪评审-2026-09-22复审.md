双实例那条的机制链（脚本按步打印，退出码非 0 即实锤）：A 的 run 挂在 `human_approval`（`timeoutSeconds=25`）并写入 `interruptions` 帧 → **B 启动时 `main.py:154 recover_pending` 替 B 重建了同一 token 的 pending，并起一条 `_resume_run` 续跑线程**（B 视角 pending 立即可见、同 token＝True）→ 人工在 A 决策 approved 返 200，A 沿「通过」分支写下游一次 → B 的 Event 收不到 A 进程内的决策，25s 后自己走 `onTimeout=reject`，**同一条 run 再写一次下游**，两进程随后互相覆盖 run 终态。对照组 `RECON_SKIP_B=1`（只起一个实例）＝通过分支×1、拒绝×0，确证双跑出自跨进程、不是单进程重复。**含义：任何 `replicas>1`、滚动发布、崩溃重启都可能让一次审批退款两次。**

另记一条与 worker 数无关的既有缺口（同一脚本测出，别误归因给多实例）：**sync `/run` 的急停在单实例下也返 409**——`cancellation_broker.register` 只在 `main.py:2696` 的流式路径调用，同步运行从不登记句柄。
