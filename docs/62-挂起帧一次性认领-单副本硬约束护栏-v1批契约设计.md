双跑的机制链（脚本按步打印，退出码非 0 即实锤）：实例 A 的 run 挂在 `human_approval` 并写 `interruptions` 帧 → 实例 B 启动时 `api/main.py:154 recover_pending` 为**同一条活帧**重建 pending 并起 `_resume_run` 续跑线程 → 人工在 A 决策 approved，A 沿「通过」分支执行下游；B 的 Event 收不到跨进程决策，25s 后自己走 `onTimeout=reject`，**同一条 run 第二次执行下游**，两进程再互相覆盖 run 终态。对照组 `RECON_SKIP_B=1`（只起一个实例）＝只落 1 次，确证成因是跨进程、不是单进程内重复路径。

## 1. 范围与非目标

**范围内（两项，L1 当批落码，L2 只出契约）**

- **L1 单副本硬约束护栏**：把"偶然安全"变成"设计上的拒绝"——容器入口对 `workers>1` fail-closed，Dockerfile 显式 `--workers 1`，compose 钉 `replicas: 1`，部署文档明文写出约束与原因。零 schema、零业务代码。
- **L2 挂起帧一次性认领（本文主体设计，待立项落码）**：`interruptions` 加消费标记，**任何进程在越过挂起点、执行下游之前都必须先原子认领该帧**；认领点位于 `graph/loader.py` 三处挂起（审批／事件等待／时长·到点等待）之后，经注入的 `resume_claim(token)` 判定，输家停止驱动、把终态让给赢家。恢复扫描及其续跑线程**保持不变**——那是单实例重启后推进挂起 run 的唯一驱动（论证见 §2 D-2）。

**显式非目标（均维持原缓做，本文不解除、也不偷偷做一半）**

- 真·多实例化：审批/事件等待/急停 broker 跨进程路由、webhook 幂等环 PG 化、登录节流与告警限流 PG 化、灰度态跨实例热同步、`/metrics` 跨进程聚合 —— 随 D19/D20/D27/D31/D32/D11。
- 下游副作用幂等化（把 `tool_call` 执行做成可重放）—— 那是"崩溃后自动接手"的前提，成本远高于本文，单列议题。
- 引入 Redis／消息队列／分布式锁／定时器：一个都不引（Redis 依赖去留仍是独立的选型待拍板项，见 docs/14 与 README 技术栈行）。
- 给 sync `/run` 补取消句柄：另案（`main.py:2696` 的 `cancellation_broker.register` 只在流式路径，单实例也恒 409），与本文同批但独立成原子，不混进认领改造。

## 2. 决策（L2 落码前必须逐条拍板；本文只推荐，不代拍）

**D-1 语义取向：at-most-once，不是 at-least-once。** ⚠️ 这是对上一轮口头方案「owner＋惰性租约」的**自我修正**。租约的含义是"进程死了租约到期后别人可以接手重放"，而下游是真实退款／真实写库、**不幂等**，可回收＝把"两个进程同时跑"换成"崩溃后隔一段时间再跑一遍"，风险同类。故本文选：**一条帧只允许被续跑一次，认领即消费**；代价是进程在续跑途中崩溃则该 run 永久停在 suspended，需人工介入（可观测、不重复扣款）。

**D-2 认领落点：loader 的「越过挂起点」那一刻，三处挂起共用一个注入口。** 先说被否掉的两版草稿，免得落码时又绕回去：

- ❌ 草稿一「只在 `_resume_run` 入口认领」：不成立。原始进程（A）走的是**请求线程内的 inline 继续**（`broker.wait()` 返回后直接往下执行节点），根本不经过 `_resume_run`；只闸恢复线程＝A 与 B 仍各跑一遍。
- ❌ 草稿二「恢复扫描不再起续跑线程」：更不成立。**续跑线程是单实例重启后唯一能推进挂起 run 的东西**（`_resume_from_frame` 的 `threading.Thread(_resume_run)`），删掉等于把 docs/24 §2.4 的恢复能力连根拔掉，还把"重启后用户点批准"变成永久卡死。

✔ 落点（读码确认）：三条挂起路径都在 `graph/loader.py` 里「先 `_emit_frame(...)` 写帧 → 再等待 → 等待返回后继续执行节点」——① 审批 `:721` `_await_human_approval`（内部 `broker.wait(token)`），② 事件等待 `:595` `event_wait_broker.wait(token, ...)`，③ 时长/到点等待（`:693` 写帧后睡 `actual_seconds`）。所以**认领必须落在这三处等待返回之后、执行下游之前**，一处语义三处调用。`_resume_run` 也是经 `run_graph(resume=frame)` 走同一段代码，因此**同一个钩子同时管住"原进程继续"和"恢复进程继续"两种角色**，不需要在 API 层再补判断。loader 保持不碰存储：沿用 `frame_sink` 的注入口先例（docs/24 §1.1），新增一个可调用参数 `resume_claim(token) -> bool`（API 层注入，内存档传 `None`＝恒真、行为逐字不变）。

**D-3 时钟权威：只用 DB 时间。** 标记列写 `CURRENT_TIMESTAMP`，与 `interruptions.created_at`／`deadline_at` 同源；**绝不**用应用侧 `now_iso()` 参与认领判定（微秒省略与跨进程偏斜都会咬人，教训同 docs/61 注记 ⑥）。

**D-4 输家怎么办：停止驱动、把终态让给赢家，不新增 run 状态。** 认领失败的一方**不再执行挂起点之后的任何节点、也不写 run 终态**；它返回的形状就用"该 run 仍处于挂起"的既有形状（赢家随后会写终态、清帧）。**刻意不新增 `superseded` 之类的 run 状态**——那会牵动 docs/03 状态枚举、04/12 契约、PG 与前端标签，收益只是排障可读性；改为在日志里记一条 `帧 <token> 已被 <resumed_by> 接管、本进程停止驱动`。

**D-5 内存档（`ATLAS_STORAGE_BACKEND=memory`）零改动。** 无库表即无跨进程面，护栏只管 L1 的 worker 数。

**D-6 L1 护栏形态：入口脚本质检 + 镜像与编排各自钉死**（三道都做，因为三条被绕开的路径互不重叠：改 CMD、`--scale`、`docker run --entrypoint`）。

## 3. L2 形状（契约，待落码）

### 3.1 迁移 029

```sql
-- 幂等：ADD COLUMN IF NOT EXISTS，两列均可空（NULL＝从未被续跑），可重复执行
ALTER TABLE interruptions ADD COLUMN IF NOT EXISTS resumed_at TIMESTAMPTZ;  -- DB 时钟 CURRENT_TIMESTAMP 置位
ALTER TABLE interruptions ADD COLUMN IF NOT EXISTS resumed_by TEXT;      -- 进程身份（见 3.3）
```

`002_storage.sql` 同步补两列（新装库一次建齐，照 021/024/026 先例）。可空＝从未被续跑；非空＝已消费，任何进程都不得再执行其下游。**不建新索引**——认领只按 `resume_token` 单行命中，而它本就是本表主键（`002_storage.sql:49`）。`resumed_at` 用 TIMESTAMPTZ 而非仓库主约定的 TEXT，理由是本表已有同类型列 `deadline_at`（`:55`）且该列要参与时间比较，跟**表内**既有口径走比套全局约定更不容易漂移；本表 `created_at` 是 TEXT，属历史异类，不跟。

### 3.2 认领纯函数（`storage/recovery.py`）

```python
def claim_frame_for_resume(engine, resume_token: str, who: str) -> bool:
    """原子一次性认领：只有把 resumed_at 从 NULL 翻成 DB 当前时刻的那个进程返回 True。"""
    # UPDATE interruptions SET resumed_at = CURRENT_TIMESTAMP, resumed_by = :who
    #  WHERE resume_token = :token AND resumed_at IS NULL
    # rowcount == 1 → True；==0 → 已被别的进程消费，调用方必须直接放弃、不抛
```

- 只此一条 SQL 承担互斥，靠 PG 的行级锁与 `resumed_at IS NULL` 谓词，**不引 advisory lock、不引 SELECT FOR UPDATE SKIP LOCKED**（那是两种实现抢同一行时的过度设计）。
- loader 侧只见 `resume_claim(token) -> bool` 这一个注入 callable（API 层用 `functools.partial(claim_frame_for_resume, engine, who=进程身份)` 包好），**loader 不 import 存储层**——照 `frame_sink` 的既有注入口，不新增第二种耦合。
- 返回 False 的分支**静默停止驱动并记一行 info/warning**，绝不抛进 run 线程——与 `_record_history`（docs/61 H2）、`_safe_record`（docs/60 G5）同一条 fail-safe 家族纪律；但**它必须真的停止驱动**，这是本改造唯一的实质闸门。

### 3.3 进程身份 `who`

`f"{socket.gethostname()}:{os.getpid()}"`，落 `resumed_by` 仅供排障（"这条 run 被谁消费了"），不参与判定，不做注册中心。

### 3.4 接线点（四处，全部只在 PG 档生效）

| 位置 | 现在 | 改成 |
|---|---|---|
| `graph/loader.py` 三处挂起（审批 `:721`／事件等待 `:595`／时长·到点等待 `:693` 之后） | 等待返回即继续执行下游 | 等待返回后先 `resume_claim(token)`；返 `False` 即**停止驱动**（不执行后续节点、不写 run 终态、按 D-4 返回挂起形状并记一行日志） |
| `run_graph`／`_execute_node` 形参链 | 只有 `frame_sink` | 新增 `resume_claim: Callable[[str], bool] \| None`，与 `frame_sink` 同链路全透传（含子图重入），缺省 `None`＝恒真 |
| `api/main.py:_resume_run` 调 `run_graph` | 已传 `frame_sink`／`resume=frame` | 补传同一个 `resume_claim` 工厂（恢复线程与 inline 走同一判定，无第二套口径） |
| `api/main.py:_frame_sink_for` 旁 | 写帧 | 不动——写帧时 `resumed_at` 保持 NULL（＝"还没人越过这个挂起点"），认领只发生在真正要继续执行的那一刻 |

**关键约束**：内存档没有帧、`resume_claim=None` 即恒真，两条档的 run 语义必须继续逐键一致（照 H4 两档对拍口径）；`_resume_from_frame` 起线程的行为**不变**（单实例重启续跑靠它）。

- U811 两档一致：内存档不查表、行为逐键不变（既有全量门零回归即证）。
- **端到端门＝`scripts/dev/multi_instance_resume_recon.py` 本身**：改造后该脚本必须从"退出码 1（双跑实锤）"翻成"退出码 0（只落一次）"。它是本批唯一能证明修好了的东西，收口必须贴真跑输出。

## 8. 残余风险（写清楚，别当成修完了）

1. **卡住是设计选择，两种路径都会**：① 进程在**认领之前**崩溃 → 帧未 claimed，重启后仍可被续跑；② 进程在**认领之后、下游执行完成之前**崩溃 → 帧已 claimed，任何进程都不再驱动它，该 run 永久 suspended。第②种是本次改造新引入的（有意的）收紧：宁可永久卡住，也不重复扣款。两条都靠 D36（人工重放／reconcile）收敛，本批不开该口。
2. **L2 做完 ≠ 支持多副本**：webhook 幂等环仍会重复触发整张图、登录节流仍是每进程一份、`/metrics` 仍是单进程快照、灰度态仍不跨实例。L2 只拆最贵的那颗雷（一次审批退款两次）。
3. **认领不覆盖"决策前"的重复**：两进程各自持 pending 时，用户可能在两个进程上都点一次批准——第二次会因 `decision is not None` 被拒（409）或被跨进程看不见而各自生效；D-2 的认领只保证**下游执行**一次，不保证**审批体验**一致。要后者得做 D20 的决策跨实例正题。
4. 时钟：认领判定全部走 DB 时间（D-3），应用侧不掺和；这也是 `resumed_at` 用 `TIMESTAMPTZ` ＋`CURRENT_TIMESTAMP` 写、而不复用 `now_iso()` 的原因（同表 `deadline_at` 已是该类型）。
